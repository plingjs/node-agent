# lesson06 · 多 Agent 委派 —— 面试题讲解（Node 版）

> 10 题，三层深度。每题按固定结构展开：**考点 → 答题结构 → 参考话术 → 代码锚点 → 常见追问**。
> 本章可引用的证据：新增 5 个文件共 396 行（`depth_guard.js` / `subagent.js` / `agent_tool.js` / `context_select.js` / `parallel.js`）；`agent.js` 只改了构造函数末尾一次注册（第 44-54 行），主循环一字未动；`test.js` 19 个用例全绿，其中 1 个是把缺口钉死的负向测试；实跑观测到父 Agent 的 `recent` 只有 4 条。

使用建议：T1 三题必须脱口而出；T2 要能讲"我踩过 / 我这么修"；T3 直接对标"0→1 方案设计"。

## T1 基础原理（必过线）

### Q1：多 Agent 到底解决什么问题？为什么不是"人多力量大"？

- **考点**：能不能给出机制层面的理由，而不是复述"多个 Agent 协同工作"这种同义反复。
- **答题结构**：先说单 Agent 的两个天花板 → 给出隔离这个核心机制 → 一句判断标准（什么时候不该拆）。
- **参考话术**："两个天花板。一是上下文污染：让一个 Agent 去分析目录，它要调十几次 `search_files`、`read_file`，几十条工具结果全堆在 `messages` 里，紧接着问它真正的问题时，注意力被那些过程数据稀释。二是职责混杂：探索、分析、写代码挤在一个 system prompt 里互相干扰。多 Agent 的解法是把一件独立子任务交给新建的子 Agent，它有自己独立的 cm，跑完只回传一段文本摘要——父的 `messages` 里只多一条 `tool` 消息，中间几十次工具调用一条都上不来。所以核心价值是上下文隔离，并行提速是第二个收益。判断标准也实用：能用单 Agent 就别拆，因为每个子 Agent 都是一份独立的 token 开销加一次结果拼装，五行的查询拆三个子 Agent 是负优化。"
- **代码锚点**：`subagent.js` 第 51 行子 Agent 自己 `new` 一个 `TieredContextManager`，与父的 `agent.js` 第 37 行那个是两个对象；`agent_tool.js` 第 96 行只把 `{ result, fromSubagent: true }` 还给父。
- **常见追问**：*隔离会不会丢信息？* → 会，所以子 Agent 的职责是"汇报可行动的结论"。本章在这件事上只做了一件事：fork 模式（`context_select.js` 第 28 行）允许显式把父的最近 4 条带下去，剩下的靠任务描述写清楚——`delegate_task` 的参数说明里就要求"包含目标、约束、需要什么证据"（`agent_tool.js` 第 53 行）。

### Q2：子 Agent 和父 Agent 的上下文是什么关系？工具集呢？

- **考点**：能不能把"共享什么、不共享什么"说清楚，这是整章的骨架。
- **答题结构**：上下文各自独立（贴证据）→ 工具表共享（贴证据）→ 一句话总结"共享手、不共享脑"。
- **参考话术**："上下文完全独立：`SubAgent` 构造时 `new` 一个自己的 `TieredContextManager`，送进模型的消息只有 system 加 task 两条。实跑抓到的证据是父 Agent 的 `cm.recent` 角色序列——`user → assistant(tool_calls:delegate_task) → tool → assistant`，一共 4 条；子 Agent 内部那些 `search_files` 的 tool 消息一条都没爬上来。工具表反过来是共享的：子 Agent 拿到的 `registry` 就是父那一个对象，工具实现、权限分级、错误分层全部复用，隔离只做在"给模型看哪些 schema"这一层（`subagent.js` 第 60 行 `_schemas` 里加白名单过滤和 delegate_task 过滤）。一句话：共享手、不共享脑。"
- **代码锚点 / 实证**：`test.js` 第 62 行断言子 Agent 只收到 2 条消息、system 恰好是 `DEFAULT_SUBAGENT_PROMPT`；第 79 行构造父上下文含 `abc123`，断言子 Agent 收到的内容里没有这个字符串。
- **常见追问**：*父的 cm 和子的 cm 会不会因为共享 `registry` 而串味？* → 不会，`registry` 里只有工具定义和权限规则，没有任何对话状态；对话状态只活在各自的 cm 里。

### Q3：怎么防止无限递归委派？

- **考点**：这道题考的是防御性设计——为什么一个门槛不够。
- **答题结构**：先讲清爆炸的后果 → 两层防御各自防什么 → 承认两者边界不一致，并说清为什么没顺手改。
- **参考话术**："两层。第一层物理隔离：拼工具列表时按深度过滤，`depth=1` 的子 Agent 的 schema 里根本不出现 `delegate_task`（`subagent.js` 第 69 行调 `shouldExposeDelegateTool`），模型看不到就不会去调，也省掉一轮注定失败的推理。第二层运行时兜底：工具真被调用时再查一次 `canDelegate(depth, maxDepth)`（`agent_tool.js` 第 70 行），越界返回一段提示而不是抛异常。为什么两层都要——物理隔离防的是正常路径，运行时兜底防的是绕过工具列表的路径：手动构造工具、配置写错、以后有人改了过滤逻辑。顺带一个我在这个项目里发现并留着没改的东西：两个门限的边界差一层，`canDelegate(1, 2)` 是 `true` 而 `shouldExposeDelegateTool(1, 2)` 是 `false`，也就是子 Agent 路径上那个兜底永远触发不到。改成一致等于放开"父→子→孙"三层，那是产品决策不是笔误，所以我按现状把两个值都钉进测试（`test.js` 第 110 行）、把缺口写进文档，改法等决策。"
- **代码锚点**：`depth_guard.js` 第 14 行 `canDelegate` 返回 `depth < maxDepth`；第 22 行 `shouldExposeDelegateTool` 返回 `depth + 1 < maxDepth`；第 27 行的提示文本让模型自己改用已有工具，而不是直接失败。
- **常见追问**：*为什么不直接抛异常让上层处理？* → 委派是模型决定的行为，异常会打断它的规划；返回一段可行动的文本，它会自己降级成"用我的工具直接干"。错误对模型可见、可行动，是这个项目的统一做法（`errors.js` 第 35 行的 `toResult`）。

## T2 工程深度（区分度所在）

### Q4：`delegate_task` 为什么做成工厂函数？

- **考点**：闭包传状态的理解，以及"为什么不用全局变量或消息传递"。
- **答题结构**：工厂函数产出什么 → `depth` 为什么必须每个实例一份 → 落回代码。
- **参考话术**："因为它要携带"我是第几层"这个状态，而工具定义对象是死的。`createDelegateTool({ depth, ... })`（`agent_tool.js` 第 33 行）每次调用把当前的 `depth` 关进闭包，父 Agent 拿到的那个捕获 `depth=0`；`fn` 里 `new SubAgent({ depth: depth + 1 })`（第 87 行）就是靠这个闭包变量算出子 Agent 的层级。换成全局变量会在多实例下互相污染；换成在消息里传层级，模型得参与记账，不可靠。工厂加闭包是纯函数式组合，层级沿调用链自然传递。老实说本章里子 Agent 从不会创建这个工具——`depth≥1` 就被物理过滤掉了——所以闭包设计当前的真正作用是给"将来放开深度"留位置。"
- **代码锚点**：`agent.js` 第 44-54 行是父侧唯一一次调用；`agent_tool.js` 第 68-97 行是 `fn` 全体；`test.js` 第 214 行验证 `subagentPrompt` 能定制子 Agent 的 system 位，靠的也是同一条工厂通道。
- **常见追问**：*多实例共用一个 registry 会怎样？* → 会互相覆盖：每个 `new Agent` 都会注册自己的 delegate 工具，后注册的覆盖先注册的，只有最后一个的 `depth` 生效。这段风险写在 `agent.js` 第 40-43 行的注释里，本章靠子 Agent 的物理隔离兜住；要彻底解决得给每个 Agent 独立 registry。

### Q5：子 Agent 的上下文预算为什么只要父的一半？

- **考点**：资源分层意识，以及"共享哪些能力、砍掉哪些"的取舍。
- **答题结构**：预算差异 → 理由 → 顺带把能力清单的差异讲清。
- **参考话术**："子 Agent 的 cm 给 `maxTokens = 2048`、`keepRecent = 4`（`subagent.js` 第 52 行与第 55 行），父 Agent 是 4096 和 6（`agent.js` 第 59 行与第 62 行）。理由是职责单一——它只做一件子任务，不需要大视野；预算小意味着更早触发压缩（`context_manager_v2.js` 第 90 行 `needsCompaction`），单个子 Agent 不可能把资源吃到失控。能力清单上砍掉的是记忆注入和错误预算——记忆归父管，子 Agent 不写记忆；错误预算（`ERROR_BUDGET = 4`，`agent.js` 第 18 行）也只有父有，这是本章的一个已知缺口，子 Agent 遇到反复 retryable 的失败只能靠 `MAX_TURNS = 8` 和 Loop 检测兜底。补齐的是 Loop 检测：这是 code review 时发现的，最初子 Agent 死磕同一工具要空转到第 8 轮，现在同工具同参数第 3 次就注入 `LOOP_DETECTED`（`subagent.js` 第 76-84 行，`test.js` 第 341 行有回归用例）。"
- **代码锚点**：`subagent.js` 第 52 行、第 76 行；`agent.js` 第 16-18 行三件套（`MAX_TURNS` / `LOOP_THRESHOLD` / `ERROR_BUDGET`）。
- **常见追问**：*为什么子 Agent 的错误预算干脆不做？* → 因为它上层的 `registry.execute` 已经把工具异常全隔离成结构化结果（`registry_full.js` 第 76-83 行），加上 `MAX_TURNS` 和 Loop 检测，失控风险已经可控；真正的缺口在 `delegateParallel` 那条路径上（见 Q7）。

### Q6：并行委派怎么实现？成本怎么控？并行到底省什么？

- **考点**：并发原语的使用 + 成本意识，两条都要。
- **答题结构**：实现（并发池）→ 为什么不用 `Promise.all(map)` → 成本三板斧 → 一句话说清省什么。
- **参考话术**："用一个固定 worker 数的并发池：`workerCount = Math.min(maxConcurrent, tasks.length)`（`parallel.js` 第 61 行），每个 worker 用 `while (next < tasks.length)` 抢任务，`results[i] = await sub.run(...)` 按下标回填（第 57 行），最后 `Promise.all` 等全部完成（第 62 行）。不用 `Promise.all(tasks.map(...))` 是因为那会把所有子 Agent 一次性点火，任务多了成本不可控。共享游标 `next++` 不需要加锁，Node 单线程，`const i = next++` 中间插不进别的 worker。成本三板斧：并发上限（本章 demo 用 2）、子 Agent 小预算（2048）、工具白名单（demo 里两个子任务只给 `search_files` + `read_file`，拿不到 `run_shell`）。并行省的是墙钟时间不是 token——4 个任务并发 2，总耗时接近最慢的那 2 个，总 token 还是 4 份。任务之间有依赖、或者几个子 Agent 要写同一个文件时就不该并行。"
- **代码锚点 / 实证**：`test.js` 第 235 行用 `active`/`maxActive` 计数器测得峰值并发 ≤ 2；第 267 行验证越界时 `llmCalls === 0`（一个子 Agent 都没造）；`test.js` 第 297 行是父 Agent 经 LLM 决策委派的完整链路。
- **常见追问**：*结果乱序怎么办？* → 不会乱，按下标回填，顺序和 `tasks` 一一对应，跟谁先跑完无关；`mergeResults`（第 67 行）再把它拼成给模型读的文本。

### Q7：子 Agent 会不会死循环？出错呢？

- **考点**：故障路径的完整性——这是我在这章里最想被问到的题，因为答案有对有缺。
- **答题结构**：死循环怎么防 → 出错分两条路径讲（一条接住了、一条没接）→ 讲清为什么这条缺口是刻意的。
- **参考话术**："死循环分两层，`MAX_TURNS = 8` 是硬上限，`_checkLoop` 是同工具同参数第 3 次就注入 `LOOP_DETECTED`（`subagent.js` 第 76 行）。出错要看走哪条路径，这是关键。走工具入口时有人接：父调 `delegate_task` 经 `registry.execute`，子 Agent 的异常会冒到那层的 `catch`，被转成 `{error:{code:"EXECUTION_FAILED"}}` 回填给父，父接着往下跑——`test.js` 第 360 行专门测了这个：让子 Agent 的 LLM 抛错，断言父拿到的 tool 消息里有 `EXECUTION_FAILED` 且父照常给出最终回答。走 `delegateParallel` 入口时没人接：那个函数里没有 per-task 的 try/catch，一个子 Agent 抛错会让整个 `Promise.all` reject，`/demo` 又不在 `try` 块里（`main.js` 第 114-119 行的 catch 只包了 `agent.run`），结果是 REPL 直接退出。这条我写成了负向测试（第 390 行）钉住现状，第 13 章补错误兜底时会改成"失败任务返回错误文本、其余任务结果照常可用"。同一个故障、两条路径两种结果，差别就在有没有那层 catch——这是我认为委派里最值得主动交代的地方。"
- **代码锚点**：`subagent.js` 第 76-84 行（Loop 检测）、第 108 行 `MAX_TURNS` 循环；`parallel.js` 第 46-59 行 worker 里没有任何 try/catch；`registry_full.js` 第 76-83 行是接住异常的那层。
- **常见追问**：*为什么先不修？* → 修法有分歧（每个任务包一层返回错误文本，还是让整批失败让调用方决定重试），这是产品语义不是纯技术选择；加上本章的负向测试已经把现状钉住，改动会有测试托底，等第 13 章做错误兜底时一起定。

## T3 架构设计（对标"0→1 方案设计"）

### Q8：这套多 Agent 离生产还差什么？

- **考点**：能不能自己列出缺口，而不是等人问。主动列缺口比宣称"我做了多 Agent"有说服力得多。
- **答题结构**：按"编排 → 观测 → 成本 → 安全 → 持久化"五块讲，每块一句现状、一句生产要求。
- **参考话术**："五块。编排：本章只有"父委派子、结果回填"这一条边，生产要 DAG 编排（依赖、条件分支、动态路由）和消息总线，让子 Agent 之间能异步通信，而不是事事经父中转。观测：现在 `verbose` 日志里只有 depth 没有身份标识——我实跑时两个并发子 Agent 都打印成 `子Agent#1`，分不出谁是谁；生产要给每个子 Agent 一个 traceId，把 token、耗时、工具调用链结构化上报，这是 OpenTelemetry 那种活。成本：本章有并发上限（`parallel.js` 第 61 行）和子 Agent 小预算（2048），但缺全局配额和熔断，任务一多就会失控。安全：子 Agent 与父共享同一个 registry，权限只能靠工具白名单收窄（`subagent.js` 第 67-69 行），生产应该让子 Agent 的权限严格窄于父，甚至到 OS 级沙箱。持久化：子 Agent 的中间结果只在内存里，进程一重启就没了——这也意味着无法做"跑到一半恢复"。"
- **代码锚点**：`parallel.js` 第 61-62 行（并发上限，只是入口限制）；`subagent.js` 第 148 行（verbose 日志只有 depth）；`agent.js` 第 44-54 行（共享 registry 注册）。
- **常见追问**：*这五块里哪一块最先做？* → 观测。没有 trace 和 token 账本，其余四块的收益和风险都无法度量，团队会在"多 Agent 到底值不值"上吵不完。

### Q9：多 Agent 系统怎么测？

- **考点**：故障与隔离这类"看不见的行为"怎么变成断言，以及能不能诚实交代测试的薄弱处。
- **答题结构**：按隔离 / 并发 / 深度 / 继承 / 端到端 / 故障六类各给一个具体断言 → 主动交代一个测试薄弱点。
- **参考话术**："隔离用一个构造出来的机密串：父上下文里放 `abc123`，委派后断言子 Agent 收到的 messages 里没有它（`test.js` 第 79 行）。并发用计数器：`active` 自增自减记录峰值，断言 `maxActive <= 2`（第 235 行）——不能只断言结果数量，那样并发没生效也测不出来。深度用边界值加 schema 双保险（第 110、121、128 行）。fork 用内容断言：父的近期内容 `背景B` 真的出现在子 Agent 的 messages 里（第 186 行）。端到端用脚本化模型走完整链路，断言父确实发出了 delegate 调用且最终答案是收尾回答（第 297 行）。故障路径用注入抛错，断言父拿到的是 `EXECUTION_FAILED` 而不是进程崩（第 360 行）。全部离线，因为 `Agent` 和 `SubAgent` 都把 `llm` 当构造参数收。有一个薄弱点我得说清楚：测试区分父、子调用靠的是 `messages[0].content.includes("子 Agent")` 这个字符串约定，它不是产品能力——如果哪天子 Agent 的默认 system 提示改掉这四个字，所有父子分支判断会一起失效，测试会静默误判而不是报错。更稳的做法是给 `SubAgent` 注入一个 traceId 标识，这个还没做。"
- **代码锚点 / 实证**：19 个用例、约 300ms、全离线；命令是 `npm test`（`package.json` 第 7 行 `node --test test.js`）。
- **常见追问**：*负向测试为什么要有？* → 它把"缺口确实存在"变成可回归的事实。本章第 390 行断言 `delegateParallel` 一挂全挂；第 13 章补完兜底后，这条断言会改成"失败任务返回错误文本、其余结果可用"——测试本身记录了演进，别人接手时一眼能看到这里曾经是什么样。

### Q10（压力题）：子 Agent 跑了三分钟还没返回，用户已经不耐烦了，你怎么处理？

- **考点**：交互与可中断性。这道题在考"你有没有想过用户"，而不是并发技巧。
- **答题结构**：先承认本章的现状 → 再给五条分层方案（超时、取消、进度、降级、可观测）→ 最后给一个当下的止血做法。
- **参考话术**："先说实话：本章这套做不到，子 Agent 一旦跑起来只能等它撞上 `MAX_TURNS = 8` 或者自己收尾，用户没有任何抓手。要落成产品，五件事按优先级排。一是超时：给整个 `sub.run` 套一个时间上限，超时返回"子任务超时"这条文本给父，让父自己决定重试还是降级。二是可取消：`AbortSignal` 一路传下去，用户说算了能立刻中断——这需要 `llm.js` 第 37 行那个 `fetch` 支持 `signal`，现在没有。三是进度：子 Agent 跑了几步、正在搜第几个文件，流式推给前端，等待才不焦虑。四是降级：父自己用工具把活干了，宁可慢也别卡死用户——`delegate_task` 返回错误文本的设计天然支持这一点，模型看到错误会自己动手。五是可观测：给每个子 Agent 一个 traceId，等出问题时能说清"哪个父委派了哪个子、跑了多久、调了什么"，现在 verbose 日志里只有 depth（`subagent.js` 第 148 行），连并发两个子 Agent 都区分不开。当下能做的止血是父侧兜底：`Promise.race` 加超时包住委派，超时就当这个工具失败。"
- **代码锚点**：`subagent.js` 第 108-159 行（循环只有 `MAX_TURNS` 一个出口）；`llm.js` 第 37-44 行（`fetch` 未接 `AbortSignal`）；`agent_tool.js` 第 95-96 行（返回结果或错误都走同一条回填通道，所以降级不需要改父）。
- **常见追问**：*为什么不在委派前先估个耗时？* → 估不准，子任务的步数取决于模型和工具返回；生产上更靠得住的是"给预算"而不是"给预测"——token 预算、步数预算、时间预算，任一超了就走降级路径。
