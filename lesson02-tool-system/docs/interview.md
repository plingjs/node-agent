# lesson02 · 工具系统 —— 面试题讲解（Node 版）

> 10 题，三层深度。每题按固定结构展开：**考点 → 答题结构 → 参考话术 → 代码锚点 → 常见追问**。
> 本课可引用的"证据"：9 个源文件 707 行、25 个离线用例（`npm test` 实测 39ms）、六步流水线（`registry_full.js:46` 起）、6 个错误码、三级权限决策树、两道防失控（Loop 阈值 3 / 错误预算 4）。

使用建议：T1 三题必须脱口而出；T2 要能讲"我踩过 / 我这么修"；T3 直接对标"0→1 方案设计"。全章的总纲只有一句：**LLM 是不可信调用方，工具系统就是给它的防御性 API**。任何一个"为什么"都能回收到这句上。

## T1 基础原理（必过线）

### Q1：第 1 章的 if-else 路由为什么撑不住？注册表解决了什么？

- **考点**：能不能看出"工具定义"这件事的复杂度在哪，而不是把它当成一次重构。

- **答题结构**：第 1 章的三个具体问题 → 注册表的解法 → 一句开闭原则落地 → 语言差异（schema 从哪来）。

- **参考话术**："第 1 章的加工具流程要动两处：`TOOLS` 数组里写一份 JSON Schema、`call_tool` 里补一个 `if (name === ...)` 分支，两处靠人工同步。三个工具时没问题，三十个工具时那个路由函数就是谁都改不动的巨型 switch，而且工具没法按场景动态启用。第 2 章把工具做成一个定义对象 `{name, description, params, fn}`——协议和实现装在同一个对象里，`register()` 注册、`Map` 查找路由，加一个工具只写一个对象，注册表代码零改动，这就是开闭原则。另外一个细节：JS 没有运行时类型系统，`async ({city}) => ...` 这个签名在执行期读不出 `city` 是 string，所以 schema 必须显式声明；Python 版能靠类型注解自动生成。生产上 JS 用 Zod——一个定义同时产出 JSON Schema 和运行时校验器，避免 schema 与实现双份维护。"

- **代码锚点**：`registry.js:25` 的 `createRegistry()` 用闭包锁住 `tools` Map，只暴露 `register`（`registry.js:31`）/ `getSchemas`（`registry.js:37`）/ `execute`（`registry.js:52`）三个方法。`getSchemas()` 生成的就是 OpenAI Function Calling 的 `tools` 字段格式。

- **常见追问**：*为什么用工厂函数而不是 class？* → 工具表是实例状态，闭包比 `this` 更难被误改；每调一次 `createRegistry()` 就是一个独立实例，测试里开十个互不污染，不需要"重置全局状态"的钩子。第 1 章的 `TOOLS` 是模块级常量，有状态的模块必须做成实例。

### Q2：讲一下完整的工具执行流水线，每一步的顺序为什么不能换？

- **考点**：有没有把"防御"落成固定顺序的工程直觉，还是每次想起来哪层写哪层。

- **答题结构**：六步清单 → 两处顺序的"为什么" → 共同出口（失败也是数据）。

- **参考话术**："六步：注册表查找（不存在 → `TOOL_NOT_FOUND`）→ 解析参数 JSON（非法 → `INVALID_PARAMS`）→ 权限决策（拒绝 → `PERMISSION_DENIED`）→ 参数校验（schema 驱动、宽容转换）→ 执行工具（异常全隔离）→ 返回 `{result}` 或 `{error:{code,message,retryable}}`。两处顺序有讲究。权限在参数校验之前是最小权限原则：先问'能不能做'，再问'做得对不对'，一个参数都不合法的调用更不该触碰副作用；反过来排的话，被拒绝的操作和参数错的操作在审计里会糊成一团。解析 JSON 在权限之前，是因为权限决策要看参数内容——`confirm(name, args)` 要把参数摆到人面前，删东西这种事尤其得让人看清'删的是哪一条'，参数都解不出来就没法判断，直接拦掉。最重要的一点是六步有共同出口：每一步的失败都变成结构化的 `role:"tool"` 消息回填，不往上层抛异常，所以模型能自己换参数、换工具或向用户解释，进程不会因为一次坏调用死掉。"

- **代码锚点**：`registry_full.js:46` 起的 `execute()`，六步的注释编号都在（`registry_full.js:47` / `:51` / `:59` / `:67` / `:75`，第六步是返回）。异常隔离的两个分支在 `registry_full.js:79-82`。

- **常见追问**：*顺序换一下会怎样？* → 权限放校验后面：非法参数会先消耗校验逻辑，且"被拒绝"和"参数错"两类审计事件混在一起；解析 JSON 放权限后面：`confirm` 拿不到参数，用户看的是 `undefined`，审批变成盲批。两处都是"安全边界要排在有副作用的前面"的变体。

### Q3：权限分级 read/write/danger 怎么定的？三态确认是什么？为什么 danger 不给"始终允许"？

- **考点**：安全默认值的直觉——分级依据、默认方向、授权作用域。

- **答题结构**：分级依据 → 三态 → danger 的特例 → 两个安全细节（fail-closed、实例级状态）。

- **参考话术**："分级依据是副作用 × 可逆性：read 无副作用自动放行；write 有副作用但可逆（新增/覆盖），需要确认，可以'始终允许'；danger 高影响不可逆（删除、支付、发布），每次强制确认。三态确认是 `confirm(name, args)` 返回 `true`（放行本次）/ `"always"`（放行并记住）/ `false`（拒绝），对应生产框架里的 ProceedOnce / ProceedAlways / Cancel。danger 不给'始终允许'的实现细节是：`alwaysAllow` 集合的快捷放行判断只对 WRITE 生效（`kind === Kind.WRITE && has(name)`），danger 即使被记进集合也每次必问——不可逆操作不存在'一次信任、永久免审'。另外两个安全细节我特意做的：没有确认通道时（后台 Agent、非交互场景）不是放行而是拒绝，默认值必须选安全的方向；`alwaysAllow` 是实例字段不是模块级单例，全局共享会让会话 A 的授权静默扩大到会话 B，那是权限提升漏洞。"

- **代码锚点**：`Kind` 三个等级在 `permissions.js:16`；决策树在 `permissions.js:50` 的 `check()`；`alwaysAllow` 实例字段在 `permissions.js:36`；WRITE 快捷放行在 `permissions.js:54`；fail-closed 在 `permissions.js:56`；danger 的终端提示在 `permissions.js:62`。测试锚点：实例隔离 `test.js:118`、danger 不免审 `test.js:271`、fail-closed `test.js:282`。

- **常见追问**：*danger 的工具怎么定？* → 按"造成的影响能不能逆转"定，不看工具名字听起来凶不凶：读操作取名 `execute_sql` 也是 read，`DROP TABLE` 那条语句是 danger；实际做法是注册期静态声明 + 代码 review 清单，声明与决策分离，审计一眼就能看出哪些工具危险。*`"always"` 这种字符串返回值在 TS 里怎么建模？* → 联合类型 `boolean | "always"`，配字面量收窄用；很多框架干脆用枚举（ProceedOnce / ProceedAlways / Cancel），比裸 boolean 表达力强，还能防住把 `"always"` 拼成 `"Always"` 这种低级错误——权限系统里一个拼错的字符串就是一次静默拒绝。

## T2 工程深度（区分度所在）

### Q4：参数校验为什么要做"宽容转换"？边界在哪？

- **考点**：把"严格 vs 宽容"当成本问题算，而不是当风格偏好选。

- **答题结构**：模型参数错误的三种形态 → 宽容的经济学 → 边界（哪些坚决不转）→ 报错信息的受众。

- **参考话术**："模型给参数是采样生成的，不是表单提交，常见三种错：必填没给、类型不对（整数给成 `"3"` 或 `3.0`）、冒出 schema 里没有的字段。这三种如果放进工具函数里才炸，模型收到的是 `Cannot read property 'weather' of undefined` 这种堆栈，它不知道下一步该改什么。宽容转换的账很简单：模型输出 `"3"` 还是 `3` 是随机性，为格式小错重试一轮 LLM 的代价（延迟 + token）远大于本地 `parseInt` 一下，所以能预期的本地修正在本地修。但边界很清楚——会改变语义的转换坚决不做：`boolean` 永不转数字，字符串 `"true"` 也不收成 boolean，array 和 object 不做深转换。这类'顺手修一下'的代价是模型学不到正确的形状，下一次还这么传。还有一条配套原则：报错信息的受众是模型，不是人。`缺少必填参数 city（期望类型: string）` 是一句能照着做的指令。"

- **代码锚点**：`validateParams` 在 `validation.js:23`，三条规则的实现分别在 `validation.js:29`（必填）、`validation.js:37`（逐参数类型与未知参数）、`validation.js:51`（有错就抛 `invalidParams`）；宽容转换表在 `validation.js:59` 的 `coerce()`，integer 分支 `:61`、number `:67`、string `:74`、boolean `:78`。测试锚点：`test.js:66`（`3.0`/`"3"`/`3.7` 都收、`"abc"` 拒）。

- **常见追问**：*宽容会不会掩盖模型的问题？* → 掩盖的是格式噪音，不是语义错误。语义错误照样拦（枚举值不存在、必填缺失一个都放不过），而且本地修正不留痕、不烧 token；真正需要"教模型"的错误都从 `INVALID_PARAMS` 走，message 是照着 schema 写的。

### Q5：为什么错误要结构化（code + retryable）？一个 message 字符串不够吗？

- **考点**：错误处理的架构位置——错误是给人看的还是给系统用的。

- **答题结构**：字符串撑不住的三件事 → 分层设计（内部异常/对外数据）→ message 的定位 → 生产延伸。

- **参考话术**："纯 message 撑不住生产的三件事：日志分类（'参数错'和'超时'要进不同告警通道）、重试决策（超时值得重试，参数错重试一万次还是错）、监控统计（哪类错误占比最高就是优化方向）。三者共同的前提是机器可读的错误码，所以我定义了 6 个 `ErrorCode`，配一个 `retryable` 布尔值——它同时是后面错误预算的燃料。分层设计是：文件内部流转用 `throw ToolError`，跨出去回传模型时统一 `toResult()` 转成普通对象，异常管内部、结构化数据管对外。message 本身不是堆栈，是写给模型的纠正指令：`` 工具 `hack_tool` 不存在。请只使用系统提供的工具。 `` 后半句是行为纠正。生产延伸一步：错误码进监控看板做工具健康度——某个工具 `EXECUTION_FAILED` 率突增，那是它的依赖挂了，不是模型的问题。"

- **代码锚点**：`ErrorCode` 表在 `errors.js:10`（`ERROR_BUDGET_EXHAUSTED` 在 `errors.js:16`），`ToolError` 类在 `errors.js:25`，`toResult()` 在 `errors.js:35`，三个工厂函数 `invalidParams` / `toolNotFound` / `executionFailed` 在 `errors.js:47` / `:54` / `:61`。流水线里的转换点在 `registry_full.js:49`、`:56`、`:63`、`:71`、`:80`、`:82`。

- **常见追问**：*为什么不 try/catch 包住整个循环了事？* → 那会把"模型该看到的错误"和"系统级故障"混在一起丢掉。错误要分类（参数错 / 权限错 / 执行错），分类信息正是模型自我纠正的依据，也是后面做错误预算、熔断、告警路由的输入。

### Q6：Loop 检测和错误预算各防什么？`MAX_TURNS` 为什么不够？

- **考点**：能不能举出轮数上限漏掉的具体失控形态，以及防护的处置哲学。

- **答题结构**：两类失控 → 两种防护的算法 → 处置方式（告知而非静默）→ 我在实现上踩的坑。

- **参考话术**："`MAX_TURNS` 漏两类。第一类是模型反复调同一个工具同一参数——每次调用都是'有效调用'，轮数根本到不了上限，只是原地打转。第二类是模型死磕一个持续报错的工具，每次微调参数重试，签名不同就不算死循环，轮数也没到，但 token 一直在烧。对应的两道防护：Loop 检测用调用签名 `工具名|参数JSON` 计数，同签名重复到阈值（3）就判定死循环；错误预算累加 `retryable` 错误，到阈值（4）就强制收手。处置方式两道都一样：不静默杀进程，而是把终止原因当成工具结果塞回去——'检测到死循环'、'重试预算耗尽，请放弃该方案，换一种方法'，给模型一次体面收尾的机会。防护的目的是改变模型行为，不是惩罚模型。我实现时踩过一个真坑：判定死循环之后原来写的是 `break` 跳出本轮的工具循环，剩下的 `tool_call` 就没有对应的 `role:"tool"` 消息了，而 `assistant(tool_calls)` 和 `role:"tool"` 必须成对，缺一条下一轮请求就被服务端 400 拒。改成'判定之后仍为每个 `tool_call_id` 回填一条 LOOP_DETECTED 结果，只是不再真的执行'，回归用例构造了一轮 4 个同签名调用：第 3 个触发判定，第 4 个仍被回填。"

- **代码锚点**：三个常量在 `agent.js:15` / `:16` / `:17`；签名计数在 `agent.js:43` 的 `_checkLoop()`；判定后的回填在 `agent.js:80-89`，错误预算在 `agent.js:98-106`；每个 `tool_call_id` 都回填在 `agent.js:109`。测试锚点：`test.js:177`（注入 LOOP_DETECTED）、`test.js:230`（预算耗尽）、`test.js:256`（MAX_TURNS 精确停在第 10 轮）、`test.js:314`（配对回归）。

- **常见追问**：*阈值为什么是 3 和 4？* → 经验值，且两者防的是不同形态：签名阈值太小会杀掉"同一工具查多个城市"这类正常重复（参数不同，签名不同，所以其实不受影响），错误阈值太小会让模型来不及换方案。生产上这两个值应该按任务类型配置，和 token 预算联动，同时保留 `MAX_TURNS` 做最后兜底——三层预算各管一种失控。*一轮里模型要调 5 个工具呢？* → 现在实现是 `for` + `await` 顺序执行（`agent.js:67`），保序、回填稳；这 5 个之间没依赖时可以用 `Promise.all` 并行，但回填必须按 `tool_call_id` 一一对应，不能靠数组顺序——并发下顺序不保证，按顺序配对一定会错位。有依赖的调用也不能并行（后一个的入参要用前一个的输出），判断标准是先看依赖图，无依赖才并行。

### Q7：这个 Agent 怎么测的？为什么不用 mock 框架？

- **考点**：可测性是不是设计出来的。

- **答题结构**：两层测法 → 依赖注入的理由 → 25 个用例覆盖什么 → 诚实说明没覆盖什么。

- **参考话术**："分两层。工具层（注册表、校验、权限、流水线）是纯函数和纯对象，直接断言，包括副作用断言——'权限拒绝不落库'那条就是确认拒绝之后 `NOTES.size === 0`，验证拦截发生在副作用之前。主循环依赖 LLM，不可控、花钱、慢，所以 LLM 调用做成构造注入：`new Agent(registry, { llm: fakeLlm })`，`fakeLlm` 是普通 async 函数，按脚本吐预设的 `tool_calls` 序列，于是'连续 3 次同签名调用 → 注入 LOOP_DETECTED'、'连续 4 次 retryable 错误 → 预算耗尽'这种场景都能确定性复现。不用 mock 框架的原因是注入之后测试目标直接拿到假依赖，不 patch 全局、不依赖框架魔法，依赖关系从构造签名就能看出来；`node:test` 内置的 test/assert/rejects 够用。代价是生产代码多一个参数——DI 和 patch 都是真实世界的常见做法，说得出取舍就行。被问到覆盖边界我会主动交底：现在没有专门用例的有三处——`main.js:21` 的 readline 交互（要真实终端，靠人工跑）、`llm.js:49` 的 `response.ok` 分支（要造 HTTP 错误响应）、`coerce()` 里 array/object/boolean 三个分支（用例只覆盖了 integer 和 string）。主路径和关键边界都测了，这三处如实说没覆盖，比含糊过去安全。还有一个踩过的坑：`check()` 从同步改成 async 之后旧用例全挂——`assert.equal(pm.check(...), true)` 拿 Promise 和 `true` 比，`assert.throws` 也抓不到 rejected Promise，修法是用例改 async 加 `await assert.rejects(...)`，所以 `test.js:95` 起那批权限用例现在都是 async 的。"

- **代码锚点**：注入点在 `agent.js:28`，测试里的用法 `test.js:197`、`test.js:206`；脚本化响应工具函数 `toolCallMsg` 在 `test.js:18`；用例清单从 `test.js:30` 到 `test.js:314`。

- **常见追问**：*负向测试有什么用？* → 把"刻意留的缺口"钉在测试里，防止后来者误以为是 bug 顺手改掉，也记录了演进：`test.js:300` 明确断言"没声明 kind 的写操作会被自动放行"，这条用例在缺口被补上（生产该 fail-closed）那天要改成断言拒绝。

## T3 架构设计（对标岗位"0→1 方案设计"）

### Q8：CLI 的 readline 三态确认，怎么演进成生产级审批系统？

- **考点**：看得出来扩展点在哪，而不是把审批当成新功能重写一遍。

- **答题结构**：先指出扩展点已经存在 → 五个演进方向 → 收口到"权限层零改动"。

- **参考话术**："这一章的权限层早就为演进留好了位置：`PermissionManager` 只依赖一个 `confirm(name, args) → true | "always" | false` 的回调，不关心背后是 readline、UI 弹窗还是 IM 审批单。生产化就是换一个 confirm 实现，有五个方向。通道上，发 IM 审批卡片（钉钉/企微/飞书），带工具名、参数摘要、风险等级，等回调。异步上是白送的——`check()` 本来就是 async，`await this.confirm(...)` 挂起等审批，Agent 主循环天然支持，这正是当初把 confirm 设计成 async 回调的回报。超时策略是默认拒绝，超时本身等价于'无确认通道'，和现在 `confirm = null` 直接拒绝是同一个安全默认。留痕是每次决策落库（谁、什么工具、什么参数、谁批的、什么时候），这是审计的输入。授权治理是把会话内的 `alwaysAllow` 集合升级成用户级/角色级策略（RBAC）。整个过程权限层一行不用改。"

- **代码锚点**：`main.js:29` 把 `cliConfirm` 注入 `buildRegistry`，`main.js:21` 是那一层的全部实现；权限层调用点在 `permissions.js:64`（`await this.confirm(name, args)`），流水线里的挂起点在 `registry_full.js:61`。测试里注入假 confirm 见 `test.js:101`、`test.js:109`、`test.js:167`。

- **常见追问**：*审批挂了很久，Agent 在等什么？* → 整条链是 async 的，主循环在这一步 `await`，没有轮询也没有占线程；要防的是"等太久"和"消息丢了"两件事，所以配超时默认拒绝 + 待审批状态可查询（生产里这类请求要落库，进程重启后还能恢复到待审状态，这块是第 10 章会话持久化的活）。

### Q9：把这个工具系统演进成平台级工具基础设施，0→1 路线怎么排？

- **考点**：排序能力——先做什么，以及每步的退出标准。

- **答题结构**：四步路线 → 每步的退出标准 → 一条反面原则。

- **参考话术**："四步，顺序不能乱。第一步工具治理：命名规范（动词_对象，防模型混淆）、description 写作规范加评审（描述质量直接等于调用质量）、kind 声明进 code review 清单、注册表按场景动态加载子集——工具超过 20 个不分组注入，模型的选择准确率会明显掉。退出标准是：新增工具不改核心代码、每个工具的 kind 和描述都能被 review。第二步可观测：每次调用记全链路（这轮的工具列表、入参、出参、耗时、错误码），出看板看调用量、失败率、延迟 P95、错误码分布，能回答'是 prompt 问题、工具问题还是依赖问题'。第三步可靠性：工具级独立 deadline、retryable 错误的退避重试、依赖故障时熔断并回传明确错误让模型换方案、429/5xx 处理和 fallback 模型。第四步生态：MCP 接外部工具，把自研工具也暴露成 MCP server 供别的 Agent 复用；审计、限流、脱敏作为横切能力挂在执行管道上——这就是插件架构。反面原则一句话：先让现有 5 个工具跑稳，再谈加载第 6 个；先堆工具数量后补治理是 Agent 项目最常见的烂尾原因。"

- **代码锚点**：第一步的落点是 `registry.js:31` 的 `register()`（工具定义对象本身就是治理单元）和 `registry_full.js:33`（kind 在注册期声明）；第二步的输入是 `errors.js:10` 的错误码表；第三步要补的能力对应 `llm.js:49`（现在只对 `!response.ok` 抛一个笼统 `Error`）和 `errors.js:61` 的 `retryable` 参数（接口已就绪，没有重试执行者）；第四步对应 `registry.js:37` 的 `getSchemas()`——它能生成协议格式，也就是能导出成 MCP 工具清单。

- **常见追问**：*工具治理里最容易被忽略的是什么？* → description 的评审。它是唯一直接决定模型选对工具的东西，却是最容易随手写"查询天气"三个字的地方；面试里能说出"我们给 description 定了模板：做什么 + 什么时候用 + 什么时候不要用"，比讲架构图更有说服力。

### Q10：（压力题）你的注册表就是个大 Map，权限就是个 if-else，这有什么架构含量？

- **考点**：被质疑时能不能不辩解"复杂度"，把价值锚在决策上。

- **答题结构**：换框架（架构含量 ≠ 代码行数）→ 逐个决策对应的事故模式 → 收口到"复杂性消化在边界上"。

- **参考话术**："我不辩解复杂度，把价值摆成决策。第一，协议和实现同体——消除双份维护，代价是 JS 要手写 schema，收益是加工具零改动路由。第二，宽容转换而不是严格校验——本地修正 vs 模型重试的成本模型，边界是不能改变语义。第三，权限决策排在参数校验之前——最小权限，被拒绝的调用不消耗校验，审计边界清晰。第四，`alwaysAllow` 做成实例字段——授权作用域就是安全边界，全局单例等于权限提升漏洞。第五，防护的处置是'告诉模型为什么停'——把 LLM 当协作者而不是被管控对象，它会自己收尾。第六，confirm 是注入的 async 回调——审批通道的扩展点，readline 换成 IM 审批流权限层零改动。这六条每条都对应一个真实的事故模式：权限提升、死循环烧钱、内部细节泄漏、无人值守误操作、幻觉工具名、坏参数崩进程。代码看起来简单，是因为复杂性被消化在边界上了——防御性 API 的成熟形态就是这样，拆开来全是决策。"

- **代码锚点**：六个决策对应的位置——`registry.js:31`（register 收的就是定义对象）、`validation.js:64`（`3.7 → 3` 的宽容截断）、`registry_full.js:59` 与 `registry_full.js:67` 的先后顺序、`permissions.js:36`（实例级 `alwaysAllow`）、`agent.js:80`（判定后回填而非静默终止）、`main.js:29`（注入的 confirm）。每个决策都有用例背书：`test.js:66`、`test.js:118`、`test.js:167`、`test.js:230`、`test.js:314`。

- **常见追问**：*那这套东西上生产，第一件要改的是什么？* → 先把 `permissions.js:51` 的默认等级从 `read` 改成最严（fail-closed），再把 confirm 通道换成带留痕的实现。这两件事都不需要动结构，改的是默认值——这套设计的成熟度不在于加了什么，而在于默认值选哪一侧。默认放行的代价是无人值守时的一次静默越权。
