# lesson05 · 跨会话记忆 —— 面试题讲解（Node 版）

> 10 题，三层深度。每题按固定结构展开：**考点 → 答题结构 → 参考话术 → 代码锚点 → 常见追问**。
> 本章可引用的"证据"：5 个新增记忆文件共 569 行、`agent.js` 对第 4 章主循环只改首尾两处、20 个离线用例全绿（`ℹ tests 20 / ℹ pass 20`）、4 条演示记忆的召回实测（同一问题一次召回 4 条、一次 0 条）、以及自己修掉的两个 bug（frontmatter 解析静默丢条目、换类型留旧目录副本）。

使用建议：T1 三题必须脱口而出；T2 要能讲清"我踩过什么、怎么修的"；T3 直接对标"0→1 方案设计"。

## T1 基础原理（必过线）

### Q1：Agent 的"记忆"和上下文压缩是什么关系？为什么不直接把历史都塞进 context？

- **考点**：能不能一句话切开"工作记忆"与"长期记忆"，并说清各自的代价。
- **答题结构**：分工（塞 vs 取）→ 全量历史回放的三个代价 → 记忆存的是提炼结果 → 结论（两者互补，生产都要）。
- **参考话术**："压缩是塞，记忆是取。第 3 章的压缩把旧历史压完继续放在窗口里，管的是本次会话的预算；记忆把事实写到窗口外，下次按需检索回来，管的是跨会话。全量历史回放有三个代价：token 费用随轮数线性涨、注意力被无关历史稀释、进程一停全没。记忆存的是 LLM 提炼过的高价值事实——比如'用户要求用 pnpm'，而不是当初讨论包管理器的 20 轮对话。所以记忆的 token 成本和历史长度解耦。这两个能力互补，生产系统里上下文管当下、记忆管长期。"
- **代码锚点**：`agent.js:75-79` 是记忆注入（`recall` + `setSystem` 拼进 system 尾部）；`context_manager_v2.js:90` 的 `needsCompaction()` 和 `98` 的 `compact()` 是压缩。两者在 `run()` 的同一个循环里各管一段，谁都不替代谁。
- **常见追问**：*那记忆能不能完全替代长上下文？* → 不能。记忆是有损的，提取会丢掉过程信息，而排障、追问细节、纠正误解都依赖原文；压缩也不能替代记忆，它解决不了跨进程的问题。

### Q2：你这套记忆系统的完整流水线是什么？

- **考点**：有没有清晰的模块边界，能不能指出每一段的落点文件。
- **答题结构**：四段流水线 → 每段一句话加文件 → 对 Agent 只暴露两个方法 → 分层带来的可替换性。
- **参考话术**："四段：提取（`extract.js`，让 LLM 从对话里提炼结构化事实）、存储（`memory_store.js`，写成 markdown 文件加 MEMORY.md 索引）、召回（`recall.js`，关键词打分取 Top-5，可选 LLM 精排）、注入（`agent.js`，拼进 system prompt 尾部）。调度中枢是 `memory_manager.js`，它把四段包成两个方法给 Agent 用：`recall(query)` 和 `scheduleExtract(llm, messages)`。所以 `Agent` 的四段实现一个都不认识，只知道这两个方法——这是我能把关键词召回换成向量检索而不动主循环的原因。"
- **代码锚点**：`memory_manager.js:40` 的 `recall()` 门面（`listMemories` → `recallByKeywords` → 可选 `rerankByLLM`）；`memory_manager.js:78` 的 `scheduleExtract`；`agent.js:75` 与 `agent.js:156` 是 Agent 唯一的两个调用点。
- **常见追问**：*提取和召回哪个先做？* → 同一轮里召回在前（推理前注入）、提取在后（`run()` 结束），但两者面对的是不同时间窗的数据：召回查的是历史存量，提取写的是本轮增量。

### Q3：记忆为什么存成 markdown 文件，不用数据库或向量库？

- **考点**：技术选型能不能给出真实理由，而不是"简单"两个字。
- **答题结构**：三个理由（可读可改 / 可版本化 / 零依赖）→ 接口不变所以可替换 → 承认向量库终局但位置不同。
- **参考话术**："三个理由。记忆是'关于用户的断言'，用户必须能打开看一眼、手改、手删，黑盒数据库做不到；markdown 放仓库里可以 diff、可以回滚，和代码一起管理；再就是零依赖，教学和演示环境不用起服务。更关键的是存储是可替换的实现细节——上层只依赖 `saveMemory/listMemories/getMemory/deleteMemory` 这几个签名，换成 SQLite 或者向量库只改 `memory_store.js` 一个文件。向量库是终局，但它解决的是召回问题，不是存储问题；原始文档照样得有个地方放着。"
- **代码锚点**：`memory_store.js:29` 的 `MEMORY_ROOT`、`35` 的四种类型、`59`/`73` 的序列化与解析；`memory_entries.js:37` 的 `saveMemory` 是上层唯一写入口。
- **常见追问**：*文件存储并发写怎么办？* → 单进程假设，进程内游标串行化；多进程会互相覆盖，这是本章明确记录的缺口，生产要换数据库加事务。

## T2 工程深度（区分度所在）

### Q4：让 LLM 提取记忆，质量怎么保证？

- **考点**：prompt 工程的实际功力，以及"不信任模型输出"的工程习惯。
- **答题结构**：prompt 里三件必做的事 → 语义去重 → 输出解析三层容错 → 失败降级原则。
- **参考话术**："提取的质量上限由 prompt 决定，三件事缺一不可：白名单（该记什么——偏好/纠正/项目约定/外部引用，对应四种类型）、黑名单（不该记什么——寒暄、临时问题、过程细节）、空输出兜底（'没有值得保存的返回 []'，少了这句模型会硬编一条交差）。另外把已有记忆的清单一起喂进去提示'避免重复提取'，这是语义级去重。输出解析必须容错：模型十次里有三次把 JSON 包进 ```json 代码块，还爱加前后废话，所以解析链是剥代码块 → `JSON.parse` → 正则抠 `[...]` → 全失败返回空数组。原则是提取失败等于本轮没提取到记忆，绝不能让解析异常打穿主对话。"
- **代码锚点**：`extract.js:15` 的 `EXTRACT_SYSTEM_PROMPT`（白名单、黑名单、`[]` 兜底）；`extract.js:33` 的 `parseExtractOutput` 三层解析；`extract.js:75` 传 `tools=null` 表明这是纯文本任务；回归用例 `test.js:124`/`132`/`139` 钉住三层容错。
- **常见追问**：*提取 prompt 有没有量化的调优手段？* → 建一批固定对话加期望提取结果的离线用例，改 prompt 前后跑回归；三个指标拆开看：该记的有没有漏、不该记的有没有进、description 写得够不够准（它直接决定召回）。

### Q5：提取必须异步，那并发正确性怎么保证？

- **考点**：这是本章最值钱的工程题——后台任务的正确性设计。
- **答题结构**：为什么必须异步 → 四道闸逐个说 → finally 里的积压合并最容易漏 → 失败隔离。
- **参考话术**："提取是一次 LLM 调用，秒级、花钱，同步做就是用户每轮多等一次模型响应，所以它是 fire-and-forget。但后台跑要挡四件事。快照：传进来的是主循环正在用的消息数组，先 `map` 拷贝一份，不拷贝就是读一个持续变化的数组。游标：记录已提取到第几条，`slice(cursor)` 保证同一批消息不会被分析两次，跑完推到快照长度。频率阈值：新增消息不足 2 条直接返回，省掉一次 LLM 调用，用户连发短消息时不至于每轮都烧钱。串行队列：正在提取时新来的快照只覆盖 `pendingMessages`，不排队；提取结束的 `finally` 里检查积压，用最新快照补跑一轮——合并成一次，因为第二轮和第一轮提取的内容大概率重叠。再加失败隔离：整个过程包 `try/catch`，出错只打日志，提取挂了主对话不能挂。"
- **代码锚点**：`memory_manager.js:78` 的 `scheduleExtract`（快照在 `80`、频率在 `83`、队列在 `87`、后台执行在 `94`）；`memory_manager.js:105` 推游标；`memory_manager.js:109-119` 是 `finally` 里的积压合并。用例 `test.js:191` 钉"游标不重复提取"，`test.js:216` 钉"1 条新消息时 `llmCalls === 0`"。
- **常见追问**：*为什么不做成任务队列、串行跑 N 个？* → 相邻两批的消息高度重叠，跑两轮等于花两份钱拿一份收益；合并成"最新快照跑一轮"在延迟和成本上都更优。

### Q6：召回怎么做？关键词版本不够用，为什么不直接上向量检索？

- **考点**：两阶段检索的通用结构 + 对自己实现局限的诚实认知。
- **答题结构**：两阶段（粗排 → 精排）→ 分词与加权的具体设计 → 宁缺毋滥 → 局限的实测证据 → 分层让替换成本极低。
- **参考话术**："两阶段：关键词粗排零 LLM 成本、毫秒级，把候选缩到 Top-5；候选多于一条时可选交给 LLM 精排。粗排的分词是中英分开的——英文按 ≥2 字符取词，中文没有天然边界用 2-gram 近似。打分按字段加权：description 最高，因为那一行就是提取时专门为'判断相关性'生成的，name 次之，body 最低（里面可能有偶然提到的词）。score 为 0 直接过滤，再取 Top-5，因为注入一条不相关记忆比不注入更糟。局限我实测过：同一个问题问两条都在说'用户用 Vim'的记忆，恰好含'编辑器'三字的召回 1 条，写成'文件默认用 Vim 打开'的召回 0 条——一条共同 token 都没有。用户不会按记忆库的措辞提问，所以生产要换 embedding。换的成本很低，只重写 `recallByKeywords` 一个函数，存储、提取、注入三层不动。"
- **代码锚点**：`recall.js:17` 的 `tokenize`（英文 `[a-z0-9]{2,}`、中文 2-gram）；`recall.js:43-45` 是 +3/+2/+1 权重；`recall.js:63`/`65` 过滤与截断；`recall.js:57` 是唯一需要替换的召回实现；`recall.js:76` 是可选精排。
- **常见追问**：*为什么单字符 token 要过滤掉？* → 防"的""我""4"这类噪音词污染打分，代价是单个数字查不出来，这个反直觉的行为被 `test.js:157` 钉住了。

### Q7：召回结果注入到哪里？为什么不是注入成一条 user 消息？

- **考点**：消息角色的语义差别，以及"记忆与上下文生命周期不同"的认知。
- **答题结构**：注入位置 → 两个理由 → 注入文本的安全标注 → recall 的 query 用什么 → `/reset` 的语义。
- **参考话术**："拼进 system prompt 的尾部。两个理由：system 层不参与对话逻辑流，每轮由 `cm.setSystem` 重建，模型把它当背景知识；注入成 user 消息会污染对话序列，模型会以为这是用户刚说的话，还可能和用户当前的指令冲突。注入文本开头我加了一句'来自历史会话，仅相关时使用'，提醒模型记忆可能过期，别当绝对事实。召回用本轮用户输入做 query，不用整段历史——用户这轮问什么就召回什么，用整段历史会被无关词稀释。另外 `/reset` 只换上下文管理器、不碰记忆：'这次会话说了什么'和'跨会话的事实'生命周期不同，一次 reset 不该清掉长期记忆。"
- **代码锚点**：`agent.js:75-79`（`recall` → `formatRecall` → `setSystem`）；`memory_manager.js:61` 的 `formatRecall`、`64` 那句"仅相关时使用"；`main.js:84` 的 `/reset` 调 `agent.reset()`（`agent.js:51`）只换 cm。
- **常见追问**：*记忆和用户当前指令冲突了怎么办？* → 模型以当前 user 消息优先（位置和角色都更近），注入文本里那句"仅相关时使用"也是为这个准备的；更彻底的做法是给记忆加时间戳和失效标记，那是 T3 的治理话题。

## T3 架构设计（对标 AI 负责人）

### Q8：记忆库只会越存越多，你怎么防止它变成垃圾场？

- **考点**：有没有把"写入容易"和"系统长期健康"分开考虑。
- **答题结构**：先承认本章的边界 → 写入侧 / 读取侧 / 治理侧三层 → 一个观点收尾（写入门槛低但必须有淘汰）。
- **参考话术**："本章只做到一半，我先说清边界：没有 TTL、没有容量上限、没有衰减。生产的做法分三层。写入侧：按 name 精确去重、提取时喂已有清单做语义去重、同主题新记忆覆盖旧的，覆盖永远优于追加。读取侧：召回只取 Top-5 天然限制了注入量，宁缺毋滥控制噪音，精排再过滤一轮。治理侧：定期让 LLM 合并相似条目、按最近一次被召回的时间做衰减淘汰、给用户留 `/memories` 和 `/forget` 的人工入口——这两个本章有了。我的观点是记忆系统的写入门槛可以低，但淘汰机制必须有，不然半年后召回质量会肉眼可见地掉。"
- **代码锚点**：写入侧去重在 `memory_entries.js:37`（同 name 同内容跳过）和 `memory_entries.js:56`（换类型删旧副本，这是我修的一个 bug）；提取侧的语义去重在 `extract.js:68`；人工入口在 `main.js:70`（`/memories`）和 `main.js:74`（`/forget`）。
- **常见追问**：*衰减按什么维度做？* → 按"最后一次被召回的时间"比按创建时间合理，因为长期没人用的记忆才是噪音；也可以按命中次数与写入时间的组合打分。

### Q9：这套记忆系统你怎么证明它是对的？

- **考点**：工程素养——测试是否覆盖到最难测的并发与持久化。
- **答题结构**：用例分块 → 三个最有价值的断言 → 测试技巧（怎么区分两种 LLM 调用、怎么等异步）→ 主动交代没覆盖的部分。
- **参考话术**："20 个用例分五块，外加 1 条 Loop 配对回归用例：存储层（序列化往返、去重、删除）、提取（三层解析容错）、召回（分词、排序、精排）、调度（游标防重复、频率阈值）、集成（注入、自动提取、工具共存、跨会话）。三个断言最值钱：跨会话那条用两个独立的 `MemoryManager` 实例模拟两个进程，session1 写、session2 能召回，证明是真落盘不是进程内缓存；游标那条对同一批消息调度两次，断言记忆条数不变；频率阈值那条用 `llmCalls` 计数器断言只有 1 条新消息时 LLM 一次都没调。技巧有两个：mock 的 LLM 用第二个参数区分角色——正常推理一定带工具 schema 数组，提取调用一定传 `null`；异步提取的断言前用 `wait(80)` 等后台任务落库。没覆盖的部分我也说清楚：串行队列的积压补跑分支没有专门用例，现有的 mock 跑不出'提取期间又来一批消息'的时序。"
- **代码锚点**：`test.js:350`（跨会话持久化）、`test.js:191`（游标）、`test.js:216`（频率阈值计数器）；两种调用的区分写在 `test.js:266`（`if (tools === null)`）；`test.js:35` 的 `before` 与 `test.js:44` 的 `after` 用 `rename` 把演示记忆库挪开再放回，跑测试不会毁掉课程数据。
- **常见追问**：*测试里怎么模拟"提取很慢"？* → 在 mock 的提取调用里 `await` 一个可控的延迟，再并发触发第二次调度，断言只补跑一次；这是本章没做的部分。

### Q10：（压力题）记忆会不会帮倒忙？用户说过"我喜欢 X"，后来改成"以后用 Y"，Agent 还在用 X 怎么办？

- **考点**：能不能主动说出自己系统的失败模式，而不是只讲成功路径。
- **答题结构**：承认会发生并给证据 → 三层缓解 → 加分项（时间戳与溯源）→ 一句收尾。
- **参考话术**："会，这是记忆系统最真实的失败模式，而且课程自带的演示库就是这么一个现场：一个用户先说喜欢白色、又说不再喜欢白色、最后确认喜欢粉色，4 条记忆里三条在讲颜色，其中一条已经作废。我的实测是问'我喜欢什么颜色'，4 条全被召回注入，包括那条作废的白色偏好——谁新谁旧，目前靠模型自己从措辞里猜。三层缓解：提取侧专门有 feedback 类型收'纠正'（`extract.js:20`），新提取会带已有记忆清单；写入侧同 name 覆盖而不追加；用户还能 `/forget` 手动删。更成熟的做法是给条目加时间戳和来源轮次，召回时把时间戳一起注入，让模型知道'这条是一周前的、那条是刚才的'，用户质疑时还能溯源到具体对话。主动说出失效路径，比只讲写入路径更能说明我做过真实系统。"
- **代码锚点**：`memories/user/用户颜色偏好.md`（白色）、`memories/feedback/用户颜色偏好更新.md`（不再喜欢白色）、`memories/user/用户颜色偏好-粉色可爱风.md`（确认粉色）三条互相矛盾；四条同时被召回的实测见 `README.md` 的快速开始；`extract.js:20` 的 feedback 类型定义。
- **常见追问**：*那为什么不在写入时就删掉旧的？* → 判断"新记忆是否否定了旧记忆"本身需要一次 LLM 调用，而且误删比留着更糟；更稳妥的是保留历史、标注时间与状态，把判断权交给模型和用户。
