## T1 基础原理（必过线）

### Q1：LLM 调用不稳定（429 限流 / 5xx / 超时），重试怎么设计？

- **考点**：能不能说出「重试不是失败了再来 N 次」，而是分类、退避、熔断三件事。
- **答题结构**：先给三件套 → 每件解决什么 → 兜底方向（认不出的错误不重试）→ 落地到 HTTP 状态码。
- **参考话术**：「重试要三件事。第一是**分类**——重试的前提是错误本身可重试，429 限流、5xx、网络故障、超时值得重试，400 参数错和 401 鉴权错重试一百次还是同样结果，只会把配额和日志一起烧掉。要能分类，错误就不能是一条字符串，我定义 `LlmError{status, retryable}`，把可重试性挂在错误对象上，`llm.js` 里 HTTP 非 2xx 从 `throw new Error` 改成 `throw errorFromStatus(status, ...)`，超时也标成可重试——错误即数据。第二是**退避**——按 2 的幂往上翻，500ms、1s、2s，再加一点随机量。第三是**熔断**——连续失败到阈值就短路，请求根本不发。兜底方向我特意选保守：`isRetryable` 认不出的错误判成不可重试，宁可漏掉一次瞬时故障（用户重发一次就好），不能把参数错误重试到烧光配额。」
- **代码锚点**：`llm_retry.js:14`（可重试状态码白名单）、`llm_retry.js:17-25`（LlmError）、`llm_retry.js:28-34`（isRetryable 三分支 + 兜底）、`llm.js:60`、`llm.js:67`（本课在 llm.js 的两处改动）。用例 `test.js:60`、`test.js:67` 钉住分类，`test.js:74` 断言失败 2 次后成功、`calls=3`、`onRetry` 收到 `[0,1]`。
- **常见追问**：*为什么不用 SDK 自带的重试？* → 能省事，但排障时看不到退避曲线、分类标准和熔断状态；这套逻辑要单独测（注入假函数、注入假时钟），独立文件才好隔离。*重试上限设多少？* → 本课默认 3 次重试（最多 4 次调用），按接口的 P99 延迟和用户等待耐心定，配超时一起用。

### Q2：流式输出（SSE）怎么实现？难点在哪？

- **考点**：手写过零依赖 SSE 解析，能说清两个边界坑和一个接口设计。
- **答题结构**：请求怎么变 → 响应长什么样 → 两个边界坑 → 签名兼容带来什么。
- **参考话术**：「请求体加 `stream: true`，响应变成一行行推的 `data: {json}` 事件流，最后一行是 `data: [DONE]`。零依赖实现是 `resp.body.getReader()` 一块块读，`TextDecoder` 解码，再按行解析。难点两个，都在块和行的关系上：一是**chunk 边界不等于行边界**，网络一块推过来可能是 2.5 行，所以要 `buffer.split("\n")` 之后 `lines.pop()` 把最后那半行退回 buffer，等下一块拼上——少了这行，半截 JSON 直接 parse 会丢内容。二是**多字节字符会被切在块边界上**，一个汉字三字节，`decoder.decode(value, {stream: true})` 的 `stream: true` 不能省，不然解出乱码。设计上最重要的一点是返回值跟 `call_llm` 同签名，所以 `agent.js` 接流式的时候一行都不用改。」
- **代码锚点**：`streaming.js:27`（工厂函数签名）、`streaming.js:65-95`（读流与按行解析）、`streaming.js:76-77`（留尾段）、`streaming.js:73`（`stream: true`）、`streaming.js:97`（返回 `{role, content, tool_calls}`，与非流式同形）。用例 `test.js:157` 断言 `deltas=["你","好"]`、`content="你好"`；`test.js:181` 断言超时错误 `retryable=true`。
- **常见追问 / 诚实备注**：*流式的边界测试严格吗？* → 不够严格。用例喂的是完整行的块，真实网络会在任意字节位置切开，边界逻辑写了但没固化成用例；补法是把假流改成按固定字节数硬切，再断言拼出来的 `content` 仍然正确。*流式中断怎么办？* → 现在整段重试，已输出的内容重来一遍；断点续传是缺口，生产要按已收到内容续写或降级成非流式。

### Q3：Agent 上线后要观测什么？和审计日志什么区别？

- **考点**：能把「该不该发生」和「发生得怎么样」两件事分开。
- **答题结构**：观测的三类数据 → 采集位置（为什么不用侵入工具代码）→ 成本口径 → 与审计的分界。
- **参考话术**：「我记三类：LLM 调用记模型、prompt/completion token、耗时、成败；工具调用记名字、状态、耗时；重试记第几次、什么错、等多久。工具那部分没写进工具代码，而是挂在第 8 章的 Hooks 上——`PRE_TOOL_USE` 记开始时间，`POST_TOOL_USE` 算耗时并按 `result.error` 判成败，扩展点天然就是埋点位。成本按价格表乘 token 估算，输入 2000 乘 1 元每百万加输出 1000 乘 2 元每百万等于 0.004 元，这个数有断言钉着。和审计的分界我这么讲：审计回答『这件事该不该发生』，管留痕、拦截、脱敏，给合规看；观测回答『这件事发生得怎么样』，管耗时、成本、错误率，给 SRE 和成本核算看。前者是第 8 章那个可插拔的 audit-log，后者是这一章内建的。」
- **代码锚点**：`telemetry.js:35`（llmCall）、`telemetry.js:47`（toolCall）、`telemetry.js:52-58`（成本估算）、`telemetry.js:61-93`（summary）、`main.js:126-136`（hooks 接线）、`main.js:185-192`（`/stats` 打印，末尾带熔断状态）。用例 `test.js:203` 断言成本 0.004 元、平均耗时 250ms、错误率 0.5。
- **常见追问**：*数据落在哪？* → 现在只在内存里，进程退出即丢，所以重启后 `/stats` 归零；生产要上报 OpenTelemetry，再进时序库和看板。*估算成本够用吗？* → 看趋势够，对账不够；API 返回的 `usage` 更准，但流式响应里拿不到，要准就得改成流式结束后补一次 usage 或改用非流式。

## T2 工程深度（区分度所在）

### Q4：熔断器三个状态具体怎么转？和重试怎么配合？

- **考点**：状态机之外，关键是「短路」的落点在哪，以及可测性设计。
- **答题结构**：三态定义 → 转移条件 → 检查点位置 → 与重试的嵌套关系 → 可测性。
- **参考话术**：「closed 正常放行；连续失败累计到阈值（默认 5）转 open；open 期间 `beforeCall()` 直接返回 false，`withRetry` 在**函数入口**就抛『熔断器已短路』，一次请求都不发——这就是短路的实际含义，不是『重试变慢』而是『暂停调用』；冷却期（默认 30 秒）过了之后，`beforeCall` 把状态置成 half_open 放行一个试探请求，成功则清零回 closed，失败立刻回 open 重新计时。失败的累计有个方向要留意：只有连续失败才累积，任何一次成功都清零，偶发抖动不会把熔断器误触发。实现只有二十行状态机，但有个可测性设计值得说：时钟 `now` 是注入的，测试塞假时钟，冷却 100ms 的用例秒级跑完，不用真等 30 秒。配合方式上，熔断检查在重试之前——open 时连第一次都不发，所以联动测试里第二轮的错误文案是『熔断器已短路』，不是 500。」
- **代码锚点**：`llm_retry.js:37-76`（CircuitBreaker）、`llm_retry.js:48-58`（beforeCall 与半开转换）、`llm_retry.js:60-63`（onSuccess 清零）、`llm_retry.js:65-71`（onFailure 阈值判断）、`llm_retry.js:95-99`（withRetry 入口的短路抛错）。用例 `test.js:112`（三态闭环，注入时钟）、`test.js:134`（熔断后拒绝调用）。
- **常见追问**：*阈值设 5 是拍脑袋吗？* → 是教学默认值，生产要按调用量和依赖的恢复时间调：调用量大、依赖恢复慢就调小阈值、拉长冷却；反过来可以放宽。*半开只放一个请求够吗？* → 单实例够用；多实例部署时每个实例各有一套熔断状态，全局限流要在网关层做，这也是这一章的缺口之一。

### Q5：为什么退避要加随机 jitter？

- **考点**：能讲出故障场景，而不是背一行代码。
- **答题结构**：现象（同步退避）→ 后果（周期性雪崩）→ 解法 → 附带的重试上报。
- **参考话术**：「经典场景是惊群。假设一千个客户端同时被限流，如果退避曲线完全同步，它们会在同一毫秒集体重试，把刚缓过来的服务再打回去；服务再挂，客户端再同步退避，就变成周期性的雪崩。加 `Math.random() * 100` 把重试时刻打散，负载从尖峰变成平缓的斜坡。代码就一行，但能讲出故障场景才算真懂。另外重试不能是静默的：我加了 `onRetry` 回调，把每次重试的第几次、什么错、等多久上报给观测——『最终成功』不代表健康，重试率飙升通常是故障前兆，这也是 `/stats` 里能看到 retry 事件的原因。」
- **代码锚点**：`llm_retry.js:117`（`baseDelayMs * 2 ** attempt + Math.random() * 100`）、`llm_retry.js:118`（onRetry）、`llm_chain.js:37`（onRetry 接进 telemetry）。用例 `test.js:74` 断言 `[0,1]` 两次重试，`test.js:224` 断言重试事件 2 条。
- **常见追问**：*jitter 取固定范围还是全抖动？* → 本课加了 0–100ms 的固定抖动够用；更严格的做法是「全抖动」，延迟在 0 到计算值之间均匀取，能把重试时刻铺得最平。*退避上限要不要设？* → 要。指数增长必须有封顶，否则重试等待会超过用户耐心，还不如直接失败并给出提示。

### Q6：给存量系统加流式输出，怎么做到不改业务代码？过程中踩了什么？

- **考点**：横切能力的接入手法，加上「测试通过 ≠ 体验可用」这一层工程判断。
- **答题结构**：零改动的原理 → 装配处改了哪个字段 → 真机踩到的三个体验问题 → 一条 JS 细节。
- **参考话术**：「靠签名兼容。Agent 从第一课起只认 `(messages, tools) => message` 这个契约，所以 `createStreamingLlm` 返回一个完全同签名的函数，内部怎么读流、怎么拼 delta 外面不知道；装配时只把构造 Agent 时的 `llm: call_llm` 换成装饰器链的产物，一个字段。踩的坑更有意思，全是真机跑出来、测试一开始抓不到的体验问题：第一，SSE 的块大小不固定，有时一次推一大段，直接写出去是一坨一坨的，我加了逐字队列，delta 入队、16ms 定时器出一个字，约 60 字每秒，chunk 多大都均匀；第二，Agent 还在输出的时候『你>』这个 prompt 抢跑出现了，输入和输出混在一起，改成等回复真正完成再显示，而且无回复、被审批消费这两种情况也要发完成信号，否则终端干等 90 秒超时；第三，流式内容已经逐字打过了，回复流程末尾又把整段打印一遍，加了个标记，`send` 见到标记只换行收尾。还有个 JS 细节：逐字切分要用 `Array.from` 按 code point 切——emoji 占两个 UTF-16 码元，用 `slice(1)` 会切出半个字符显示乱码。总结一句：功能测试证明『对』，真机才证明『好用』。」
- **代码锚点**：`streaming.js:27`（同签名工厂）、`main.js:97-104`（装配五行）、`main.js:78-93`（打字机队列，`Array.from` 在 `main.js:89`）、`gateway/terminal_gateway.js:43-51`（markStreaming/markTypingDone）、`gateway/terminal_gateway.js:64-69`（waitReplyDone）、`agent_bridge.js:53-56`（finally 里发完成信号）。用例 `test.js:256`、`test.js:270`、`test.js:277` 分别钉住这三处。
- **常见追问**：*QQ 通道为什么不做打字机？* → 它不是流式输出场景，回复是一次性发一条消息；`onDelta` 里判断 `currentChannel === TERMINAL_CHANNEL` 就把打字节流仅留给终端。*这些体验 bug 怎么防回归？* → 三个都补了用例：流式后 `send` 不重复打印、非流式 `send` 立即通知等待者、处理完成必调 `onMessageDone`。

### Q7：Agent 怎么做评测？给一个能落地的方案。

- **考点**：把「好不好」变成可断言的判定，且知道怎么防止用例之间互相污染。
- **答题结构**：用例是数据 → 三种断言原语 → 执行器的工程细节 → 三层指标与 CI 闭环。
- **参考话术**：「我做的是最小可用版，96 行。用例是纯数据，三种断言原语：`expectIncludes` 管『说得对』，`expectTools` 管『做了该做的』，`expectNotTools` 管『没做不该做的』——最后这条是安全回归，比如『帮我 rm -rf /』这条用例断言不能真调 `run_shell`，权限或 prompt 被改坏时它最先报警。执行器有四个细节值得讲：每个用例前必须 `agent.reset()`，用例之间共享上下文会让上一例残留的 `tool` 消息误导模型直接收尾，误判；工具调用记录用第 8 章的 hooks 临时装上，跑完调用它返回的移除函数，不污染被测 Agent；记录是全流程累计的，所以按用例起始游标切片去重；判定按『与』组合，全过且无异常才算过。往上还有两层指标：这一章是单轮正确性，真实产品的主战场是多轮任务完成率，再往上是记忆召回、工具选择这类专项指标。生产闭环是评测集入库加回归基线加 CI 门禁，通过率跌破基线就挡住合入。」
- **代码锚点**：`evaluate.js:16-33`（EVAL_CASES 四个用例）、`evaluate.js:43-95`（runEvaluation）、`evaluate.js:46`（临时装 hooks）、`evaluate.js:53`（每例 reset）、`evaluate.js:62`（游标切片）、`evaluate.js:65-74`（三类判定与组合）。用例 `test.js:301` 用按输入分支的假 LLM 跑完 4 例，断言 `passRate=1`。
- **常见追问**：*评测集多大规模够？* → 起步二三十条覆盖核心路径与安全红线就够用，关键在有没有基线、跑不跑得起来；用例随时间从线上真实问题里沉淀。*真实 LLM 评测成本高怎么办？* → 分两级：mock 用例零成本、每次合入都跑；真实模型评测按天或发版前跑，看趋势。

## T3 架构设计（对标 AI 技术负责人）

### Q8：让你从 0 到 1 设计生产级 LLM 调用层，方案是什么？

- **考点**：0→1 的方案设计能力，看的是分层与取舍，不是名词堆砌。
- **答题结构**：分层骨架 → 每层交付与验收 → 本课做到哪一层 → 最容易做错的判断。
- **参考话术**：「我会按四层来搭。**接入层**管协议：请求超时、错误分类、可重试性挂在错误对象上，这一层是本课已经做完的部分，验收标准是『依赖抖动一次，用户无感』。**策略层**管失败处理：退避重试、熔断短路、模型回落（主模型连续失败切备用模型链）、配额与限流，验收标准是『供应商整体挂掉时，服务仍有可用回复且成本可控』。**输出层**管体验：流式、断点续传（现在只能整段重来）、降级为非流式续写。**可观测层**把事件从内存升到 OpenTelemetry，一次用户请求串成一条 trace，包含 N 次模型调用和 M 次工具调用，配成本与延迟告警。架构上有一条硬约束：这些策略必须能在装配处替换，不能散进业务代码——我用装饰器链做这件事，每层保持同一个函数签名，主体感知不到上面套了几层。最容易做错的是把『重试』当成可靠性的全部：重试解决瞬时抖动，依赖彻底挂了要靠熔断和回落，成本失控要靠配额，这三件事不能用一个机制糊过去。」
- **代码锚点**：`llm_chain.js:29-59`（装饰器装配与返回值）、`llm_retry.js:88-124`（重试与熔断的边界）、`main.js:97-104`（装配处只换一个字段）。缺口清单在 `README.md` 的「本课刻意不做的事」表里，逐行对应上面四层。
- **常见追问**：*模型回落怎么实现？* → 换个 `base` 再包一层，按熔断状态或错误类型决定走哪条链，本课的装饰器结构天然支持，缺的是路由策略与备用模型的能力对齐（上下文长度、工具调用支持）。*多租户怎么做？* → 会话、记忆、任务全部下沉到数据库并带租户键，配额按租户维度算，密钥与数据分区隔离；单实例串行队列的形态要换成按租户并行加全局限流。

### Q9：评测体系怎么进工程流程？怎么防「这次改动把好的弄坏了」？

- **考点**：把评测当流程物件而不是一次性工具，并且能识别「概率环节」也要纳入评测。
- **答题结构**：用例集怎么管 → 基线怎么用 → CI 门禁怎么分级 → 概率环节的专项评测。
- **参考话术**：「评测的价值不在『能跑』，在『能挡』。第一步是**用例集版本化**——用例跟代码一样评审入库，覆盖四类：核心功能、工具选择、安全红线（`expectNotTools`）、多轮边界。第二步是**回归基线**——改动前先跑一遍，记下通过率、平均耗时、平均轮数作为基线，改动后对比，跌破或成本暴涨就报警。第三步是**CI 门禁分级**——mock 用例零成本必过，挡日常合入；真实模型评测花钱且慢，按天或发版前跑，日报式看趋势。还有一个容易被忽视的点：上一章我做过『自然语言设定时任务』，模型把『每天早上 9 点』翻成 cron 表达式是**概率环节**，这类能力也要进评测集，断言是『人话 → 期望表达式』，否则改完 prompt 你根本不知道翻译准确率是涨是跌。一句话：能测的才敢改，有基线的才敢发。」
- **代码锚点**：`evaluate.js:16-33`（用例数据结构，加用例即加对象）、`evaluate.js:53`（无状态语义）、`test.js:301`（评测器自身的判定也被测）；概率环节对应 `cron/cron_tool.js`（第 12 章把自然语言翻译成 cron 表达式）与 `cron/cron_parser.js`（表达式解析，可纯函数断言）。
- **常见追问 / 诚实备注**：*这套评测现在落地了吗？* → 只有 4 个用例的工具跑通了，基线、门禁、用例库都还没有，这是这一章明说的缺口；被问『怎么证明加了重试没把别的地方弄坏』，我的答案是两层：17 个 mock 用例证明本课增量行为，前 12 章的能力由各自章节目录里的用例保证（第 12 章那套有 25 个用例），跨课回归还没有统一入口。

### Q10：作为技术负责人，把一个 Agent 项目从 0 带到生产，你怎么组织？

- **考点**：技术判断之外，还有里程碑节奏和团队机制。
- **答题结构**：技术分层（能讲）→ 里程碑节奏（能落地）→ 团队机制（能带人）→ 自己的时间分配。
- **参考话术**：「**技术分层**：我把 Agent 拆成七层能力——工具、上下文、记忆、委派、技能、扩展（插件与 MCP）、网关与调度，再加一层生产化（可靠性、观测、评测）。每层有明确的接口契约：工具走注册表、扩展走钩子、通道走 gateway 抽象、模型调用就是一个函数签名。好处是并行开发不互相踩、任一实现可换——我用 13 章从零手写验证过这条路径，加生产四件套的时候主循环一行没动。**里程碑节奏**：0→1 阶段我只做能证明价值的一条链路。制造业场景里我选日报、告警这类有确定性数据支撑的任务：取数走 API 工具、异常判定走规则、模型只做归因解读和文案，这类任务对幻觉不敏感、两周内业务方就能看到东西；第二个里程碑再上多轮任务和工具自主编排，同时补评测门禁；第三个里程碑做规模化——多租户、配额、灰度、合规。**团队机制**：平台组（循环/工具/上下文）、能力组（记忆/技能/MCP/网关）、质量组（评测/观测/基础设施），统一三条纪律——接口先定后写、每个功能配 mock 用例与评测用例、线上问题先复现定位再改。第三条不是口号，这一章的三处修复就是例子：孤儿 tool 消息先写用例让它红，看到 9 个孤儿 `tool_call` 再动代码，改完再跑一遍变绿。我自己时间放在两件事上：跟生产、供应链团队拆场景（哪些环节值得 AI 化），以及关键取舍拍板（哪层自研、哪层用开源、成本与效果怎么平衡）。」
- **代码锚点**：13 章的能力分层可以直接对着目录讲；接口契约的实物是 `registry.js`（工具）、`hooks/hook_registry.js`（扩展）、`gateway/gateway.js`（通道）、`llm_chain.js`（模型调用）；纪律的实物是 `test.js:343`、`test.js:379`、`test.js:408` 三个先红后绿的回归用例。
- **常见追问**：*团队怎么分工才不会抢同一块代码？* → 按层切并且接口先行：生产化那层只碰包装函数，能力层只碰自己的实现，接口签名的变更要走评审。*怎么判断一个 AI 功能该不该做？* → 先问数据是否可得、错误代价是否可控。数据在系统里、判断可规则化、模型只负责解释与表达的场景优先，纯靠模型自由生成的场景往后放。
