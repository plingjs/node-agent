## T1 基础原理（必过线）

### Q1：cron 表达式什么结构？让你写一个解析器，你会怎么做？

- **考点**：能不能把"时间表达式"归约成一个可判定的数据结构，而不是拿正则去撞。
- **答题结构**：五字段与取值范围 → 四种字段写法 → 解析产物的形态 → 与下游的接口。
- **参考话术**："五字段，从左到右是分、时、日、月、周，各自取值域不同，所以字段定义单独声明：`minute` 0-59、`hour` 0-23、`day` 1-31、`month` 1-12、`weekday` 0-6（0 是周日）。每个字段支持四种写法：`*` 取全部、`a,b` 列举、`a-b` 范围、`*/N` 步进。解析的产物不是能匹配时间的正则，而是**每字段一组排序去重的数字**：`0 9 * * *` 变成 `{minute:[0], hour:[9], day:[1..31], month:[1..12], weekday:[0..6]}`。选集合而不是正则，理由全在下游——调度器要问'比当前分钟大的下一个匹配值是多少'，集合上是一次 `find`，正则上只能一分钟一分钟试。"
- **代码锚点**：字段定义 `cron_parser.js:22-28`；单字段展开 `expandField` 在 `cron_parser.js:31-55`（`Set` 收集天然去重，最后排序返回）；入口校验 `cron_parser.js:63-67`；测试 `test.js:53`、`test.js:62`、`test.js:68`。
- **常见追问**：*字段内部写错了怎么办，比如 `mon` 这种月份名？* → 本课是宽容解析：识别不了的段静默忽略，只有字段数不对（比如只给 4 段）才抛错。取舍理由是错的表达式应该由下游兜住——`nextRun` 算不出就返回 `null`，工具层再把它变成给模型看的错误。抛碎的解析器会把"用户打错一个字"升级成"整轮对话失败"。

### Q2：到点触发有三条路——轮询、`setInterval`、算出下次时间睡过去，怎么选？

- **考点**：对"漂移"这个概念有没有实感，能不能说清三种实现各自错在哪。
- **答题结构**：三条路各自的失效方式 → `nextRun` 为什么无漂移 → 对应的代码位置。
- **参考话术**："轮询每秒扫一遍，绝大多数 tick 什么都没做，还受扫描间隔限制精度。`setInterval(fn, 86400000)` 看着更省事，但那个 86400000 是从上一次回调**结束**的时刻重新起算的，回调本身跑的几秒、事件循环繁忙造成的延迟都会累加进周期，跑上几周就开始偏移——这是累积漂移。我用的是第三条：`nextRun` 算出下一个匹配时刻，`setTimeout` 睡过去，醒来执行完立刻重新算。每次醒来都对着墙上时钟对表，回调跑了十分钟也不影响下一次落点。"
- **代码锚点**：`nextRun` 在 `cron_scheduler.js:20-67`（对齐到分钟 `:22-23`，从下一分钟起 `:25`，扫描上限 `:28`，进位三条分支 `:42-64`）；触发循环 `_armCron` 在 `cron_scheduler.js:179-197`（触发后立即重新武装在 `:191-194`）。
- **常见追问**：*系统时间被改、或者夏令时怎么办？* → 本课没处理。实现依赖 `Date.now()` 的墙上时钟，时钟回拨会让下一次触发点算偏。生产要么统一用 UTC 调度、按用户时区换算展示，要么引入单调时钟做间隔保护，这是我知道的边界。

### Q3：Agent 的定时任务，为什么用进程内调度，不用系统 crontab 或 K8s CronJob？

- **考点**：选型理由必须挂到"任务要干什么"，而不是"哪个更简单"。
- **答题结构**：两种实现的本质差异 → 定时任务到点要用的东西 → 代价如实说。
- **参考话术**："系统 cron 到点拉起的是**一条新命令**，那个进程只有命令行参数，够不到常驻进程里的运行时。而我的定时任务到点要做的事恰好全在运行时里：恢复这个用户的会话上下文（第 10 章）、召回他的偏好（第 5 章）、调工具（第 2 章）、写操作走审批（第 11 章）。crontab 拉起 `node xxx.js` 等于把 Agent 降级成裸脚本。代价我也清楚：生命周期绑在进程上，进程挂了任务就没了，重启还会丢任务——生产要配任务落盘、进程守护、多实例去重这三件套。Qwen Code 这类产品的定时能力同样是进程内调度。"
- **代码锚点**：任务回调 `cron_tool.js:50-61`（`scheduler.schedule` 里直接调 `bridge.handleSystemMessage`）；系统消息入口 `agent_bridge.js:76-80`；`main.js:109-124` 是装配处。
- **常见追问**：*那为什么不用 K8s CronJob 拉起一个专门的服务？* → 可以做，但那是"把一个长任务拆成进程外调用"，还是绕不开运行时问题，除非调度服务自己持有 Agent 状态，那又回到了常驻进程。

## T2 工程深度（区分度所在）

### Q4：定时任务里踩过最阴的坑是哪个？

- **考点**：有没有被静默错误咬过，以及能不能把根因讲成通用规律。
- **答题结构**：现象 → 根因 → 修法 → 回归测试 → 为什么这类坑危险。
- **参考话术**："Node 的 `setTimeout` 把 delay 当 32 位有符号整数，上限 2^31-1 毫秒，也就是 **24.86 天**。超过这个值的处理方式很阴：不报错、不截断，按 Node 文档的行为到点会立即执行，顺带打一条溢出警告。我们注册年度任务（`0 0 1 1 *`，实跑距下次触发 110 天）时，'每年 1 月 1 日'的总结会在注册那一刻就发出去。修法是分段 sleep：距离超过上限就先睡满一段，醒来重新武装，目标时刻不变、剩余距离递减，直到小于上限才对准触发点。回归测试很轻巧——注册年度任务等 50 毫秒，断言 `fired === 0`，溢出 bug 一跑就现形。这个坑的价值在于它**静默**：不 crash、不报错，业务语义直接错。"
- **代码锚点**：上限常量 `cron_scheduler.js:89`；分段 sleep 判断 `cron_scheduler.js:187-190`；回归用例 `test.js:149`。
- **常见追问 / 诚实备注**：*你自己复现过'溢出即触发'吗？* → 没有。那条裸复现命令（单写一个 `setTimeout` 试大数）在本机跑的时候被权限层拦下了，所以我把这个行为归到 Node 官方文档，写进文档时也标了"未执行"。修复之后的回归测试是实跑的，这条我敢认。

### Q5：定时任务的消息，怎么进一个已经有"审批回复消费"逻辑的 IM 桥接层？

- **考点**：一条通道两种语义的冲突，能不能识别出来并做隔离。
- **答题结构**：原入口的副作用 → 具体踩踏场景 → 新入口的三处差异 → 回归怎么测。
- **参考话术**："绝不能复用用户消息入口。桥接层的 `handleMessage` 开头先过一道 `handleReply`，判断'这条是不是某个待确认任务的批复'，识别不出的输入按安全默认当拒绝消费。定时任务走同一个入口会出事：用户手上挂着一个 `run_shell` 待批准，任务文本 `【定时任务】巡检` 进来，`handleReply` 找不到'批准/拒绝/1/2/3'，把这条消息当'拒绝'消费掉——用户还没表态审批就被拒了，任务本身也被吞。一条通道上用户批复和系统指令两种语义互相踩。解法是 `handleSystemMessage` 平行入口，十行：跳过审批消费；共用同一个串行队列，保证和用户消息互斥；返回回复文本给调用方，因为定时任务没有'原消息'可以回复，推到哪个通道是工具层的事。回归用例复刻了整个踩踏场景：pending 挂着时系统消息进来，断言任务正常返回**且** `waitingCount` 仍是 1，之后用户回'批准'照常生效。"
- **代码锚点**：审批消费点 `agent_bridge.js:61-66`（消费发生在 `:64`）；新入口 `agent_bridge.js:76-80`；`_process` 的 `system` 形参 `agent_bridge.js:106`；回归用例 `test.js:413`；审批安全默认 `approval_flow.js:104-106`。
- **常见追问**：*为什么不给系统消息单独一条队列？* → 单 Agent 实例不能并发跑两次推理，队列必须共享，否则两条消息会同时改同一份上下文。隔离的是"语义判断"，不是"执行通道"。

### Q6：你从这份代码里揪出过什么 bug？怎么定位的？

- **考点**：code review 的深度，以及跨课复用代码时有没有做同族问题排查。
- **答题结构**：三个 bug 各一句根因 + 修法 + 一个通用教训。
- **参考话术**："三个。第一个是**孤儿 `tool_call`**：死循环检测判定后原来写的是 `break`，跳出这一轮的工具循环，可那条带 N 个 `tool_calls` 的 assistant 消息已经进上下文了，剩下几条永远拿不到回填。`assistant(tool_calls)` 和 `role:\"tool\"` 必须成对，少一条下一轮请求就被服务端 400 拒。我先写了回归用例再改代码：一轮构造 5 个同签名调用、第 3 个触发判定，旧代码测出来只回填了 3 条（`actual: 3, expected: 5`），改成 `continue` 后 5 条全有配对、只有前 2 条真的执行。这个 bug 第 2、3、4 章修过，从第 5 章开始的课复制代码时又把 `break` 带了回来——所以跨课复用代码必须查同族问题，子 Agent 里那份也一起改了。第二个是**测试全绿但进程不退出**：`node:test` 的 runner 默认等事件循环清空，测试里注册的 `0 9 * * *` 留下一个指向 14 小时后的定时器。定位靠最小复现二分——空测试文件正常退出、带定时器的挂，一下锁定。修法是调度器提供 `stopAll()`，凡创建过任务的测试末尾都调，再给 npm test 加 `--test-force-exit` 兜底。第三个是排查第二个时顺出来的：任务存在 `Map<name, job>` 里，同名注册会覆盖条目但不清旧定时器，旧任务成了 `stopAll` 遍历不到的孤儿句柄，到点照常触发，cron 任务还会自己重新武装、永远停不下来。修法是覆盖前先 `remove(name)`。通用教训一句话：**测试里的 server、socket、timer 都是资源句柄，断言通过不等于资源干净——失败会红，没清理只会沉默。**"
- **代码锚点**：修复处 `agent.js:143-156`（`continue` 在 `:155`）、`subagent.js:130-142`；回归用例 `test.js:468`；`stopAll` 在 `cron_scheduler.js:137-142`，调用点 `test.js:163`、`test.js:219`、`test.js:230`、`test.js:247`；同名覆盖修复 `cron_scheduler.js:112`、`cron_scheduler.js:121`，回归用例 `test.js:536`。
- **常见追问**：*孤儿 `tool_call` 为什么本地跑不出来？* → 它只在"一轮里多个 `tool_call` 且判定不在最后一个"时出现，日常单个工具调用的路径碰不到；这也是为什么必须用假 LLM 构造批次形状，而不是等线上 400 报错。

### Q7："用户说句话就注册一个会自主执行的定时任务"，安全上怎么兜？

- **考点**：把"持续改变系统行为"这类操作的风险看清楚，而不是只做参数校验。
- **答题结构**：权限级别 → 校验时机 → 失败隔离 → 推送隔离。
- **参考话术**："四层。① 注册权限定成 **write 级**：一次工具调用顶多改一个文件，而一个定时任务会在未来每一天自动执行并推送，影响面完全不同，所以要过审批——用户在自己所在通道里回复 1 批准 / 2 拒绝 / 3 始终允许，60 秒不回复按拒绝处理。② 校验前置于注册：`parseCron` 在 `schedule` 之前跑，非法表达式直接抛给模型自愈，测试同时断言'抛错'和'任务列表为空'，不留半成品任务。③ 执行失败隔离：`fire` 里回调外层有 try/catch，任务炸了只写一行日志，调度器继续跑其他任务。④ 推送隔离：目标通道走 `channel || bridge.currentChannel || defaultChannel` 的链，QQ 用户设的任务推回他自己的 QQ，不会把 A 的日报发给 B。"
- **代码锚点**：write 级注册 `main.js:113-120`；`list_cron_jobs` 的 read 级 `main.js:121`；校验与抛错 `cron_tool.js:44`；失败隔离 `cron_scheduler.js:157-161`；推送路由 `cron_tool.js:48`；不留半成品的断言 `test.js:222`。
- **常见追问**：*任务到点后 Agent 要调危险工具，还审批吗？* → 审批。`_process` 会把当前通道写进 `bridge.currentChannel`（`agent_bridge.js:107`），confirm 回调读它，确认请求发到这条任务所属的通道，等人回复或超时拒绝。危险操作不因为"是系统发起的"而绕过确认。

## T3 架构设计（对标 AI 技术负责人）

### Q8：让你把"自然语言设定时任务"做成生产品功能，完整方案是什么？

- **考点**：0→1 的推进顺序，以及在每一层能说清"怎么验收"。
- **答题结构**：链路可靠性 → 任务持久化 → 运行保障 → 效果闭环，四段各给交付与验收。
- **参考话术**："四层。**链路**：模型把人话翻成 cron 是概率环节，工具 description 里内嵌示例表达式提正确率（本课已做），还必须建评测集——一批'人话 → 期望表达式'的用例跑回归，上线后监控'注册后 5 分钟内被用户删掉或改掉'的比例当误译代理指标。**持久化**：任务记录（表达式、任务文本、通道、上次触发时间、下次触发时间）落盘，用第 10 章那套 `.tmp + rename` 原子写，启动时重载并重新武装。**运行保障**：进程守护拉起、错过补偿（学 anacron 的做法：错过且未过窗口才补跑一次）、多实例去重（分布式锁或者把调度独立成单点服务）。**闭环**：每次执行埋点成功率与耗时，接连失败自动降级并通知设置者。做得最差的是跳过第一层直接上自动学习——先把表达式校验、触发链路、审批这些做扎实，后面几层都是替换内部实现。"
- **代码锚点**：可被持久化的字段就在 `CronJob` 里（`cron_scheduler.js:70-86`）；原子写在第 10 章的 `session_manager.js`；失败隔离在 `cron_scheduler.js:157-161`；评测挂到第 13 章的三型用例上。
- **常见追问**：*任务很多（几千个）时调度器还扛得住吗？* → 现在是每个任务一个定时器，几千个定时器对 Node 来说内存上没问题，但触发时刻相近时会挤在事件循环里排队。真要上规模得改成时间轮或者"只为一个最近任务设定时器、触发后取下一个"，`_armCron` 是唯一要改的地方。

### Q9：Agent 主动推送（定时、告警）的通用架构怎么设计？推给谁、在哪个上下文里执行？

- **考点**：能否把"时间/事件"抽象成一类消息源，并说清收件人和上下文的归属。
- **答题结构**：把时间当第三类消息源 → 三个设计决策 → 迁移到其他事件源。
- **参考话术**："把时间和事件抽象成第三类消息源，让它和用户消息走同一条下游：调度器 → `handleSystemMessage(channelId, text)` → 串行队列 → 恢复该通道会话 → Agent 全能力执行 → 按通道推送。三个决策：**通道即收件人**，任务记录绑定设置者通道，QQ 用户推 QQ、群任务推群、终端推终端，第 11 章的 `channelId` 路由直接支撑；**上下文归属**，任务跑在目标通道的会话里，所以推送带着这个用户的记忆和历史，像'记得你约定的助手'而不是群发机器人；**写操作仍走审批**，定时任务里要 `run_shell`，确认请求就发回该通道等回复。实跑能看到这个效果：同一任务第二次触发时，假 LLM 收到的消息条数是 4 而不是 2——它读到了上一次的问答，这条证据在课程文档里。这套'事件源 → 桥 → 会话 → 通道推送'同样能接告警 webhook 和 MQ 消费。"
- **代码锚点**：整条链路 `cron_tool.js:50-61`（系统消息 + 推送）；入口 `agent_bridge.js:76-80`；会话恢复与保存 `agent_bridge.js:106-137`；通道路由 `cron_tool.js:48`、`main.js:117`。
- **常见追问**：*推送失败怎么处理？* → 本课只做了 `catch(() => {})` 级别的兜底，没有重试和死信。生产要把推送抽成带重试的投递层，失败落库，重要通知再叠一层备用通道（比如 QQ 失败转短信）。

### Q10：制造业场景里，产线日报加供应链缺料预警，用这套定时任务体系怎么承接？

- **考点**：把技术方案翻译成业务语言，同时守住"哪些不该交给模型"的边界。
- **答题结构**：两个场景各自的链路 → 四个生产要素 → 边界与度量。
- **参考话术**："产线日报是每天 22:00 拉 MES/SCADA 数据、汇总后推车间管理群；缺料预警是每 30 分钟比对 ERP 库存水位和在途订单，低于安全库存就提醒计划员。架构上四个要素：① **取数是主体，模型是尾巴**——确定性数据用工具或 API 按 read 级取（`list_cron_jobs` 这类），模型只做归因解读和文案，能确定的绝不交给模型；② **任务分级**——日报可以错过（次日一起补），预警不能错过，所以预警要更细的调度粒度、进程守护、双通道冗余推送；③ **静默与升级**——同一异常 30 分钟内不重复告警，无人响应 15 分钟升级到上级，这部分超出 cron 本身，是任务体系上的告警治理；④ **效果度量**——预警准确率、误报率、响应时长进看板，阈值持续调。这套对应 JD 里'生产、供应链全链路场景规模化应用'的落地路径：调度是骨架，工具是手脚，模型是大脑，治理是护栏。"
- **代码锚点**：任务定义与表达式在 `cron_tool.js:26-71`；`write` 级审批挡在 `main.js:113-120`；任务执行失败的日志在 `cron_scheduler.js:160`；任务级观测目前是 `list()` 的 `runs` 与 `lastRunAt`（`cron_scheduler.js:144-149`），只够看有没有跑。
- **常见追问**：*如果取数接口挂了，日报怎么办？* → 现在只会记一行执行失败日志，没有降级。生产要区分"取数失败"和"汇总失败"，前者重试、后者推一条带原因的说明给车间群，避免群里静默缺席。
