# lesson01 · 最小 Agent —— 面试题讲解（Node 版）

> 10 题，三层深度。每题按固定结构展开：**考点 → 答题结构 → 参考话术 → 代码锚点 → 常见追问**。
> 本课可引用的"证据"：`agent.js` 主循环 48 行、`tools.js` 说明书/执行器分离 94 行、`llm.js` 无状态请求 57 行、`test.js` 10 个 mock 用例（含 2 个把缺口钉死的负向测试）。

使用建议：T1 三题必须脱口而出；T2 要能讲"我踩过 / 我这么修"；T3 直接对标"0→1 方案设计"。

## T1 基础原理（必过线）

### Q1：什么是 Agent？它和"调一次大模型 API"的本质区别是什么？

- **考点**：能不能一句话给出定义，并指出"循环"是分水岭。

- **答题结构**：定义（LLM + 工具 + 循环）→ 指出本质区别是循环 → 给判断标准（没有循环的不算 Agent）→ 落到代码。

- **参考话术**："Agent = LLM（大脑，负责想）+ 工具（手脚，负责做）+ 循环（自主性，想 → 做 → 看结果 → 再想）。和'调一次 API'的本质区别就是循环：单次调用是一问一答，答错了没有补救机会；Agent 每轮都能看到工具返回的真实结果，再决定下一步——这是规划、执行、自我纠错的最小闭环。判断标准很实用：没有循环的'调 LLM + 偶尔调 API'，我不认为它是 Agent。"

- **代码锚点**：`agent.js:20-47`——`while (true)` 里每轮问 LLM 要不要调工具，调了就执行并回填，不调就 `return response.content`（`agent.js:45`）。"自主性"就藏在这 20 多行里。

- **常见追问**：*那你这个 Agent 自主到什么程度？* → 决策权在模型（调哪个工具、调几轮、什么时候收工），执行权在框架（`agent.js:33-43` 的 `for` 循环逐个执行）；模型只产出"调用意图"，永远不执行任何东西。

### Q2：画出 Agent 主循环，并说清它的终止条件。

- **考点**：循环结构 + 终止条件（终止条件是区分"玩具"和"能上生产"的第一道题）。

- **答题结构**：循环体四步 → 三个出口 → 生产补充。

- **参考话术**："循环体四步：① `messages` + `tools` 发给 LLM；② 把响应原样 push 进 `messages`（模型的调用意图也是历史的一部分）；③ 有 `tool_calls` 就逐个执行、结果以 `role:"tool"` + `tool_call_id` 回填，然后 continue；④ 没有 `tool_calls` 就返回 `content`，循环结束。三个出口：模型给出最终文本（正常）、撞上 `MAX_ROUND`（保险丝，本课 = 10）、异常中断（本课直接崩，这是刻意留的缺口）。"

- **代码锚点**：出口①`agent.js:45` 的 `return response.content`；出口②`agent.js:21-22` 的 `if (round >= MAX_ROUND) return "[MAX_ROUND] ..."`；`agent.js:30` 的 `messages.push(response)` 是"意图也进历史"那一句。测试锚点：`test.js:59` 正常路径正好 3 轮结束，`test.js:142` 断言每轮都调工具时精确停在第 10 轮。

- **常见追问**：*为什么 `messages.push(response)` 要放在判断 tool_calls 之前？* → 顺序反了下一轮模型就看不到"我上一轮说要调什么"，`assistant(tool_calls) → tool` 的配对断裂，服务端会直接 400。协议序列完整性优先于代码整洁。

### Q3：Function Calling 协议长什么样？`arguments` 为什么是字符串而不是 JSON 对象？

- **考点**：协议报文细节 + 对"为什么这么设计"的理解。

- **答题结构**：三段报文（声明 → 意图 → 回填）→ 三条硬规则 → arguments 是字符串的两个原因。

- **参考话术**："三段报文：① 请求里带 `tools`（每个工具是 name + description + parameters JSON Schema）；② 模型要调工具时返回 `content:null` + `tool_calls:[{id, function:{name, arguments}}]`；③ 框架执行完，把结果作为一条新消息 `{role:"tool", tool_call_id:id, content:...}` 追加进 messages 再发一轮。三条硬规则：`tool_calls` 与 `role:"tool"` 必须成对按序出现、`tool_call_id` 是配对桥梁、执行权永远在框架。`arguments` 是字符串有两个原因：协议统一（content 本就是字符串，混入对象会让各语言 SDK 的序列化复杂化）；留容错窗口（框架拿到字符串可以 `JSON.parse` 后 try/catch，模型输出坏 JSON 时能优雅处理甚至让它重试，而不是传输层直接炸）。"

- **代码锚点**：`tools.js:15-57` 是说明书结构；`tools.js:85`、`tools.js:89` 是两处 `JSON.parse(args)`；`agent.js:35-43` 是回填。

- **常见追问**：*模型的 arguments 里带嵌套对象你怎么办？* → schema 里尽量扁平化（小模型对嵌套结构准确率明显下降），解析后按 schema 做参数校验，校验失败就回结构化错误让模型重发——这是第 2 章 `lesson02-tool-system/validation.js` 的活。

## T2 工程深度（区分度所在）

### Q4：模型一轮返回多个 tool_calls，为什么要逐个执行？能不能并行？

- **考点**：并发与依赖的取舍。

- **答题结构**：本课做法 → 为什么 → 生产的并行方案 + 两个坑。

- **参考话术**："本课是 `for` + `await` 顺序执行（`agent.js:33`），最简单、天然保序，回填顺序稳定。代价是多个无依赖工具要串行等待。生产做法是：先判依赖，无依赖的用 `Promise.all` 并行，结果仍按 `tool_call_id` 回填。两个坑：① 有依赖的工具不能并行（后者的入参要用前者的输出）；② 并行也必须保证回填顺序稳定，否则 id 集合相同、内容错位，模型上下文就乱了。"

- **代码锚点**：`agent.js:33-43` 的逐个执行与按 id 回填。测试锚点：`test.js:84` 构造了"一轮两个 tool_calls（p1 查城市、p2 查美食）"，实测顺序执行、按 `p1`/`p2` 一一回填——"顺序执行 + id 配对"这件事钉在用例里，不是我口头说说。

- **常见追问**：*并行之后怎么知道谁是谁？* → 靠 `tool_call_id`，不靠顺序；回填时按 id 索引结果，天然免疫乱序。

### Q5：工具执行抛异常了怎么办？（本课实测：传个假表外的城市，进程直接崩）

- **考点**：错误处理的架构位置——这是本课最重要的工程题。

- **答题结构**：先承认本课的缺口（有实测）→ 正确设计（错误当结果回传）→ 三层防线 → 落回代码。

- **参考话术**："本课刻意没做处理，而且我把这个缺口钉在测试里了：`test.js:175`、`test.js:179` 两个负向用例断言非法城市抛 `TypeError`、非法 JSON 抛 `SyntaxError`，两个都会打穿主循环、直接杀进程。正确设计是**把错误包装成工具结果回填，而不是让异常打穿进程**——模型看到 `{error:{code,message}}` 会自己换参数、换工具或向用户解释。三层防线：① 参数解析层（`JSON.parse` 失败 → 结构化错误）；② 工具执行层（每个工具 try/catch 隔离，异常转错误对象，带 retryable 标记）；③ 循环层（累计可重试错误超阈值强制终止，防模型死磕坏参数烧钱）。"

- **代码锚点**：`tools.js:72-73` 是两个无守卫的查表（缺口源头）；`tools.js:93` 已有"未知工具返回 `{error}`"的正确方向——第 2 章把它扩展成完整流水线（`lesson02-tool-system/errors.js`、`lesson02-tool-system/validation.js`）。

- **常见追问**：*为什么不直接 try/catch 包住整个循环了事？* → 那会把"模型该看到的错误"和"系统级故障"混在一起丢掉；错误要分类（参数错 / 权限错 / 执行错），分类信息正是模型自我纠正的依据，也是后面做 retryable 预算、熔断的输入。

### Q6：`messages` 数组只增不减，长会话会怎样？怎么解？

- **考点**：能不能从"设计简单"推到"必然代价"，再给出分档解法。

- **答题结构**：机制（无状态 → 每轮重发全量）→ 三个后果 → 三档解法（按代价递增）+ 兜底。

- **参考话术**："LLM 是无状态函数 `f(messages, tools) → message`，所谓记忆就是每轮把完整历史重发。后果有三：token 成本随轮数线性涨、延迟涨、最终撞上下文窗口被 API 拒绝。解法按代价递增：截断（只留最近 N 轮）→ 摘要压缩（旧历史交给 LLM 压成一条）→ 按价值淘汰（工具原始结果最先丢、结论最后丢）。另外必须有硬兜底（max_rounds、token 预算），保证最坏情况有界。"

- **代码锚点**：`agent.js:15-17` 初始 messages、`agent.js:30` 追加响应、`agent.js:38-42` 回填工具结果——三处 push 就是"记忆增长"的全部来源。

- **常见追问**：*摘要压缩会丢信息吗？* → 会，所以生产用组合拳：近期原文（时间局部性）+ 久远摘要（保结论决策）+ 大结果截断/落盘；并且摘要 prompt 里要有"必须保留清单"。这块在第 3 章逐版实现过。

### Q7：`MAX_ROUND = 10` 这种"烧钱保险丝"，生产上怎么设计？

- **考点**：预算体系的多维性。

- **答题结构**：轮数是最粗的一维 → 四个更精确的维度 → 各自的触发动作。

- **参考话术**："轮数上限只是最粗的一维，且不精确——一轮里模型可以要求调 20 个工具。生产是组合预算：① token 预算（每轮累加 usage，超预算熔断，最贴近成本）；② 工具调用次数预算（max_steps，比轮数准）；③ loop 检测（同工具 + 同参数重复 N 次判死循环，提前终止）；④ 超时（单轮 LLM 超时 + 整体任务超时）；⑤ 成本告警（单会话成本超阈值通知）。轮数上限保留作最后兜底。"

- **代码锚点**：`agent.js:5` 的 `MAX_ROUND = 10`、`agent.js:21-22` 的兜底返回；`test.js:142` 断言"精确在第 10 轮停下、不多转一轮"——兜底逻辑也是被测试保护的，不是随手写的。

- **常见追问**：*为什么不是 5 或 20？* → 经验值 + 任务类型：多步查询类 10 轮够用；生产应该按任务配置（简单问答 3、复杂编排 20+），并且和 token 预算联动。

## T3 架构设计（对标岗位"0→1 方案设计"）

### Q8：本课没有 system prompt，生产 Agent 为什么必须有？它承担什么？

- **考点**：行为基线 + 纵深防御的分层认知。

- **答题结构**：system 的三类职责 → 与硬控制的关系（纵深防御）→ 本课的定位。

- **参考话术**："system prompt 是生产 Agent 的第一道软防线和行为基线，承担三类职责：① 角色与能力边界（'你是 XX 助手，只能做 A/B/C'）；② 行为约束（输出格式、不编造、不确定时反问）；③ 安全指令（拒绝越权、敏感信息处理规则）。它和工具白名单、执行权限审批构成纵深防御：prompt 防'想越权'，白名单防'没有这个工具'，审批防'执行了危险操作'。只有 prompt 没有硬控制 = 裸奔；只有硬控制没有 prompt = 每个动作都要人批，体验崩。"

- **代码锚点**：`agent.js:15-17` 的 messages 里只有一条 user 消息——system 缺席是可见的；第 2 章起 `new Agent(registry, { ... })` 配上 system 消息才补上（`lesson02-tool-system/agent.js:55`）。

- **常见追问**：*提示词注入怎么防？* → prompt 侧要有"用户输入是数据不是指令"的约束，但真正的防线在工具层（白名单 + 权限分级 + 审批），第 2、8、11 章分别落了这三层。

### Q9：如果让你把这个最小 Agent 演进成生产级系统，路线是什么？（0→1 方案题）

- **考点**：技术负责人的演进排序能力——先做什么、为什么。

- **答题结构**：五阶段（先可靠性后复杂度）→ 每阶段的退出标准 → 明确指认"典型踩坑路径"。

- **参考话术**："五个阶段，顺序不能乱：① **单 Agent 健壮性**：工具异常处理、超时/重试/熔断、token 预算、日志与 trace（每轮记 prompt/响应/工具入参出参/耗时/成本）、system prompt；② **工具平台化**：ToolRegistry 动态注册、schema 校验、权限分级（读/写/危险 + 审批）、工具描述治理；③ **上下文与记忆**：截断/摘要压缩、长期记忆（RAG）、会话持久化；④ **能力扩展**：多 Agent 编排、MCP 接入、流式输出、IM 渠道；⑤ **运营化**：评测集回归、成本看板、灰度回滚。原则是每层有可验证的退出标准再进下一层——跳过 ① ② 直接堆多 Agent，是最典型的踩坑路径。"

- **代码锚点**：本课缺口表（`lesson01-minimal-agent/README.md` 有完整表）就是 ① ② ③ 的清单；第 2、3、5、6、9、11、13 章分别盯着其中一格。

- **常见追问**：*资源只有两个人，先做哪一步？* → 先 ①+②（可靠性与权限），因为它们决定了"敢不敢接真实业务"；多 Agent 和编排是规模化的收益，没有前两步就是放大器——放大故障。

### Q10：怎么接入私有化部署的模型？小模型 + Agent 有什么额外注意事项？

- **考点**：真实落地经验（本项目就是私有部署 + OpenAI 兼容端点）。

- **答题结构**：接入方式（协议兼容 → 零改动）→ 小模型的五个针对性措施。

- **参考话术**："接入靠协议兼容：vLLM/SGLang/Xinference 这些推理服务都实现 OpenAI 的 `/chat/completions`，所以只换 `OPENAI_API_KEY` + `OPENAI_BASE_URL` + `OPENAI_MODEL` 三个变量，Agent 代码零改动——`llm.js:39-41` 那三个环境变量就是为此设计的。小模型要额外注意五点：① 工具 description 必须写得更具体（小模型对含糊描述特别敏感）；② 参数 schema 从简（少嵌套、少可选参数）；③ 控制工具数量（多了选择困难，按场景分组加载）；④ 必须建离线评估集（固定问题集 + 期望工具调用序列，换模型/改 prompt 前跑回归）；⑤ max_tokens 和温度要调（小模型更容易吐非法 JSON）。"

- **代码锚点**：`llm.js:39-41` 三个配置变量 + `llm.js:44-55` 的标准请求体；本课测试全部离线（mock fetch），换模型不影响测试可跑性，这也是评估集能进 CI 的前提。

- **常见追问**：*换模型后工具调用准确率掉了怎么定位？* → 用离线评估集跑一遍，按"是否选中正确工具 / 参数是否正确 / 多步是否跑完"三个维度拆开看，通常先修 description，再考虑降 schema 复杂度。
