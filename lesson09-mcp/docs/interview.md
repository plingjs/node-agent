## T1 基础原理（必过线）

### Q1：MCP 解决什么问题？

- **考点**：能不能说清它是"协议标准化"，而不是笼统的"让 Agent 能调外部工具"——后者没有 MCP 也做得到。
- **答题结构**：接入现状的 N×M 问题 → MCP 降成 N+M → 标准化的三件事（工具声明 / 调用协议 / 传输层）→ 一句话收口。
- **参考话术**："没有 MCP 之前，工具接入是 N×M：N 个 Agent 框架各自一套工具描述格式，M 个外部系统要按每个框架各写一遍适配。MCP 把它降成 N+M：外部系统实现一个 server，用 JSON Schema 声明自己的工具；任何支持 MCP 的客户端连接时动态发现即可调用，客户端零适配。它标准化的是三件事——工具声明（schema 由 server 给）、调用协议（JSON-RPC 2.0，方法名统一是 `tools/list`、`tools/call`）、传输层（本地 stdio，远程 HTTP/SSE）。所以 MCP 的价值不在'能调外部工具'，在于'一次实现、到处能用'。"
- **代码锚点**：工具清单写在 server 侧（`mcp/mcp_server.js:21-48` 的 `TOOLS` 常量），客户端一个字段都没翻译，`params` 直接把 `t.parameters` 抄过去（`mcp/mcp_tools.js:26`）——这就是"客户端零适配"的代码形态。
- **常见追问**：*MCP 和直接写个 HTTP 工具函数有什么区别？* → 差别在谁定义接缝。自己写 HTTP 包装，接口形状由我定，换一个框架要重写；MCP 把接缝定在协议上，server 不知道客户端是谁，客户端不知道 server 内部是什么系统，两边可以各自替换。

### Q2：MCP 的通信流程？

- **考点**：三步协议能不能按顺序说清，以及每一步的数据形状。
- **答题结构**：三步（握手 → 发现 → 调用）→ 传输层 → 本课实现方式 → 报文证据。
- **参考话术**："三步。第一步 `initialize` 握手，交换协议版本和能力声明，server 顺便报身份；第二步 `tools/list` 动态发现，server 返回全部工具的 schema；第三步 `tools/call` 执行，请求体是 `{name, arguments}`，响应体是 `content` 数组，元素形如 `{type: 'text', text: '579'}`。传输层本地用 stdio——子进程方式启动 server，stdin 写请求、stdout 读响应，每条 JSON 消息一行，`\n` 就是消息边界；跨机器换成 HTTP/SSE。我实现的是 stdio：`spawn` 出子进程，用 `readline` 按行读 stdout。"
- **代码锚点**：三个方法名的分派在 `mcp/mcp_server.js:51-77`（握手 53-58、发现 59-60、调用 61-73）；stdio 传输的读写循环在 `mcp/mcp_server.js:80-92`；客户端侧的握手在 `mcp/mcp_client.js:61`。实测报文：`{"jsonrpc":"2.0","id":4,"method":"tools/call","params":{"name":"add","arguments":{"a":123,"b":456}}}` 换回 `{"result":{"content":[{"type":"text","text":"579"}]}}`。
- **常见追问**：*为什么不一次性把所有工具定义在客户端？* → 那就退回 N×M 了：每接一个系统都要改客户端代码并重新发版。动态发现让"加工具"只发生在 server 那一侧。

### Q3：MCP 工具注册后和普通工具有什么区别？

- **考点**：是否真的做到"平等"，还是把外部工具当成需要特殊照顾的一类。
- **答题结构**：命名空间前缀 → 注册形态与内建工具一致 → 权限/校验/错误分层同一条流水线 → 一句实测证据。
- **参考话术**："没有区别，这是设计目标。注册时给一个 `mcp__<server>__<tool>` 的名字：前缀做命名空间，两台 server 都有 `echo` 也不会互相覆盖；同时让日志和审计一眼看出这次调用出了进程。注册用的定义对象和 `run_shell` 完全一样，是 `name/description/params/fn` 四件套，`params` 用 server 声明的 schema，之后走同一套权限决策、参数校验、错误分层、防失控。我实测过权限这一段：同一个 registry 里，拒绝 `mcp__calc__add` 和拒绝 `run_shell` 拿到的错误体逐字同形，都带 `"code":"PERMISSION_DENIED"`、`"retryable":false`。"
- **代码锚点**：注册循环 `mcp/mcp_tools.js:18-38`（前缀在 24 行、schema 透传在 26 行、等级在 33 行的 `"write"`）；执行流水线在 `registry_full.js:46-84`，六步依次是查表、解析参数、权限、校验、执行、结构化错误。
- **常见追问**：*默认给 write 级是不是一刀切？* → 是保守的默认值，不是结论。理由是外部调用的副作用不可知：多一个确认的成本很低，误放行一个写操作的成本很高。确定只读的 MCP 工具可以把等级改成 `"read"`（`registry_full.js:33-37` 把等级随工具名一起记进权限表，注册期声明、决策期只叠加用户规则）。

## T2 工程深度（区分度所在）

### Q4：MCP 客户端怎么处理并发请求？

- **考点**：RPC 客户端的核心机制——请求与响应怎么配对。
- **答题结构**：自增 id → pending Map → 逐请求超时 → 为什么不用"发一条等一条"。
- **参考话术**："靠 id 匹配。每个请求发出去之前取一个自增 id，把 `{resolve, reject, timer}` 存进一张 `pending` 表，然后才写 stdin；响应回来时按 `msg.id` 从表里取对应的 Promise，取到了就删表项、清定时器，把 `result` 交给 resolve。请求和响应之间没有别的约定，只有这个 id。这样多个请求可以同时在途，不依赖 FIFO 顺序；每个请求挂自己的超时，一个卡住不会拖垮其他请求，超时文本还带方法名，比如 `MCP 请求超时: initialize`，排查时直接看出卡在哪一步。诚实的补充：我这一章的 server 是逐行处理的，响应顺序其实稳定，所以顺序做法在演示里看不出问题；id 匹配买到的是并发安全和将来换 transport 时的免改。"
- **代码锚点**：发请求与挂表 `mcp/mcp_client.js:66-78`（`nextId++` 在 67 行、timer 在 69-72 行、`pending.set` 在 73 行）；响应路由 `mcp/mcp_client.js:46-59`（id 匹配在 49-55 行）；实测报文里 id 是 2、3、4、5 一路递增，握手那次是 1。
- **常见追问**：*pending 里的 Promise 如果永远不 resolve 会怎样？* → 有超时兜底，超时会 reject 并把自己从表里删掉（`mcp/mcp_client.js:70`），不会泄漏表项。缺的是子进程崩溃后的处理：写 stdin 会得到 EPIPE，client 目前不重连，这一条我写在 README 的缺口表里。

### Q5：MCP 错误怎么处理？为什么用 isError 不抛异常？

- **考点**：错误分层意识，以及"给模型的错误"和"给程序的异常"这两个概念的区分。
- **答题结构**：两层错误（协议级 / 业务级）→ 各自走哪条路 → 为什么业务错误不能抛 → 客户端怎么翻译。
- **参考话术**："分两层。协议级错误——JSON 解析失败、请求 id 对不上这类——走 JSON-RPC 自己的 `error` 字段，客户端收到后 reject；业务级错误——工具不存在、参数不对、下游系统不可用——走结果的 `isError: true` 加 `content`，不抛异常。原因是这两种错误该被谁处理：工具错误是给 Agent 看的信息，模型看到'未知工具: nope'下一轮自己改名字，走结果路径它才有机会；抛异常会打断整条会话，把一次可以自愈的调用变成一次失败请求。客户端在 `callTool` 里做翻译，把 `isError` 转成内部的 `{error}`，接进 registry 既有的错误分层，于是外部错误和内部工具错误在模型眼里长得一样。"
- **代码锚点**：server 侧返回 isError 在 `mcp/mcp_server.js:72`，协议级错误路径在 `mcp/mcp_server.js:87-90`（只有 JSON 解析失败会写 `error` 字段）；客户端翻译在 `mcp/mcp_client.js:90-92`；协议的 reject 分支在 `mcp/mcp_client.js:53`。
- **常见追问 / 诚实备注**：*那"未知方法"是协议级错误吗？* → 在本课代码里不是。`mcp/mcp_server.js:74-76` 的 `default` 分支返回 `{error: ...}`，会被 86 行塞进 `result` 字段，实跑 `_request("bogus/method")` 得到的是 resolve 而不是 reject：`{"error":"未知方法: bogus/method"}`。这是代码和我文档口径不一致的地方，我把它记成了已知问题（README 缺口表里，一行修复方案），没有藏起来；副作用是客户端 `mcp/mcp_client.js:53` 的 reject 分支目前没有真实触发路径，也就没有用例覆盖。

### Q6：动态发现 + 注册是怎么落地的？

- **考点**：协议红利能不能落到"改动量"这个可验证的说法上。
- **答题结构**：一个循环的三步 → 四个字段逐个对应 → 接入成本量化 → Agent 侧零改动。
- **参考话术**："落地就是一个循环。`registerMcpTools` 先 `listTools()` 拿回工具数组，然后逐个 `registry.register`：名字拼成 `mcp__<server>__<tool>`，描述后缀标出来源，`params` 用 server 给的 schema，`fn` 是闭包捕获这个 client 的一次 `callTool`。接入一台新 server 的改动量就是这一个循环加上一两行调用——`connectMcpServer` 把'建客户端、握手、注册'收成一步，`main.js` 里就是一行。真正的红利在 Agent 那侧：`agent.js` 对 MCP 一行都不改，它只认 registry 里的名字。所以架构上这不是给 Agent 加了一层能力，而是给 registry 多了一个工具来源。"
- **代码锚点**：`mcp/mcp_tools.js:18-38`（四个字段分别在 24、25、26、27-30 行）、`mcp/mcp_tools.js:41-47`（一步接入）、`main.js:55-58`（调用现场）；实测注册结果是三个名字 `mcp__calc__add` / `mcp__calc__echo` / `mcp__calc__get_time`。
- **常见追问**：*工具名冲突、同名覆盖怎么办？* → 前缀把冲突挡在注册之前，同名工具在不同 server 下是两个不同的 key。真要收敛工具数量，做法是在注册时按 server 白名单过滤，而不是让后注册的覆盖先注册的。

### Q7：Loop 检测命中之后，同一条响应里剩下的 tool_calls 怎么处理？

- **考点**：对"消息配对"这条硬约束的理解，以及对同族缺陷的排查习惯。
- **答题结构**：约束是什么 → 原实现的错在哪 → 修复形态 → 怎么证明修完了 → 边界诚实交代。
- **参考话术**："规则是硬约束：模型一条响应里发了几个 `tool_calls`，下一轮请求里就得有几个对应的 `role='tool'` 消息，一个都不能少，顺序也要跟得上。原来的实现在防失控的 Loop 检测命中后直接 `break` 跳出工具循环：如果这条响应里有多个 `tool_calls`、命中的不是最后一条，后面的调用既没执行、也没有回填——下一轮那条 assistant 消息仍然带着全部 `tool_calls`，服务端一数配对数量对不上，直接 400。修法是加一个 `loopDetected` 标志：判定命中后剩下的调用仍然跳过执行（防死循环的目的不变），但每条都补一条 `LOOP_DETECTED` 错误结果，`break` 换成 `continue`。配对这件事我只用离线用例断言：把 `cm.build()` 拿下来，逐条检查每个 `tool_calls` 的 id 都有配对，两个用例分别盯 Agent 和子 Agent；这个 400 本身我没有对着真实服务端复现过，如实说，第 4 章的文档里记过它的真实形态。"
- **代码锚点**：修复后 `agent.js:139-165`（标志位在 143 行、判定在 152-154 行、回填在 156-164 行）；子 Agent 侧 `subagent.js:122-151`；回归用例 `test.js:228` 与 `test.js:270`，公共断言函数在 `test.js:34`。跨章同款：`lesson04-core-tools/agent.js:69-95` 与 `lesson04-core-tools/test.js:237`（第 4 章先修），第 10 章沿用同一写法（`lesson10-session/agent.js:138`、`lesson10-session/test.js:122`）。
- **常见追问**：*还有哪些地方会拆散配对？* → 上下文压缩的切点：如果切点正好落在一条 tool 消息上，前面的 assistant(tool_calls) 被压进摘要、tool 消息留下，配对同样断掉。第 3 章的做法是把切点前移对齐消息边界（`context_manager_v2.js:98-108`），第 10 章在恢复会话时还要再截断一次。同一个约束在三个地方出现过，这类缺陷值得按"配对完整性"当关键词全仓搜一遍。

## T3 架构设计（对标 AI 技术负责人）

### Q8：MCP、Skill、Plugin 三者的完整关系？

- **考点**：三个常被混着说的扩展机制能不能分层说清，而不是当成三个并列功能。
- **答题结构**：各自本质（协议 / 知识 / 代码）→ 各自解决什么 → 各自的加载时机 → 一个组合例子。
- **参考话术**："三者正交，解决不同层的问题。MCP 是**协议**，管外部工具怎么接进来，加载时机是连接时动态发现，解决'有系统'；Skill 是**知识**，教 Agent 用已有工具完成任务，加载时机是命中场景按需注入，解决'会干活'；Plugin 是**代码**，通过钩子给 Agent 本体加横切能力，加载时机是启动时装配，解决'能扩展'。组合起来是一个完整故事：MCP server 提供 `add` 这个外部能力，Skill 写'做数学任务时先调 add 再交叉验证'，Plugin 挂一个 `PreToolUse` 钩子把每次 add 调用记进审计。一句话收口：MCP 给手，Plugin 给能力，Skill 教手巧。"
- **代码锚点**：本章的 MCP 在 `mcp/` 三个文件；钩子扩展点在 `hooks/hook_registry.js:15-18`（两个事件）与 `agent.js:167-184`（触发点）；技能那一侧在 `skill_trigger.js` 与 `agent.js:115-122`（三段注入）。三者交汇的地方就是 registry：工具、钩子、注入文本最终都作用在同一次推理上。
- **常见追问**：*如果只能留一个，留谁？* → 留工具系统，另外两个都是加在它上面的。顺序也能看出依赖关系：MCP 要先有 registry 才能注册，钩子要先有工具执行链才能挂，技能要先有工具才有"怎么用"可教。

### Q9：MCP 客户端的连接管理与健壮性，你现在做到哪一步？

- **考点**：对自己实现的边界清楚，且知道生产要补什么、为什么。
- **答题结构**：已做（握手、超时、关闭）→ 缺的（重连、心跳、连接预算、可配置 server）→ 每一条的动机 → 诚实边界。
- **参考话术**："已做的三件：`connect` 里 spawn 子进程并完成握手；每个请求独立 5 秒超时；`close` 杀子进程，`main.js` 退出时调用，避免留孤儿进程。缺的四件：子进程崩溃后客户端没有感知，写 stdin 得到 EPIPE 就结束了，生产要加健康检查和有上限的重连，Qwen Code 的做法是重连最多 3 次；半开连接要靠心跳发现；连接预算，一个 Agent 能挂几台 server 要有个上限，否则配置错了会同时拉起几十个进程；server 命令要可配置，我现在把脚本路径硬编码在客户端里（`mcp/mcp_client.js:19-22`），只能连本目录这个 server。诚实说一句：stdio 是'进程信任边界'内最简的传输，跨机器必须换 HTTP/SSE，那时候上面这些要求会全部重来一遍。"
- **代码锚点**：`mcp/mcp_client.js:40-63`（spawn 与握手，`stdio: ["pipe","pipe","inherit"]` 在 41-43 行）、`mcp/mcp_client.js:66-78`（逐请求超时）、`mcp/mcp_client.js:102-108`（close）、`main.js:114`（退出时关闭）。
- **常见追问**：*子进程假死（活着但不回消息）怎么办？* → 现在靠请求超时，5 秒后 reject，报错文本带方法名。缺的是"发现之后怎么办"：一次超时之后应该探测连接健康、必要时重建 client 并重新注册工具，否则注册表里那批工具会一直指向一个死进程。

### Q10：生产环境接 MCP 还要考虑什么？

- **考点**：0→1 之外的安全与规模化意识，对标"方案设计"这一类问题。
- **答题结构**：传输层选型 → 安全三件（工具投毒 / SSRF / 认证）→ 输出上限 → 可观测与成本 → 一句改安全边界的话。
- **参考话术**："分五块。传输层：本地 stdio 和远程 HTTP/SSE 是两种信任模型，远程要支持服务端推送和多路复用。安全是最重的一块：恶意 server 可以声明诱导性工具让模型误用，这是工具投毒，防线是工具白名单加信任标记；外部 server 不能被用来打内网，要挡 SSRF；远程 MCP 还要认证，OAuth 或 service account。输出上限：MCP 的返回可能放大到几百 KB，比普通工具大一个量级，我这一章它和别的工具共用同一个 1000 token 的截断（`context_manager_v2.js:21`），生产要给 `mcp__` 前缀单独配。可观测：每次外部调用的耗时、token、成功率要能归因到具体 server，接审计钩子就能做。最后收一句：MCP 把安全边界外移到了 server 进程，所以信任标记和输出上限是远程 MCP 的第一优先级，不是可选优化。"
- **代码锚点**：默认等级与来源标注在 `mcp/mcp_tools.js:25` 和 `33`；截断实现在 `context_manager_v2.js:28-37`；钩子接入点在 `agent.js:168` 与 `agent.js:184`（审计与脱敏都能挂在这两处）。本课缺的安全项在 README 缺口表里逐条列了后果与补法。
- **常见追问**：*让 Agent 自动安装并连接第三方 MCP server，风险在哪？* → 等于让模型决定代码执行路径。可控做法是三层：server 清单由人审后写入配置、连接前校验来源与命令白名单、工具级信任标记控制是否需要每次确认。本课的默认 write 级确认只是第一层。
