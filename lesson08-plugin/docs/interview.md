## T1 基础原理（必过线）

### Q1：Plugin、MCP、Skill 三者的区别？第 8 章为什么做 Plugin 而不是做 MCP？

- **考点**：三个常被混着说的"扩展机制"能不能按层次分开，而不是笼统说成"都能加能力"。
- **答题结构**：一句话定性（代码 / 协议 / 知识）→ 各自解决什么 → 加载时机 → 分层收口。
- **参考话术**："它们解决不同层次的问题。MCP 是**协议**（JSON-RPC），管外部工具怎么标准化接进来，工具实现根本不在这个进程里，连接时才发现有哪些工具；Plugin 是**代码**，通过 Hooks 给 Agent 运行时注入能力，是框架的扩展点，启动时装配；Skill 是**知识**（提示词 + 步骤），教 Agent 用**已有**的工具完成某类任务，按需加载。一句话：MCP 是协议、Plugin 是代码、Skill 是知识。分层看，MCP 和 Plugin 提供'手'，Skill 提供'手巧'。第 7 章做的 Skill 是往 system prompt 里塞文本，改变的是模型的判断；第 8 章做的 Plugin 塞的是可执行代码，改变的是工具被调用这件事本身——它能在执行前把调用拦下来，这是文本做不到的。"
- **代码锚点**：`hooks/hook_registry.js:15-18` 定义事件枚举（`preToolUse` / `postToolUse`）；`plugins/audit-log/plugin.js:46` 是插件工厂；`hooks/hook_registry.js:4-6` 的文件头注释直接标明对应 Qwen Code 的 `hooks/` 系统。
- **常见追问**：*第 7 章的技能不是也改了行为吗，为什么不算 Plugin？* → 技能只能改变模型的输入，模型完全可以不照做；插件在框架层执行，模型没有拒绝的余地。可靠性来源不同，这是两者必须都留的原因。

### Q2：Plugin 的本质是什么？为什么 Hooks 是插件系统的核心？

- **考点**：能不能把"插件"说到扩展点的层面，而不是背一个 `install()` 的接口。
- **答题结构**：本质（横切扩展）→ Hooks 的三件套（定义事件 / 暴露注册 API / 在合适时机触发）→ 反面（没有 Hooks 会怎样）→ 类比成熟产品。
- **参考话术**："Plugin 本质是**代码级横切扩展**：不改框架源码，通过订阅生命周期事件注入能力。插件系统最怕的就是'加能力要改框架'——写一个审计插件要动 `agent.js`、写第二个要再动一次，框架很快就不敢升级了。Hooks 把这件事解掉：框架只做三件事，定义事件、暴露注册 API（`add(event, fn)`）、在合适的时机触发（`fire`），插件订阅事件自己决定做什么，卸载时把注册摘掉。没有 Hooks，插件就只剩'改框架源码'一条路，谈不上插拔。这套模式在成熟系统里到处是：VS Code 的 ExtensionHost、webpack 的 Tapable、浏览器扩展 API、Git hooks。"
- **代码锚点**：`hooks/hook_registry.js:38-45` 是注册 API（未知事件名直接抛错，避免静默注册一个永不触发的钩子）；`hooks/hook_registry.js:48-56` 与 `hooks/hook_registry.js:59-64` 是两个触发点；`agent.js:55` 是框架侧唯一为插件付出的成本——`this.hooks = hooks || new HookRegistry()`。
- **常见追问**：*为什么不做成事件总线或者用现成的 EventEmitter？* → 零依赖是一个原因，更重要的是语义：这里要的不是"广播消息"而是"可以否决的钩子"，pre 需要短路返回 `{blocked}`、post 需要能改写结果，通用的 EventEmitter 表达不了这两件事，还得在框架侧补一层约定，反而更绕。

### Q3：PreToolUse 和 PostToolUse 分别能做什么？触发语义是什么？

- **考点**：两个钩子的能力边界，以及"为什么只有这两个"这种克制型设计。
- **答题结构**：两个钩子的输入输出 → 短路语义 → 串行顺序 → 为什么不再往里加触发点。
- **参考话术**："PreToolUse 收到 `{name, args, turn}`，返回 `{blocked: true, reason}` 就拦下这次执行，返回 undefined 表示放行；同一个事件有多个钩子时按注册顺序串行，**第一个 blocked 立即短路**，后面的钩子不再跑——拦截是一票否决。PostToolUse 收到 `{name, args, result}`，只能原地改 `payload.result`，用来脱敏、统计、后处理。触发点只有两个是刻意的：再往里就走进了推理循环内部（改消息、改预算、改轮次），那是重写框架而不是扩展框架；而这两个点覆盖了真实插件的大部分需求——执行前要检查和记录，执行后要脱敏和统计。"
- **代码锚点**：`hook_registry.js:48-56` 的短路返回、`hook_registry.js:50` 的 `(await fn(payload)) || {}`（钩子返回 undefined 也不会炸）；`hook_registry.js:59-64` 的 post 循环与返回；框架侧两个调用点是 `agent.js:163`（pre）和 `agent.js:181`（post）。
- **常见追问**：*钩子执行顺序可控吗？* → 只有注册顺序一种语义，没有优先级字段，也没有并发。串行是为了让结果可预测（先留痕后放行、还是先放行后留痕，审计记录不一样）；代价是慢钩子会拖慢整个工具调用，生产要给每个钩子加超时，这是本章认的缺口。

## T2 工程深度（区分度所在）

### Q4：你写的 audit-log 插件解决了什么问题？为什么不重新写一个工具来实现？

- **考点**：价值论证能力，以及"横切关注点不该写进业务逻辑"这条判断。
- **答题结构**：四个能力 → 各自挂在哪 → 为什么用钩子而不是改工具 → 真实产品对标。
- **参考话术**："它对准企业落地 Agent 的四个硬需求。**合规留痕**回答'谁在什么时候让它调了什么、结果如何'，内存可查 + `audit.log` 留档，每行一条 JSON；**危险拦截**把 `rm -rf`、`shutdown`、fork bomb 挡在执行之前，规则是 `{tool, field, pattern, reason}` 四元组，可配置；**参数脱敏**把键名里带 token、password 的字段打码成 `***`，防审计日志本身泄漏凭据；**使用统计**按工具记 调用 / 错误 / 拦截 三个数，这是成本分析和质量监控的基础。为什么不用改工具实现？因为这三件事对六个工具都一样，写进工具就是六份重复代码，而且第二个需求（统计）来了还要再改六遍。用钩子写一遍，工具一行不动——我的账是新增 3 个文件 215 行、`agent.js` 只碰 3 处。真实产品里这类能力对应 LangSmith 的 trace 层和企业的合规审计系统。"
- **代码锚点 / 实测数字**：`plugin.js:65-78`（pre：先跑危险规则、命中留痕并返回 blocked，未命中才写 `call` 记录）；`plugin.js:22` 与 `plugin.js:25-37`（`SENSITIVE_KEYS` + `maskArgs`）；`plugin.js:81-89`（post 记 `status` / `errorCode` / 120 字符预览）；`plugin.js:113-122`（`summary()` 按工具聚合成 `{calls, errors, blocked}`）。实跑记录格式：`{"event":"call","name":"fetch_url","args":{"url":"...","api_key":"***"}}`；`summary()` 输出 `{"run_shell":{"calls":0,"errors":1,"blocked":1}}`——被拦的调用只记 `blocked` 不记 `call`，所以"调用次数"不会被拦截虚高。
- **常见追问**：*脱敏写在这一层够吗？* → 不够，也不该当唯一防线。键名匹配是尽力而为的兜底，模型把密钥塞进 `command` 这种通用字段就漏了。真正的治理是让凭据不进参数（用引用替代），插件层只防疏忽——"脱敏是纵深防御的一环"这句话比"我做了脱敏"更接近工程现实。

### Q5：插件的可插拔怎么实现的？卸载会不会影响别的插件？

- **考点**：`install` 返回卸载函数这个契约的实现细节，以及有没有想过多插件共存的场景。
- **答题结构**：注册契约 → 卸载实现（闭包 splice）→ 多插件隔离 → 实测验证方式。
- **参考话术**："`install(hooks)` 注册全部钩子并**返回一个卸载函数**（`plugin.js:92-98`），里面是 `removers.forEach((remove) => remove())`。每个 `remove` 是 `HookRegistry.add` 返回的闭包，它捕获了自己 push 进去的那个函数引用，卸载时按引用 `indexOf` 再 `splice`（`hook_registry.js:41-44`）——所以摘掉的是自己那一个，不会误伤别的插件。这一点我实测过：同一个插件 `install` 两次，卸载其中一次之后，钩子仍然生效（pre 依然返回 `{"blocked":true,...}`），说明移除函数只摘自己注册的那一个。可插拔的工程价值是按环境启用插件（开发装调试插件、生产只装审计），出问题能一键摘掉，框架侧不留残留。"
- **代码锚点**：`plugin.js:92-98`；`hook_registry.js:38-45`；`main.js:45-47` 装配三行、`main.js:116` 退出前 `uninstallAudit()`。
- **常见追问**：*插件卸载了，之前写进审计文件的记录怎么办？* → 记录是数据不是能力，卸载不回收。而且 `records` 也存在内存里，进程重启就没了——所以本章的审计只能算"进程内可查 + 本地留档"，生产要落到集中式日志或 OpenTelemetry。

### Q6：PreToolUse 拦截之后，模型会变成什么样？为什么不静默跳过？

- **考点**：对"框架与模型分工"的理解——拦截逻辑保持简单，决策留给模型。
- **答题结构**：回填什么 → 模型会怎么反应 → 静默跳过的危险 → 与权限系统的区别。
- **参考话术**："拦截之后不执行工具，往消息历史里回填一条 `role:"tool"` 的结果，内容是 `{"error":{"code":"HOOK_BLOCKED","message":"[audit-log] 拦截递归删除 rm -rf"}}`——就是模型发起调用时那条 `tool_call_id` 对应的回填位置。模型拿到的是一个"工具报错"，它会自己换方案：换命令、换工具、或者来问你。理由写具体很重要，看到"被判定为递归删除"它才会真的改；只写"被拦截"它会重试。静默跳过是更糟的选项：模型以为命令执行成功了，会基于"已经清理完"这个错误前提继续推理，你连它错在哪都不知道。和权限系统的区别是分工——权限系统在问'谁来批准'（需要用户在场、交互式），钩子在做'策略判定'（不需要用户、可编程、可批量）。顺序上钩子在外层、权限在里层：`agent.js:163` 的 PreToolUse 先跑，放行之后才进 `registry.execute`（`agent.js:176`），权限决策发生在执行流水线内部（`registry_full.js:59-65`）。所以插件可以在用户被问之前就把危险调用挡掉，省掉一次确认弹窗。"
- **代码锚点**：`agent.js:163-174`（firePreToolUse → blocked → 回填 → `continue`）；回填内容在 `agent.js:169`；`test.js:150` 的端到端用例就是断言模型"看到"的是 HOOK_BLOCKED 而不是只看插件内部状态。
- **常见追问**：*被拦的调用还能继续同一条响应里其他 tool_calls 吗？* → 能。这里是 `continue` 不是 `break`：一次响应可能带多个调用，一个被拦不该中断其余调用。反过来说，同一条响应里每个 `tool_calls` 都必须有回填，少一条历史就配对不全——这正是本章修掉的第一个 bug。

### Q7：这一章你改了哪些代码？怎么发现这些问题的？

- **考点**：缺陷发现的方法论，以及"没有报错不等于正确"的自觉。
- **答题结构**：四类改动 → 最有价值的那个怎么发现 → 回归用例怎么写 → 诚实的未覆盖项。
- **参考话术**："四处改动都不是崩溃型的。最有价值的是 Loop 检测那条：判定死循环时代码用 `break` 跳出工具循环，结果是同一条响应里排在后面的 `tool_calls` 既没执行也没有 `role:"tool"` 回填，`assistant(tool_calls)` 与 `tool` 消息不成对，真实服务端会直接 400。**我是怎么找到的**：这个缺陷跟第 2、3、4 章修过的是同一个族，那几章的 `agent.js` 已经写成 `loopDetected` 标记 + `continue` 逐条回填（对照 `lesson03-context/agent.js:84-96`、`lesson04-core-tools/agent.js:83-93`），我 grep 了所有 agent.js 里 `LOOP_DETECTED` 附近的代码，发现第 5、6、7 章的这份代码还是 `break`，本章这份也是。修法是加标记 + 逐条回填 `LOOP_DETECTED`（`agent.js:138-160`），同一轮把第 5~7 章的同款代码一起改掉（`lesson05-memory/agent.js:98-124`、`lesson06-multi-agent/agent.js:110-136`、`lesson07-skill/agent.js:136-162`），回归用例 `test.js:218` 用一个配对断言函数 `test.js:204` 扫全部消息，断言每条带 `tool_calls` 的 assistant 后面对齐了所有 id、且没有孤儿 tool 消息；修复前它直接报 `AssertionError: tool_call 没有回填: b2`。另外三处：post 钩子改写结果的返回值之前被丢掉了（只 await 不取返回值，替换写法静默失效，用例 `test.js:268`，修在 `agent.js:181`）；`/audit-summary` 被 `startsWith("/audit")` 前缀吞掉成了死代码（`main.js:74`，谓词实跑确认过 `true`）；上下文预算被复制回了第 6 章的 4096（实跑水位线 2867 对 28672，注入 system 469 token，两个满额工具结果就压过旧水位线，修在 `agent.js:80`）。"
- **代码锚点**：`agent.js:138-160`；`test.js:204-263`；`agent.js:181-183`；`main.js:74`；`agent.js:80`。
- **常见追问 / 诚实备注**：*这些都测了吗？* → 三处有自动化用例（Loop 回填、post 改写、端到端拦截），`/audit-summary` 那处**没有**：`main.js` 是 REPL 入口，导入即启动读循环，元命令分发的逻辑没抽成可测函数，我用等价谓词（`"/audit-summary".startsWith("/audit")`）实跑确认了分支判断，但没有端到端覆盖。把分发逻辑从 REPL 里拆出来是可测性该付的代价，本章没做，写进 README 缺口表。第 5、6、7 章的同类 `break` 我这轮一并改了：三章各自的配对断言跟着补上，属实的说法是"这一族缺陷现在四章一致"。

## T3 架构设计（对标 AI 技术负责人）

### Q8：把 Hooks 放进整个 Agent 执行链，它和工具、权限、防失控、上下文这些机制的先后关系是什么？

- **考点**：能不能把自己写的这一层放进系统里讲，而不是只描述这个模块。
- **答题结构**：一次工具调用的完整链路 → 插件插在哪两处 → 与相邻机制的分工与冲突 → 顺序本身的设计取舍。
- **参考话术**："一次工具调用在本章的链路是这样：模型返回 `tool_calls` → **Loop 检测计数**（`agent.js:147`，超阈值就回填错误不执行）→ **PreToolUse 钩子**（`agent.js:163`，插件可拦截）→ `registry.execute`（`agent.js:176`，内部依次是注册表查找、权限决策、参数校验、执行、异常隔离）→ **PostToolUse 钩子**（`agent.js:181`，可改写结果）→ 重试预算判定与超长截断（`agent.js:187`、`agent.js:197`）→ 回填 `role:"tool"`。分工上，防失控管"是不是在死磕"、权限管"准不准执行"、插件管"执行前后还有什么要做的"、上下文管理管"这段历史放不放得下"。有一处顺序我明确说过是取舍：Loop 检测在钩子之前，所以同一条危险命令连调三次，第三次报的是 `LOOP_DETECTED` 而不是 `HOOK_BLOCKED`。更符合直觉的是把拦截放在计数之前——被拦下的调用不该算进死循环——但那样改动会碰到防失控的语义，本章保留现状并写进缺口表。"
- **代码锚点**：`agent.js:133-203` 是整个工具分支；`registry_full.js:46-84` 是执行流水线的六个阶段；`agent.js:147-149`（Loop）、`agent.js:163`（pre）、`agent.js:176`（execute）、`agent.js:181`（post）、`agent.js:197`（截断）。
- **常见追问**：*如果插件想改的是工具清单而不是某次调用呢？* → 钩子做不到。工具清单来自 `registry.getSchemas()`（`agent.js:130` 传给模型的那份），要按用户权限动态裁剪得在 schema 生成那一步做，那是另一层（也叫工具过滤/允许清单），不是 Hooks 的职责。分清楚"拦一次调用"和"根本不给这个工具"是设计这类系统时的第一个岔路口。

### Q9：生产级插件系统还缺什么？你现在这版上线会出什么事？

- **考点**：对自家实现边界的清醒程度，特别是"没做的那部分会发生什么"。
- **答题结构**：按事故类型分类（稳定性 / 治理 / 观测）→ 每类的具体缺口 → 演进方向。
- **参考话术**："按事故类型分三类。**稳定性**上最大的缺口是钩子没有独立错误边界和超时——`agent.js` 里 `firePreToolUse` 和 `firePostToolUse` 都没有 try/catch，插件内部抛异常会直接炸掉主流程；`audit-log` 自己做了静默（写文件失败吞掉，`plugin.js:57-61`），但这只保护了它自己，装第三方插件就裸了。生产要给每个钩子包 try/catch + 超时（慢钩子不能拖慢工具调用），还要定"钩子失败是放行还是拒绝"——安全类插件应该失败即拒绝（fail-closed），统计类插件失败即放行。**治理**上缺插件发现与隔离：`manifest.json` 现在只是声明，加载是 `plugin.js:128-136` 硬编码的工厂，装新插件要改 `main.js`；插件与框架同进程同权限，没有沙箱，也没有优先级字段（多个 pre 钩子只能按注册顺序）。**观测**上审计只写本地文件和内存，多实例各写各的，重启丢内存态，要真做合规得上集中式日志或 OpenTelemetry trace。
- **代码锚点**：`agent.js:163`、`agent.js:181`（两处没有 try/catch）；`plugin.js:57-61`（插件自己的静默）；`plugin.js:128-136`（硬编码加载，对照 `manifest.json:1-14` 的声明）；`plugin.js:108-109`（`query` 的内存数据集）。
- **常见追问**：*插件失败该放行还是拒绝？* → 按插件的职责定，而且要写在插件清单里让框架知道：审计/统计类失败应该放行（不能因为日志写不进去就拦用户的活），拦截类（DLP、危险命令）失败应该拒绝。这就是 manifest 里除了 `hooks` 之外该有的字段，现在只有 `config`。

### Q10：如果让你从 0 到 1 设计一个企业级插件平台，路线怎么走？

- **考点**：0→1 方案设计能力 + 对扩展点治理的理解，而不是把功能清单堆一遍。
- **答题结构**：三阶段（能插 → 可治 → 可隔离）→ 每阶段的交付与验收 → 最容易做错的地方。
- **参考话术**："三个阶段。**第一阶段能插**：固定事件集 + 注册 API + `install` 返回卸载函数，本章的 215 行就是这个阶段的最小原型，验收标准是'加一个插件不改框架代码'。**第二阶段可治**：manifest 驱动发现（扫描目录、读清单、注入配置、生命周期管理）、钩子优先级、错误边界与超时、失败语义声明（fail-open / fail-closed）、审计结果落到集中式 trace，验收标准是'第三方能自己发布插件，框架不用为它改一行'。**第三阶段可隔离**：插件跑在独立进程或沙箱里（能力通过 IPC 暴露），按清单声明授予权限（只读文件? 能发网络?），配额与限流（一个插件不能吃满 CPU），灰度与一键摘除，验收标准是'一个坏插件最坏只影响自己'。最容易做错的是第一阶段就上沙箱和进程隔离——插件生态最难的部分是让人愿意写插件，接口简单才有生态；隔离是有了真实插件之后才付的账。"
- **代码锚点**：第一阶段的两个契约在 `hook_registry.js:38-45` 与 `plugin.js:92-98`；第一阶段的"框架零侵入"证据就是 `agent.js` 只有三处插件相关代码（`agent.js:55`、`agent.js:163`、`agent.js:181`）；第二阶段的入口是 `manifest.json` 的三个字段（`hooks` / `config` / 缺失的失败语义与优先级）。
- **常见追问**：*插件和 MCP 会功能重叠吗？两边都能提供工具。* → 重叠的是"能提供工具"，不重叠的是"能不能改变框架行为"。MCP 的边界是工具面（发现、调用、错误），它管不到"工具执行前拦一下"或者"输出前脱敏"；Plugin 是框架内的代码，能挂生命周期。真要在生产里做一件事，判断标准是"这个能力是数据面还是控制面"——数据面走 MCP，控制面走 Plugin。第 9 章接 MCP 之后这两条线会同时存在。
