# lesson07 · Skill 系统 —— 面试题讲解（Node 版）

> 10 题，三层深度。每题按固定结构展开：**考点 → 答题结构 → 参考话术 → 代码锚点 → 常见追问**。
> 本章可引用的证据：新增 4 个文件 266 行（`skill_store` / `skill_registry` / `skill_tool` / `skill_trigger`）+ 3 个 `SKILL.md` 共 70 行；`agent.js` 只改了 3 处；17 个用例全绿（离线，约 180ms）；自动注入只取 1 个有专门用例。

## T1 基础原理（必过线）

### Q1：Skill、MCP、Plugin 三者的区别？

- **考点**：能不能把三个"扩展机制"按层次分开，而不是笼统说成"都能加能力"。
- **答题结构**：一句话定性（协议 / 代码 / 知识）→ 三者各自解决什么 → 加载时机 → 分层收口。
- **参考话术**："它们解决不同层次的问题。MCP 是**协议**（JSON-RPC），管外部工具怎么标准化接入，一个 server 能被任何客户端调，连接时才发现有哪些工具。Plugin 是**代码**，给 Agent 运行时注入新能力（钩子、工具），是框架的扩展点，启动时装配。Skill 是**知识**，教 Agent 用**已有**的工具完成某类任务，按需加载。一句话：MCP 是协议、Plugin 是代码、Skill 是知识。分层看，MCP 和 Plugin 提供'手'，Skill 提供'手巧'。"
- **代码锚点**：`skill_store.js:1-13` 的文件头注释直接写明本章实现对应 Qwen Code 的 `.qwen/skills/<name>/SKILL.md` 和 Hermes 的 skill 机制；技能根目录固定在 `skill_store.js:20-23`。
- **常见追问**：*为什么不做成插件（代码）而要做成知识（文本）？* → 因为要解决的是"知道怎么做"而不是"能做"，文本可以被领域专家写、被 review、进 git 版本化；知识用代码表达会把写技能的门槛抬到"会写代码"。

### Q2：`SKILL.md` 的格式长什么样？为什么 `when_to_use` 要单独占一个字段？

- **考点**：文件格式的设计动机，而不是背字段名。
- **答题结构**：frontmatter 四字段 + body → 每个字段给谁用 → `when_to_use` 与 `description` 的分工。
- **参考话术**："`skills/<name>/SKILL.md`，frontmatter 四个字段加正文。`name` 是索引 key，`description` 是给模型看的用途说明（显式加载时它判断这个技能对不对得上），`when_to_use` 是**给触发器看的关键词表**，`tools` 是技能用到的工具白名单；正文是步骤/要点/示例，注入后当执行指南。`when_to_use` 单独一个字段是因为两种消费者要的东西不一样：`description` 写给人读的一句话，`when_to_use` 写给机器匹配的一串关键词。混在一起写，匹配精度和可读性会互相牵制。"
- **代码锚点**：`skills/code-review/SKILL.md:1-5` 是 frontmatter 实例；`skill_store.js:27-57` 是解析函数，`skill_store.js:28` 的正则用 `\n+` 宽容处理分隔符后的空行（手写技能时 `---` 后面常常直接接正文）；`skill_store.js:48` 缺 `name` 直接返回 `null`。
- **常见追问**：*技能写坏了会怎样？* → 单个技能解析失败返回 `null` 被静默跳过，不炸整个技能库（`test.js:72` 钉住这条行为）。代价是写错不报错，只表现为"列表里少一个"，生产要在启动时做校验并告警。

### Q3：技能和记忆都往 system prompt 尾部注入，区别在哪？

- **考点**：能不能分清"事实"和"方法"两类上下文。
- **答题结构**：四维对照（内容 / 来源 / 粒度 / 触发）→ 机制相同这一层 → 落到代码位置。
- **参考话术**："机制是同构的，都是 system prompt 尾部的动态片段，都不落进对话历史。区别在内容和来源：记忆是**事实和偏好**（用户用 4 空格缩进），来源是对话中自动提取，粒度是一条条小事实，靠 description 相关性召回；技能是**流程和方法**（怎么做 code review），来源是人工编写沉淀，粒度是一个完整任务流程，靠 `when_to_use` 做任务类型匹配。一句话：记忆回答'你是谁、你喜欢什么'，技能回答'这类任务该怎么做'。"
- **代码锚点**：`agent.js:107-118` 三段拼接就是这两个系统的交汇点——`memory.formatRecall(recalled)` 在前、`buildSkillInjection` 在后；两边打分逻辑对照着看更清楚：记忆 `recall.js:35-47` 是 description+3 / name+2 / body+1，技能 `skill_registry.js:55-57` 是 when_to_use+2 / description+1 / name+1。
- **常见追问**：*两者冲突怎么办？* → 记忆里的事实优先（比如用户明确说过"我们不用 pytest"），技能里的步骤允许偏离；本章的注入标题写了"任务符合该技能场景时"就是留这个余地。

## T2 工程深度（区分度所在）

### Q4：技能有哪两条触发通道？各自靠什么保证可靠？为什么自动注入只取一个？

- **考点**：双通道设计的取舍意识 + "最小注入"这种克制型的工程判断。
- **答题结构**：两条通道 → 可靠性来源不同 → 为什么都留着 → Top 1 的理由 → 实测数据。
- **参考话术**："显式通道是模型自己调 `skill("code-review")` 工具，正文作为 tool 结果回填。它灵活，模型可以按需组合多个技能，但依赖模型'知道有哪些技能'，所以 system 里必须注入可用技能清单，否则工具形同虚设。自动通道是框架对用户输入打分，命中就注入，不依赖模型判断，更可靠，但关键词匹配有误差。生产两条都留：自动覆盖常见场景，显式覆盖模型的自主判断。自动只注入 **Top 1**：技能注入是指导不是堆砌，同时塞两个流程，模型要在两套步骤间自己选，还可能撞上互相矛盾的要求。没被选中的技能仍在清单里，模型可以自己拉进来。"
- **代码锚点 / 实测数字**：`skill_tool.js:19-50` 是显式工具体；`skill_trigger.js:16` 是 `AUTO_INJECT_LIMIT = 1`，`skill_trigger.js:24-26` 就一行 `slice(0, AUTO_INJECT_LIMIT)`；可用清单在 `skill_tool.js:54-60`，由 `agent.js:115` 拼进 system。实跑打分："帮我 review 一下 lesson07-skill 目录的代码" → code-review 6 / bug-hunt 1；"写份报告，排查一下报错" → bug-hunt 5 / report 3，只注入分高的那个（`test.js:151` 钉住 Top 1 行为）。
- **常见追问**：*自动匹配错了怎么办？* → 两条兜底：模型看到注入的步骤不合场景可以按自己的判断做（注入标题写了"符合场景时"）；用户也可以直接点名"用 xxx 技能"走显式通道。

### Q5：自动触发的打分是怎么设计的？关键词匹配的天花板在哪？

- **考点**：权重设计的依据 + 对方案的局限有清醒认识。
- **答题结构**：分词复用 → 权重与依据 → 局限（举反例）→ 演进路径（接口不变）。
- **参考话术**："分词直接复用第 5 章的 `tokenize`：英文数字取 ≥2 字符的词，中文切 2-gram。打分是 `when_to_use +2 / description +1 / name +1`，依据是'字段为什么被写出来'——`when_to_use` 存在的唯一目的就是做触发关键词表，命中它说明任务类型对上了；`description` 是给模型看的说明，顺带参与；技能名是弱信号。天花板很明确：字面不重合就召不回。用户说'帮我看看这段 Vim 配置'、技能里写的是'编辑器配置'，没有共同 token，自动通道就失效。跨过去要换 embedding 语义检索，而 `match()` 是唯一改动点——这是把匹配实现藏在一个函数后面换来的好处。"
- **代码锚点**：`skill_registry.js:44-63`（打分循环在 `skill_registry.js:53-58`，过滤 `score > 0` 在 61 行，降序在 62 行）；分词在 `recall.js:17-33`；无命中不注入的行为在 `test.js:143`。
- **常见追问**：*为什么不用 LLM 来选技能？* → 可以，第 5 章的 `rerankByLLM` 就是这个思路（`recall.js:76` 起）。代价是每轮多一次模型调用，技能选择这种粗粒度判断先用关键词过滤、必要时才用模型精排更划算。

### Q6：技能怎么和工具配合？`tools` 字段到底有什么用？

- **考点**：是否知道自己实现的边界（声明了但没生效的字段，敢不敢说）。
- **答题结构**：技能不提供工具 → 提供的是调用顺序与取舍 → `tools` 的三重作用 → 如实说明当前未生效。
- **参考话术**："技能不新增任何工具，它提供的是'怎么组合已有工具'的 SOP：先 `git diff` 定位变更范围，再 `read_file` 读上下文，最后按严重度汇报——这三步用的都是第 4 章就有的工具。`tools` 字段有三重作用：文档（逼写技能的人想清这个任务要什么能力）、校验（技能要求的工具不存在时能提前发现）、权限（未来可按技能绑最小工具集）。**本章只做到声明，执行层没有按它过滤**——技能的返回体只有 name/description/content 三个字段，`tools` 不参与执行，这一点我专门写了用例钉住（`test.js:122`），缺口写进测试，下一章修的时候先看红灯。"
- **代码锚点**：`skill_tool.js:41-48` 是返回体（只有三个字段）；白名单声明在 `skills/code-review/SKILL.md:5`；落实它的地方应该是 registry 的 schema 过滤或第 8 章的 `PreToolUse` 钩子。
- **常见追问**：*技能要求一个不存在的工具，你现在会发现吗？* → 不会，本章没有做这个校验；生产做法是加载技能时对着 registry 的名字表校验一遍，缺失就打日志或拒绝加载。

### Q7：这个技能系统你怎么测的？

- **考点**：能不能把"注入"这类看不见的行为测出来。
- **答题结构**：用例分块 → 最关键的一条测法 → 缺口如实交代。
- **参考话术**："17 个用例分五块，外加 2 条 Loop 配对回归用例：解析（frontmatter、tools 数组、往返、坏内容返回 null）、索引（match 排序）、显式通道（加载成功 / 不存在返回错误+清单 / 清单文本）、自动通道（命中 / 无命中不注入 / 多技能只取 Top 1 / 注入文本格式）、Agent 集成。最有价值的是集成测法：假 LLM 被调用时把 `messages[0].content` 抓下来，断言里面同时出现基础提示、'已加载技能'、'code-review'、'可用技能'（`test.js:197-200`）——**注入这件事本身可断言**，不必依赖最终回答好不好。显式通道则是让假 LLM 第一轮返回 `skill("report")` 的 tool_calls，断言技能正文被回填后按技能执行（`test.js:238`）。"
- **代码锚点**：`test.js:34-76`（解析层）、`test.js:79-85`（索引）、`test.js:92-131`（显式通道）、`test.js:132-173`（自动通道）、`test.js:174-239`（集成）。全程离线，`npm test` 约 180ms。
- **常见追问 / 诚实备注**：*加了技能到底让回答变好了多少，你测了吗？* → 没测。本章的回归只能证明"该注入的注入了、该加载的加载了"，证明不了效果提升——那需要一个离线评估集（固定问题 + 期望工具调用序列），第 13 章的评测三型用例是合适的落点。如实说"主路径测了、效果评估还没做"比含糊过去安全。

## T3 架构设计（对标 AI 技术负责人）

### Q8：技能和子 Agent（第 6 章）是什么关系？怎么组合？

- **考点**：两类"复用"的粒度区分 + 组合能力。
- **答题结构**：知识复用 vs 执行复用 → 组合场景 → 落到同一份代码。
- **参考话术**："两者都是复用，粒度不同。技能是**知识的复用**：同一个 Agent 内，把专家流程注入上下文，不新增实例；子 Agent 是**执行的复用**：新起一个 Agent 实例，独立上下文，可以并行。组合方式很自然：父 Agent 识别到任务匹配某个技能，加载技能拿到步骤框架，其中某一步很重（比如要扫整个仓库找线索），就把那一步委派给子 Agent，结果汇回来继续按步骤走。技能回答'怎么做'，委派回答'谁来做'。"
- **代码锚点**：两套能力在同一个构造函数里注册——`agent.js:54-64` 注册 `delegate_task`，`agent.js:66` 注册 `skill` 工具；`agent.js:108-111` 里记忆召回和技能匹配并行执行，委派发生在推理循环内（`agent.js:134-184` 的工具调用分支）。
- **常见追问**：*子 Agent 会继承技能吗？* → 本章不做技能的传递：子 Agent 只拿到任务描述和受限工具集（`agent_tool.js` 的 fork 语义）。生产中让子 Agent 也带技能是个真实需求，做法是把父 Agent 已加载的技能正文拼进子 Agent 的 system。

### Q9：技能质量怎么保证？坏技能会怎样？

- **考点**：治理意识——把"知识资产"当工程物件管理。
- **答题结构**：谁写 → 验收标准 → 坏技能的危害与防线 → 演进。
- **参考话术**："技能由领域专家或一线使用者写，验收看三点：步骤可执行（每一步都能对应到具体工具操作）、要点可验证（'先定位再读文件省 token'这种能拿数据说话）、示例真实（给出'用户这么问 → Agent 这么做'的触发样例）。坏技能比没技能更糟——技能正文会被模型当成指令读，一个过时的步骤会被忠实地执行。所以防线有两层：注入时标注'任务符合该技能场景时'照做，保留模型的判断力；技能是 markdown 文件，能进 git、能 review、能回滚，团队可以审质量。"
- **代码锚点**：注入标题的措辞在 `skill_trigger.js:36`；三个示例技能就是可 review 的样本（`skills/code-review/SKILL.md:7-21` 的步骤与要点分节）；技能质量直接影响注入文本，`buildSkillInjection`（`skill_trigger.js:33-46`）不做任何清洗，写什么就注入什么。
- **常见追问**：*技能里的错误步骤导致事故，怎么定位？* → 注入的文本就在 system prompt 里，日志里能看到当轮注入了哪个技能，能追溯到具体文件；这也是坚持 markdown 而不是把经验塞进代码字符串的原因——可追溯。

### Q10：如果让你从 0 到 1 设计一个企业的技能平台，路线是什么？

- **考点**：0→1 方案设计能力，以及对真实产品（Qwen Code / Claude Code / Hermes）的对照理解。
- **答题结构**：三阶段（可用 → 可治理 → 可进化）→ 每阶段交付与验收 → 明确说清哪一步最容易做错。
- **参考话术**："三个阶段。**第一阶段可用**：`skills/<name>/SKILL.md` + frontmatter + 双通道触发 + 注入，本章的 266 行就是这一阶段的最小原型，验收标准是'加一个技能不用改代码'。**第二阶段可治理**：加载时校验 `tools` 字段对着真实工具表、技能长度设上限（防止一个技能吃掉整个上下文窗口）、版本与 owner 元数据、使用埋点（哪个技能被自动命中、命中后任务是否真的做完了），验收标准是'能回答哪个技能值得留'。**第三阶段可进化**：从成功会话里生成技能草稿，人审后入库；离线评测集做技能回归（同一批任务，注入与不注入对比完成率）。最容易做错的是跳过第一阶段直接做语义检索或者自动学习——先把文件格式、触发通道、注入位置这三件事做扎实，检索和生成都只是替换内部实现，接口不用动。"
- **代码锚点**：文件格式与解析在 `skill_store.js:27-57`，匹配实现在 `skill_registry.js:44-63`（换 embedding 只动这里），触发策略在 `skill_trigger.js:16-26`（换策略只动 `AUTO_INJECT_LIMIT` 与 `matchSkillsForInput`）；本章实现与 Qwen Code 的 `SkillTool` / `SkillActivationRegistry`、Hermes 的 `skill_view` 机制同构（`skill_store.js:11-12`、`skill_tool.js:6`）。
- **常见追问**：*技能多了以后（几百个）怎么办？* → 全量打分变成先粗筛再精排：按场景/标签分组，先用关键词或向量召回候选，再用小模型精排 Top N；清单也不能全量注入 system，改成按当前任务动态生成。
