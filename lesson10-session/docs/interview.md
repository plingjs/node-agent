## T1 基础原理（必过线）

### Q1：Agent 的会话保存恢复，到底要持久化什么？

- **考点**：能不能把运行时状态按"崩了能否重建"分层，而不是笼统地说"都存下来"。
- **答题结构**：四层 → 每层给结论和理由 → 收口成一句可背的话。
- **参考话术**："运行时状态分四层，只有两层该落盘。**对话上下文**是核心：上下文管理器（cm）的三层——system、summary、recent——就是对话本身，丢了就断了。**会话元数据**也要存：id、标题、创建与更新时间、模型名、消息数，列表和恢复调度都要用。**记忆**不用会话层再存一遍，第 5 章就是文件持久化，天生跨会话。**工具和技能**是静态资产，启动时重建即可；运行时的防失控状态（loop 签名计数、错误预算）本来就是每次 run 重建的。一句话可以背：**状态要存，资产要建**。"
- **代码锚点**：落盘的三个字段在 `serializeContext`（`session_state.js:39-45`）；元数据在 `SessionManager.create`（`session_manager.js:39-53`，含 id/标题/模型/时间戳/消息数）；守卫每次 run 重建见 `agent.js:94-96`（`_newGuards`）；测试里"只存基础 system"这条行为被 `test.js:84` 钉住。
- **常见追问**：*registry 里的工具函数能不能一起序列化？* → 不能，函数没有 JSON 表示；能序列化的是工具的 schema 和名字，工具本身的构造应该走代码（`core_tools.js:21` 的 `buildCoreTools`），这也是"资产"的含义——启动时用代码装一遍。

### Q2：多会话怎么管理？`/use` 切换的那一瞬间，内存里发生了什么？

- **考点**：是否清楚"单活跃会话"这个模型，以及在最少的代码里怎么表达它。
- **答题结构**：存储形态 → 内存模型 → 切换的三步 → 启动恢复复用同一条路径。
- **参考话术**："一个会话就是一个 `sessions/<id>.json` 文件，id 取 uuid 前 8 位——够人抄。内存里同一时刻只有一个会话的 cm，切换的语义是三步：**先把当前会话存回去 → 再把目标会话文件读出来 → `restoreContext` 覆盖内存里的 cm 三层**，然后把 system 换回基础 prompt。启动时复用同一条路径：`list()` 按更新时间倒序取第一个，也就是上次最后一个聊过的会话，于是有了跨进程续聊。文件层的能力是 CRUD 加一个只改元数据的 `touch`。"
- **代码锚点**：`SessionManager` 的构造函数和 `create`（`session_manager.js:29-53`）、`list` 按 `updated_at` 倒序（`session_manager.js:74`）；切换实现在 `main.js:83-90`；启动取最近一个在 `main.js:107-117`；`/sessions` 的打印在 `main.js:92-104`；切换测试在 `test.js:229` 和 `test.js:260`（两个会话互不干扰）。
- **常见追问**：*为什么不支持两个会话同时挂着？* → 内存里只有一个 cm，同时挂着要每个会话配一个 Agent 实例（各自一份 registry 引用和 cm），内存翻倍；产品里常见的做法是懒加载——前台只保留活跃会话，其余都在磁盘上。真需要并发就是多进程或多实例，那又回到存储层的并发写问题（见 Q9）。

### Q3：重开会话后，Agent 怎么"想起来"之前聊过什么？

- **考点**：能不能把"本次会话的连续性"和"跨会话的持久性"分开，而不是混成一句"它有记忆"。
- **答题结构**：两条互补机制 → 各自的载体 → 一句话区分。
- **参考话术**："两层机制互补。**上下文层**管这次会话的连续性：`restoreContext` 把 summary 和 recent 填回 cm，模型下一轮直接看到'压缩过的旧历史 + 近期原文'。**记忆层**管跨会话的持久性：用户偏好、项目约定这些事实的载体是 `memories/` 下的 markdown 文件，恢复后第一轮 run 照常召回注入。一句话：**上下文管'这次会话别忘事'，记忆管'跨会话不忘人'**。恢复机制只负责前者，后者是既有能力，两套系统正交——所以恢复会话的代码里看不到任何记忆相关的处理。"
- **代码锚点**：恢复只覆盖三层（`session_state.js:52-57`）；记忆在 `run` 开头召回并拼进 system（`agent.js:112-121`）；记忆存储根目录是固定路径（`memory_store.js:29-32`，生产会改成可配置）。
- **常见追问**：*如果摘要（summary）也在文件里，它和记忆有什么区别？* → 摘要是一次会话内被压缩的历史，属于"这次对话说过什么"；记忆是从对话里提取出来、跨会话复用的长期事实。前者会随会话归档，后者长期驻留。

## T2 工程深度（区分度所在）

### Q4：每轮注入的记忆和技能，为什么不能写进会话文件？

- **考点**：上下文生命周期这条线最容易画错，看候选人有没有真的想过"system 里哪部分是持久的"。
- **答题结构**：system 的构成 → 直接序列化的两个后果 → 正确做法为什么零额外代码。
- **参考话术**："system prompt 每轮 run 都会被重建成四段：基础提示 + 记忆召回 + 技能注入 + 可用技能清单，后面三段是运行时生成的。如果序列化当前 cm，落盘的就是这份'注入后的快照'，两个后果：恢复时它已经**过期**（那之后记忆库可能变了），而且恢复后第一轮 run 又拼一次注入，新旧两份**叠在上下文里**。正确做法是保存前先把 system 还原成基础 prompt，注入内容留在内存不落盘；恢复后第一轮 run 照常重新召回，走的还是同一条路径，没有补偿代码。这就是'注入 vs 持久'的边界：**注入答'这一轮需要什么背景'，持久答'这段对话说过什么'**，前者每轮重算，后者只在轮次边界落盘。"
- **代码锚点**：注入后的 setSystem 在 `agent.js:120-122`（`Promise.all` 拿召回和技能，拼好再写进 system）；保存前的还原在 `main.js:69`；被钉住的行为是 `test.js:84`。
- **常见追问**：*那注入内容会不会在恢复后丢失一段时间？* → 只丢"上一轮那一份"，恢复后第一轮就补回来了，代价是一次召回调用的开销（第 5 章的召回是关键词匹配，通常没有额外模型调用）。反过来把注入落盘，看起来"省了一次召回"，代价是长期带着一份可能过期的上下文。

### Q5：序列化会话有哪两个坑？

- **考点**：对消息协议和文件 IO 两处边界的熟悉程度，最好能说出"不这么做会炸成什么样"。
- **答题结构**：配对的坑（现象 + 截断解法 + 双向防御）→ 原子写的坑（半截文件的后果 + rename 的原子性）→ 两个坑各自的测试。
- **参考话术**："第一个是**消息配对完整性**。协议要求每条 `role:'tool'` 消息必须回应一次 `tool_calls`；崩溃时机下 recent 末尾会挂着一条没有工具结果的 `assistant(tool_calls)`，这种历史发出去服务端直接 400。解法是序列化时截断到最后一个完整配对边界——承认半截的工具调用没法重放，宁可少一轮也不发非法请求。序列化和恢复**两个方向都截一次**：前者挡崩溃，后者挡'文件被人手工改坏'，数据入口再拦一道比信任上游便宜。第二个是**原子写**，先写 `.tmp` 再 `rename`。直接写目标文件时写到一半被杀，留下半个 JSON，下次 load 时 parse 抛错，整个会话报废——比丢最后一轮严重一个量级。同文件系统内 rename 是原子的，目标文件要么完整旧版、要么完整新版，不存在中间态。"
- **代码锚点**：截断实现 `session_state.js:19-32`（`break` 在 `session_state.js:26`）；序列化与恢复 `session_state.js:39-45`、`session_state.js:52-57`；原子写 `session_manager.js:95-101`（`rename` 在 `session_manager.js:100`）；用例 `test.js:97`（孤立 tool 被截断）、`test.js:111`（恢复入口再截）、`test.js:309`（无 `.tmp` 残留）。
- **常见追问**：*截断会不会把有效历史也丢了？* → 会丢一个残缺的尾巴，这正是选择：那批工具调用没有结果，模型也无从依据。真正需要注意的是截断方向——只保留配对完整的前缀，而不是试图补齐缺失的 `tool` 消息（凭空造一个工具结果比丢一轮更糟）。

### Q6：自动保存的时机怎么选？崩溃时丢什么？保存失败怎么办？

- **考点**：是否做过"保存频率 × IO 成本 × 可接受丢失量"这类工程权衡，以及容错习惯。
- **答题结构**：三个候选方案 → 选定方案与丢失上限 → 失败路径 → 可优化方向。
- **参考话术**："三个候选：每轮推理后保存（细但 IO 频繁）、`run` 结束后保存、纯手动保存。本章选的是**每轮 run 结束后保存 + 退出时保存 + 切换会话时保存**，崩溃丢数据上限是当前这一轮——和 ChatGPT 最多丢最后一条是同一个取舍。配套两个设计：保存失败静默，catch 里只打一行 warn，不打断对话，会话存储是辅助功能；`list()` 遇到坏文件跳过，不报错也不崩。想更细就每轮推理后保存再加防抖（把短时间内的多次写合并），代价是 IO 频率，属于可以按产品形态调的参数。"
- **代码锚点**：保存函数与静默失败 `main.js:66-80`（catch 在 `main.js:77-79`）；退出时保存 `main.js:126-130`；每轮自动保存的调用与日志 `main.js:212-213`；坏文件跳过 `session_manager.js:67-71`。
- **常见追问**：*为什么不用进程退出钩子只靠 `process.on('exit')`？* → 退出钩子里的异步 IO 不可靠（事件循环已经在收尾），本章的做法是在主循环里显式保存（`/exit` 分支），不依赖信号；真要兜底就是每个轮次边界都落盘，丢失窗口变成"半轮"。

### Q7：Loop 检测判定死循环之后 `break`，会有什么后果？你是怎么发现和修的？

- **考点**：这是本章最有区分度的一题——看候选人有没有"改一处要想同族还有没有"的意识，以及修 bug 是否配回归。
- **答题结构**：现象 → 根因 → 修复 → 验证（修复前后同一份测试的结果对比）。
- **参考话术**："后果是**孤儿 tool 消息**，具体表现是服务端 400：`Messages with role 'tool' must be a response to a preceding message with 'tool_calls'`。触发条件很窄——模型一条响应里同时要调两个工具，第一个刚好触发死循环判定，原来的 `break` 会让第二个调用一条 `tool` 消息都没有，下一轮 `assistant(tool_calls)` 后面少一条配对。修法是加一个 `loopDetected` 标记：判定之后同一条响应里剩下的调用不再执行，但每条都要回填一条错误消息，用 `continue` 而不是 `break`；措辞也分开，第一条是'检测到死循环'，后面的是'本轮已判定死循环，跳过执行'，模型能看到区别。发现路径是同族扫描：主 Agent 有自己的工具循环，子 Agent 也有一份，两处都写了 `break`，所以我一并改掉。验证是回归用例：断言消息序列里每条 `tool_calls` 都能找到配对的 `tool` 消息。同一份 `test.js` 放到修复前的代码上跑，结果是 10 通过 2 失败，红灯直接点名 `tool_call s2b 缺少配对的 tool 消息`；修完全绿。"
- **代码锚点**：修复后的判定 `agent.js:151-163`（`loopDetected` 在 `agent.js:155`，`continue` 在 `agent.js:163`）；阈值常量和判定函数 `agent.js:24` 与 `agent.js:98-103`；子 Agent 的同一处 `subagent.js:133-145`；两个回归用例 `test.js:122`、`test.js:180`。
- **常见追问**：*为什么不在执行前就检查整批 tool_calls，发现死循环直接整批回填？* → 逻辑上等价，区别在"第几条触发"：逐条判能保留下前面那几条真实执行的结果，整批判会把已经执行成功的调用也丢掉。另外要注意这个 bug 只在多 `tool_calls` 时暴露，单调用测试覆盖不到——这也是它藏得久的原因。

## T3 架构设计（对标 AI 技术负责人）

### Q8：多会话之间，什么该隔离、什么该共享？

- **考点**：把"隔离/共享"当成主动的设计决策，而不是默认行为。
- **答题结构**：隔离什么（对话上下文）→ 共享什么（记忆）→ 落成一句判断依据。
- **参考话术**："对话上下文**刻意隔离**：每个会话有独立的 cm 和独立的 JSON 文件，切换时 `restoreContext` 整体覆盖三层，A 会话的工具调用记录不会出现在 B 会话里。记忆**刻意共享**：`memories/` 目录所有会话共用——'用户用 4 空格缩进'这种偏好应该跨会话生效，否则每开一个新会话都要重新教它一遍。**共享什么、隔离什么，是设计决策，不是默认**：短期状态按会话隔离，长期知识按用户共享。这个判断还能推广到多用户场景——把 `memories/` 按用户分目录，会话目录也按租户分，隔离粒度就从'会话'上升到'用户'。"
- **代码锚点**：会话目录可注入（`session_manager.js:29`，测试就靠这个参数把数据写到临时目录），主流程用默认目录 `main.js:62`；记忆根目录是固定路径 `memory_store.js:29-32`，要按租户隔离就得改这里；测试隔离的手段本身也是证据——`test.js:42-61` 会把 `memories/` 改名到 `.seed-backup` 再还原，说明记忆是"跨会话共享的一等公民"。
- **常见追问**：*两个会话同时读同一份记忆会不会打架？* → 读不会（都是读文件）；写是"读-改-写"，本课的记忆写入是追加式的新文件，冲突面很小。真到多进程高频写就要加锁或换带事务的存储。

### Q9：零依赖的 JSON 文件存储，怎么演进到生产？

- **考点**：知道当前方案的边界在哪，并且能给出"接口不变、实现替换"的迁移路径。
- **答题结构**：现状（优点 + 局限）→ 迁移路线（SQLite → 分布式）→ 为什么迁移成本低。
- **参考话术**："现状是每会话一个 JSON 文件加 `.tmp` + `rename` 原子写，优点是零依赖、人类可读、可以 `cat` 出来排查，教学和单机自用都够。局限三条：**没有并发写锁**（两个进程同时写同一会话会互相覆盖）、**没有索引**（会话多了 `list()` 是全表扫 + 全量 parse）、**单机**（多实例部署共享不了）。迁移路线是两步：先换 SQLite，事务解决并发、索引解决列表慢、单机仍然够用；再往上是 Redis 或对象存储，多实例共享会话状态。迁移成本低是因为存储细节被关在 `SessionManager` 里：`create/load/save/list/delete/rename` 的签名不动，只需要重写 `_atomicWrite`、`load`、`list` 三个方法的内部实现——这就是仓储模式的价值。"
- **代码锚点**：默认目录 `session_manager.js:19-22`；`list()` 的扫描与排序 `session_manager.js:56-75`；原子写 `session_manager.js:95-101`；CRUD 其余方法 `session_manager.js:104-134`。
- **常见追问**：*换 SQLite 时 `recent` 消息数组怎么存？* → 消息数组可以整体存成一个 JSON 文本列（读写路径几乎不变，最小改动），也可以拆成 messages 表按 `session_id` 关联（可查询、可增量追加）。前者的迁移是几小时，后者是几天——先按最小改动上线，等真需要按消息查询再拆表。

### Q10：如果让你从 0 到 1 设计一个多用户的会话系统，路线是什么？

- **考点**：0→1 的方案设计能力，以及对真实产品（ChatGPT / Claude / Qwen Code）的对照理解。
- **答题结构**：三阶段（能用 → 可治理 → 可扩展）→ 每阶段的交付与验收 → 明确说清哪一步最容易做错。
- **参考话术**："三个阶段。**第一阶段能用**：会话是一份状态快照（cm 三层 + 元数据），存储用文件加原子写，切换语义是 save 旧的、load 新的，本课这 211 行就是这一阶段的最小原型，验收标准是'重开进程能接着聊、能开第二条线'。**第二阶段可治理**：存储换 SQLite（并发与索引），加会话级 token 与成本统计（按 `session_id` 聚合），加搜索与分页，加导入导出，验收标准是'能回答哪个会话贵、能找回旧会话'。**第三阶段可扩展**：多租户隔离（按用户分目录或加 tenant 列）、多实例共享会话、会话数据的保留策略与合规。最容易做错的是**跳过第一阶段直接上分布式存储**——序列化协议（存什么、怎么截断、注入内容不落盘）没定清楚，存到哪都救不回来；反过来协议定对了，换存储只是重写三个方法。"
- **代码锚点**：协议与截断 `session_state.js:39-45`、`session_state.js:19-32`；注入不落盘 `main.js:69`；元数据字段 `session_manager.js:43-50`；留了口子但没接线的 `rebuildContext`（`session_state.js:60`）——它说明"从存储恢复出一个完整 cm"这个用法在接口上已经预留。
- **常见追问**：*会话数量上百万以后，这套设计最先撑不住的是哪里？* → 不是存储，是恢复策略：启动时 `list()` 全量读会崩，要改成按需分页 + 延迟加载；其次是"每个活跃会话一个 cm"这个内存模型，并发会话数会被内存限制，要靠淘汰策略（LRU 落盘 + 用时再载）。
