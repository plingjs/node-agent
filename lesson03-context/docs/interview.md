# lesson03 · 上下文管理（合并版）—— 面试题讲解（Node 版）

> 10 题，三层深度。每题按固定结构展开：**考点 → 答题结构 → 参考话术 → 代码锚点 → 常见追问**。
> 本课可引用的"证据"：14 个源文件 1105 行 + 406 行测试（20 个用例，实测约 45ms 全绿）、`search_logs` 实测返回 858901 字符被截成 4025、压缩前后账本 569 → 122、Loop 提前终止的孤儿 `tool_calls` 实测复现再修复。

## T1 基础原理（必过线）

### Q1：上下文为什么会溢出？溢出的后果是什么？

- **考点**：能不能从"LLM 无状态"推到"每轮全量重发"，再指出 Agent 的增长尖峰来自工具结果。

- **答题结构**：机制 → 两个增长来源 → 两种后果（可见的 400 / 静默劣化）→ 本课的处理原则。

- **参考话术**："LLM 是无状态函数，服务端不留对话状态，所以每轮请求都要带上完整历史——这就是溢出的根。增长有两个来源：对话本身每轮至少加两条消息，是线性的；工具结果是尖峰，我这一章的 `search_logs` 返回 10000 行日志、858901 字符，一条消息就能顶掉整个窗口，这是 Agent 区别于普通聊天的关键点。后果分两种：API 报 400 是看得见的失败，好办；更阴险的是实现偷偷裁掉最早的消息'挤进'窗口，system prompt 和早期决策一起没了，模型行为漂移还没人发现。所以处理原则是**提前管理预算**，不是等溢出再补救——溢出时请求已经被拒，没有补救机会了。"

- **代码锚点**：`context_manager_v2.js:75-82`（`build()` 每轮组装全部消息，这就是"全量重发"的物理体现）；`agent.js:59`（推理前查水位线）；`agent.js:114`（工具结果回填前先截断）。

- **常见追问**：*你怎么知道快到上限了？* → 靠 token 估算 + 水位线，见 Q2 和 Q8；估算精度不重要，重要的是判断"是否接近上限"。

### Q2：token 怎么数？估算有 10~20% 误差，凭什么叫预算管理？（压力题）

- **考点**：能不能把"近似"讲成工程决策，而不是"没做完的精确版"。

- **答题结构**：精确做法 → 零依赖近似（两条比例）→ 误差为什么可接受（二分类 + 缓冲带）→ 什么时候必须精确。

- **参考话术**："精确做法是 tokenizer 逐 token 计数，误差接近 0。零依赖版本按字符类型分账：中文一字一 token，其余每 4 字符一 token，这是 GPT 系 BPE 词表的经验值。误差能接受的原因是判断的性质——预算管理问的是'是否接近上限'这个二分类问题，不是精确到第几个 token；水位线取可用预算的 80%，剩下 20% 的缓冲带正好吸收估算误差。真正需要精确的地方是计费对账和逼近硬上限的最后 1%，那是另一个模块的事。另外消息不等于纯文本，每条还有 role、tool_call_id 这些包装开销，我在 `estimateMessageTokens` 里按 4 / 8 分开算了。"

- **代码锚点**：`token_counter.js:16-24`（CJK 码位区间）、`token_counter.js:27-37`（两条比例）、`token_counter.js:40-52`（单条消息的结构开销）、`context_manager_v2.js:56`（水位线公式里的 0.8）。

- **常见追问**：*换精确 tokenizer 要改多少东西？* → 只换 `estimateTokens` 的实现，水位线、三层结构、递归压缩一行不动——估算精度可插拔，预算架构不是。第 13 章的观测模块就是直接复用这个估算器接口做成本核算的。

### Q3：滑动窗口为什么不行？你后来改成了什么？

- **考点**：是否真踩过"最直观的解法"，以及能不能说出改进的驱动力。

- **答题结构**：做法一句话 → 三个缺陷 → 升级方案 → 负向测试的证据。

- **参考话术**："滑动窗口是从最新往前保留到预算满，'近期更重要'这个时间局部性的直觉是对的，但它只按位置取舍：system prompt 在最前面，预算一紧就最先出局，模型失去角色和行为约束；用户第一轮的目标、第三轮确认的决策同样最旧，也最先被丢，而这些恰恰价值最高。我把它实现成一版对照代码，配了一个 `isSystemPreserved` 探针做负向测试，构造预算只够一条 user 消息的场景，断言它确实丢了 system——缺陷被钉在测试里，然后才升级成分层截断：system 与最后一条 user 永远保留，中间历史从新到旧填剩余预算。**先暴露缺陷再修，比直接抛最优解更能说明我在设计什么。**"

- **代码锚点**：`sliding_window.js:21-33`（滑动窗口实现）、`sliding_window.js:39-44`（探针）、`test-context.js:56`（负向断言 `isSystemPreserved(...) === false`）、`context_manager.js:26-67`（分层截断的三步分配）。

- **常见追问**：*分层截断还丢信息吗？* → 会，中间历史是整体丢弃，第 1 轮确认的决策丢了就找不回来，所以还要压缩（Q4）；压缩只保结论，跨会话的知识要靠外置检索（记忆，第 5 章）。

## T2 工程深度（区分度所在）

### Q4：截断和压缩的本质区别？生产上怎么选？

- **考点**：取舍依据、成本、风险三者的权衡。

- **答题结构**：本质对比 → 生产组合 → 压缩质量靠什么兜底。

- **参考话术**："截断按位置或角色取舍，零成本，丢掉的信息再也不会回来；压缩按语义取舍，代价是一次 LLM 调用的 token 和延迟，换来关键信息以摘要形式保留，风险是摘要本身失真。生产不是二选一，是组合：近期消息留原文（时间局部性，最近的对话需要逐字细节）、久远历史压成摘要（只留结论和决策）、单条工具结果单独截断。压缩质量的上限由摘要 prompt 的**必须保留清单**决定——用户目标与约束、已确认决策、关键数字与路径、未完成事项、用户的偏好和纠正，这几类写多细，摘要就保多准。"

- **代码锚点**：`summary_compactor.js:15-24`（必须保留清单）、`summary_compactor.js:32-41`（`summarize`，注意第二个参数传 `null`）、`summary_compactor.js:47-63`（切分与保留）、`context_manager_v2.js:28-37`（工具结果 head+tail 截断）。

- **常见追问**：*摘要 prompt 里为什么要专门列"用户的纠正"？* → 用户说过"不要用 pytest"这类纠正，丢了就是重复犯错，属于最贵的一类丢失。

### Q5：压缩的切点有什么坑？消息序列有什么隐含约束？

- **考点**：协议层的配对约束，以及"这类 bug 会重复出现"的意识。

- **答题结构**：坑是什么 → 为什么 → 修复 → 同族坑（我在本课又撞了一次）。

- **参考话术**："坑是切点落在 `role: "tool"` 消息上。OpenAI 协议要求 tool 消息紧跟对应的 `assistant(tool_calls)`，纯按位置 slice 一旦切在 tool 上，压缩后的消息以一条孤儿 tool 消息开头，`build()` 出来前面没有 tool_calls，请求直接被拒 400。修复是切点前移，把对应的 assistant(tool_calls) 一起留在 recent。这个认知的通用形态是：**消息序列不是独立条目的集合，是带配对约束的组**，`assistant(tool_calls)` 和它的 N 条 tool 结果必须同生共死。我在这一章里又踩了同族的第二次：死循环检测触发时原来只给触发的那一条回填错误就 `break`，同一批里后面的 tool_calls 变成孤儿——我一轮构造 3 个调用、第 2 个触发，跑出来实测孤儿 id 是 `b3`。改成用 `loopDetected` 标记加 `continue`，整批逐条回填，触发的那条报'重复调用 3 次'，没执行的那条报'本轮已判定死循环，跳过执行'。"

- **代码锚点**：`context_manager_v2.js:101-108`（切点前移的 `while`）、`agent.js:84-96`（整批回填）、`test.js:124`（断言每个 tool_call id 都有配对回复）、`lesson04-core-tools/test.js:207`（切点用例的跨章归属，实测单跑 1/1 通过）、`lesson04-core-tools/test.js:237`（同名 Loop 配对用例）。

- **常见追问**：*切点那条用例在你这一章吗？* → 不在，它在 `lesson04-core-tools/test.js:207` 跨章回归跑着——如实说清归属比含糊其辞安全；本课自己的 20 个用例里，Loop 提前终止的配对完整性有专门一条（`test.js:124`）。

### Q6：工具结果几 MB 怎么办？

- **考点**：截断策略的细节，以及"截断解决进入预算、落盘解决要不要全量"的分层。

- **答题结构**：为什么是尖峰 → head+tail 的理由 → 两级方案（截断 / 落盘加路径）。

- **参考话术**："工具结果是 Agent 里唯一能一条顶掉窗口的东西。这一章的 `search_logs` 实测返回 858901 字符，包成结果 JSON 是 868901 字符，回填时切成 4025 字符，中间那截换成一句 `[中间 864901 字符已截断]`。留头留尾而不是只留头部，是因为结构化输出头部有格式和上下文、尾部有结论和最新状态，只留头部会丢掉'最后发生了什么'；中间那句省略标记本身也是信息，模型看到它知道这里缺了一截，可以换工具重查。生产再进一步是落盘加路径引用：完整内容写文件，上下文里只放路径和首尾摘要，模型需要时分段读回来。**截断解决'进不进得去'，落盘解决'要不要全量'。**"

- **代码锚点**：`context_manager_v2.js:21`（1000 token 上限）、`context_manager_v2.js:28-37`（head+tail 与标记）、`tools_demo.js:51-63`（`search_logs` 生成 10000 行）、`test.js:44`（回填内容含"已截断"）、`agent.js:114`（截断发生在回填之前，水位线统计的才是真实发送量）。

- **常见追问**：*按 4 字符折算字符数有什么问题？* → 纯中文文本一字一 token，同样的 token 预算换算成字符数会多留约 4 倍，中文大结果截断后仍然偏大；这是本课记录在案的精度缺口，生产要按真实 token 数切。

### Q7：一条"错误预算耗尽"的分支，你怎么证明它不是死代码？

- **考点**：测试是否真的覆盖到分支，还是只跑主路径。

- **答题结构**：这条分支是什么 → 怎么测 → 测试过程中的真实翻车 → 通用检查手法。

- **参考话术**："错误预算的逻辑是工具返回 `retryable` 错误时累加计数，到 4 次把错误码换成 `ERROR_BUDGET_EXHAUSTED`，模型看到它就换方案。要测到它，需要一个总是抛可重试错误的工具，于是我在测试里注册了一个 `flaky`，每次 `throw executionFailed("网络超时", true)`。第一次写的时候挂得很漂亮：同一个工具、同一套参数连调 4 次，第 3 次就被 Loop 检测拦下判成死循环，压根走不到预算分支。改成每次带一个不同的 `attempt` 参数，签名各不相同，才真正覆盖到目标路径——这条用例断言前 3 次是 `EXECUTION_FAILED`、第 4 次起换成 `ERROR_BUDGET_EXHAUSTED`。顺带说，本课之前这条分支是没有任何测试保护的，只有代码存在。"

- **代码锚点**：`agent.js:102-109`（错误预算分支）、`agent.js:17`（`LOOP_THRESHOLD = 3`，就是它先拦截）、`test.js:172`（用例起点）、`test.js:190`（每次换参数的注释）、`test.js:199-200`（断言前 3 次与第 4 次）。

- **常见追问**：*平时怎么发现"写了但没生效"的代码？* → 搜索导出符号的引用（无引用即死代码）、逐个检查断言是否真的构造了失败场景、每个修复都配回归测试——这套方法在第 6 章的代码审查里排查出过五类同类纰漏。

## T3 架构设计（对标岗位"0→1 方案设计"）

### Q8：Token 预算怎么分配？水位线为什么是提前触发？

- **考点**：预算体系的参数化能力，以及"为什么不等满"的工程判断。

- **答题结构**：总预算的拆分 → 三个参数各管什么 → 提前触发的理由 → 可观测性。

- **参考话术**："总预算是 `system + summary + recent + 输出预留`。输出预留要单独留（这一章给 512），不预留的话输入把窗口填满，模型没有余量生成回复，轻则被截成半句重则 400，这是最容易被漏的参数；工具结果单独设上限（1000 token 一条）并截断，因为它才是尖峰来源；system 通常固定且偏大，历史占剩下的部分。水位线公式是 `(maxTokens - reserveForOutput) × 0.8`，这一章配下来是 2867，达到就压缩。提前的原因有三条：压缩本身要占一次 LLM 调用的时间和额度；下一轮可能又来一条大工具结果；等 100% 时 API 已经拒了，没有补救窗口。那 20% 缓冲顺手把 token 估算误差也吸收了。另外必须配账本——`budget()` 把 system / summary / recent / total 分层打印，不然'为什么压缩了还超预算'无从排查。实测过一组数字：把预算压到 `maxTokens 400 / ratio 0.5`，压缩前总量 569（水位线 175），压缩后 recent 层从 560 降到 101、summary 层 12、总量 122。"

- **代码锚点**：`context_manager_v2.js:47-61`（四个参数与水位线计算）、`context_manager_v2.js:90-92`（`needsCompaction`）、`context_manager_v2.js:128-143`（`budget()` 账本）、`main.js:29-34`（演示用的参数）、`test.js:66` 与 `test-context.js:138`（极小预算强制触发压缩的用例）。

- **常见追问**：*这套预算是静态的，怎么演进？* → 按任务类型调 ratio、按模型窗口自动配置、把 token 成本接进观测告警（第 13 章的 telemetry 就是拿这一章的估算器算成本的）。

### Q9：压缩会不会丢"用户刚说的重要指令"？怎么设计才安全？

- **考点**：能不能给出结构性的防护清单，而不是"我压得比较小心"。

- **答题结构**：先给结论（时间局部性）→ 五条防护 → 分层的安全观。

- **参考话术**："不会，靠时间局部性：压缩只针对久远历史，最近 `keepRecent` 条原文不动，用户的当前指令一定在 recent 层。完整的安全设计分五条：近期保留原文层；摘要 prompt 里有必须保留清单（目标、约束、决策、事实、未完成、偏好纠正）；摘要消息带 `[对话历史摘要]` 前缀，告诉模型这是压缩产物、可能丢细节，防它对摘要过度自信；摘要消息的 role 用 user 不用 assistant，否则模型会把摘要当成自己说过的话，污染自我认知；压缩切点不落在 tool 消息上，保配对完整。**防丢分两层：不能压的用结构保证，压了以后别被误解用 prompt 标记保证。**"

- **代码锚点**：`context_manager_v2.js:51`（默认 `keepRecent` 6，`main.js:34` 用 4）、`context_manager_v2.js:78`（摘要消息的 role 与前缀）、`context_manager_v2.js:101-108`（切点前移）、`summary_compactor.js:15-24`（保留清单）、`test-context.js:107`（切分与保留条数的断言）。

- **常见追问**：*摘要失真怎么发现？* → 靠离线评测集（第 13 章）：固定问题集 + 期望的关键事实，换 prompt 或换模型前跑一遍回归；更彻底的方案是结构化摘要，把目标/决策/事实/待办做成 JSON 字段，字段天然有上限也便于校验。

### Q10：工具系统和上下文管理为什么要落在同一个主循环？这个 Agent 离生产还差什么？

- **考点**：架构收口能力 + 对"完整形态"和"生产差距"的边界感。

- **答题结构**：三处协同 → 接口的本质 → 差距清单 → 排优先级的判断。

- **参考话术**："三处协同都在 `agent.js` 里：工具结果先截断再回填，因为尖峰来自工具，没截断的话一次日志查询就能顶爆预算；水位线检查挂在每轮推理之前，保证发出去的消息永远在预算内，也让'工具结果 → 水位线 → 压缩'形成闭环；Loop 检测在工具执行前拦重复调用、错误预算在执行后按 `retryable` 累加。接口的本质是工具流水线的产出（**结构化错误 + 原始结果**）正好是预算层的输入：`retryable` 决定预算是否累加，结果长度决定要不要截断。一句话收口：合体的本质是让三条链路共享同一个消息生命周期。离生产还差一批东西，我按优先级排：精确计数与成本对账、会话持久化（摘要现在只在内存，进程退出就没了）、大结果落盘加路径、重试退避熔断、流式输出、观测与评测——前四项属于'敢不敢接真实业务'，后两项属于运营能力。还有一条本课自己记录的缺口：未知工具默认按 read 放行，`permissions.js:51` 的注释里留了一条待办（第 6 章再改），但第 4 到 13 章还是同一份文件，这条我是如实标注的。"

- **代码锚点**：`agent.js:59`（推理前压缩）、`agent.js:100`（完整流水线执行）、`agent.js:114`（回填前截断）、`agent.js:118`（回填）、`agent.js:102-109`（错误预算）、`registry_full.js:46-84`（六步执行流水线与结构化错误）、`permissions.js:51`（fail-open 的缺口）。
